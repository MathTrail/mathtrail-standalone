## 1. The protocol: stateless, and how a server is authorized

**Statelessness.** "The Model Context Protocol (MCP) is a **stateless protocol**: all the information needed to process a request is contained in the request itself." and "State that needs to span multiple requests (e.g., long-running tasks, application-level handles) **MUST** be referenced by an explicit identifier the client passes on each request." (base protocol, "Statelessness"). The sessions are gone: "Remove protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport." (key changes, item 1). An endpoint of this revision refuses the old requests — "HTTP GET or DELETE to the MCP endpoint: respond with `405 Method Not Allowed`." — and still guards against DNS rebinding: "Servers **MUST** validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks." (Streamable HTTP). The revision is current: "The **current** protocol version is [**2026-07-28**](/specification/2026-07-28/)." (versioning).

**Authorization.** It is optional — "Authorization is **OPTIONAL** for MCP implementations." — and when used it is OAuth 2.1: "Authorization servers **MUST** implement OAuth 2.1 with appropriate security measures for both confidential and public clients." (authorization). Tokens are bound to their server: "MCP servers **MUST** only accept tokens specifically intended for themselves and **MUST** reject tokens that do not include them in the audience claim or otherwise verify that they are the intended recipient of the token." and "The MCP server **MUST NOT** pass through the token it received from the MCP client." (security considerations). "Dynamic Client Registration is deprecated." (client registration). "Authorization servers **SHOULD** issue short-lived access tokens to reduce the impact of leaked tokens. For public clients, authorization servers **MUST** rotate refresh tokens" (security considerations).

**The proxy's confused deputy** (Security Best Practices): "This attack allows malicious clients to obtain authorization codes without proper user consent by exploiting the combination of static client IDs, dynamic client registration, and consent cookies." The cure is consent of the proxy's own: "To prevent confused deputy attacks, MCP proxy servers **MUST** implement per-client consent and proper security controls as detailed below." with a rule on when the state may be set: "The consent cookie or session containing the `state` value **MUST NOT** be set until **after** the user has approved the consent screen at the MCP server's authorization endpoint." And on handles: "MCP servers **MUST NOT** treat possession of a state handle as authentication."

**Tools** (tools page; overview). Defence sits mostly with the host: "For trust & safety and security, there **SHOULD** always be a human in the loop with the ability to deny tool invocations."; "For trust & safety and security, clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers."; "Show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration"; "For authenticated servers, a handle is a name, not a capability. The server should validate the caller's authorization against the handle on every call."

**What paper A takes.** MathTrail's endpoint speaks this revision without sessions [C062], and the service is its own OAuth 2.1 authorization server in front of Google [C040]: an MCP proxy server in the Best Practices' sense, to which the confused-deputy section applies directly. Its SPEC at the pin lists the matching measures — its own consent screen, a consent cookie bound to the client, exact redirect matching, PKCE, tokens held to the canonical resource, Client ID Metadata Documents first and registration as the fallback. Paper A cites the specification as the requirement and claims no audit. Two points of literal conformance are for the author, not for the paper: the product sets a CSRF nonce cookie together with the consent page, before approval, while the rule above speaks of the cookie that holds the `state` (the nonce is not the state, so the rule's intent appears met); and it rotates refresh tokens without retiring the one presented, against a rotation rule whose source, OAuth 2.1 §4.3.1, was not read here.

## 2. MCP Apps and what a card receives

- **The sandbox.** "All View content MUST be rendered in sandboxed iframes with restricted permissions." and "The Host and the Sandbox MUST have different origins." If the resource declares no policy at all, the host uses a default: "default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' data:; connect-src 'none';" and "**No Loosening:** Host MAY further restrict but MUST NOT allow undeclared domains" (`mcpapps2026`). ChatGPT: "Widgets run inside an isolated iframe with a strict Content Security Policy. They cannot access privileged browser APIs such as `window.alert`, `window.prompt`, `window.confirm`, or `navigator.clipboard`." (`openai2026plugins`, security and privacy). A resource that declares a policy with empty lists gets no outside origin: "Empty or omitted = no external connections (secure default)" (`mcpapps2026`, the `connectDomains` field).
- **What a card receives.** The call's arguments, complete: "`ui/notifications/tool-input` - Host MUST send this notification with the complete tool arguments after the View's initialize request completes." (`mcpapps2026`); ChatGPT's `toolInput` is the "Arguments supplied when the tool was invoked." (`openai2026plugins`, reference).
- **Who sees which part of a result — the two documents disagree.** MCP Apps' best practice: "`content`: Text representation for model context and text-only hosts - `structuredContent`: Structured data optimized for UI rendering (not added to model context) - `_meta`: Additional metadata (timestamps, version info, etc.) not intended for model context". ChatGPT's reference on `structuredContent`: "Surfaced to the model and the component. Must match the declared `outputSchema`, when provided."; on `_meta`: "Delivered only to the component. Hidden from the model."
- **The card speaking to the model** may be delayed: the host "MAY defer sending the context to the model until the next user message (including `ui/message`)" (`mcpapps2026`).
- **A tool for the card alone** is kept from the model: "Host MUST NOT include tools in the agent's tool list when their visibility does not include `"model"`" (`mcpapps2026`).
- **The threat model** the specification names: "Malicious server delivers harmful HTML content - Compromised View attempts to escape sandbox - View attempts unauthorized tool execution - View exfiltrates sensitive host data - View performs phishing or social engineering".
- **For a listing in ChatGPT**, a dedicated origin: "Dedicated origin for hosted components (required when submitting a plugin with UI; must be unique per plugin)." (`openai2026plugins`, reference).

**What paper A takes.** The card declares a policy whose lists of domains are empty, which MCP Apps reads as no external connections [C068]; a script that got into its page could still call the service's tools or post to the chat, so what keeps a model-written text from becoming markup is that the card renders text as text, not the policy. Since the two documents disagree on whether `structuredContent` reaches the model, the safe reading is that the model sees everything a tool returns — which is how MathTrail's sealing is designed. One sentence of the draft must change: the card is drawn by `submit_task`, and a host must hand a card the complete arguments of the call that drew it, so the task's key and solution reach the card's memory before the child answers, although the card never shows them [C096]. With the host's own tool log, which anyone in the same chat can open [C064], that exposes the answer to someone who inspects the card or opens the log, not to the child looking at the card. Paper A therefore says the answer is never *shown* before the child answers, not that it never reaches the card. The product's own rule says the answer must not appear in widget payloads, so this goes to the author as K10 (C099, Q71).

## 3. Attacks on tool-using agents and on MCP

- **Indirect prompt injection** (Greshake et al.): "We argue that LLM-Integrated Applications blur the line between data and instructions." (abstract). Planted instructions steer the model and slip past the chat's filters: "1) instructions injected indirectly can successfully steer the model; the data and instruction modalities are not disentangled, 2) prompts that are typically filtered out via the chat interface are not filtered out when injected indirectly" (§4.2). An injection can set a conversational goal — "we design an injection (Figure 4) that instructs the LLM to persuade the end user to divulge their real name." (§4.2.1) — and persist: "achieving attacks’ persistence across sessions by copying the injection into memory" (§3.2). No defence is foolproof: "Unfortunately, it is currently hard to imagine a foolproof solution for the adversarial prompting vulnerability" (§5.6).
- **A threat taxonomy for MCP** (Hou et al.): "we construct a comprehensive threat taxonomy that categorizes security and privacy risks across four major attacker types: malicious developers, external attackers, malicious users, and security flaws, encompassing 16 distinct threat scenarios." (abstract). "This vulnerability arises because MCP tools expose metadata fields (e.g., descriptions) that LLMs treat as authoritative." (§5.1.4); "Tool chaining abuse occurs when multiple low-risk MCP tools are implicitly combined by the model to perform unintended high-impact operations." (§5.3.3). Its gap in authorization — "MCP currently lacks a standardized framework for authentication and authorization across clients and servers." (§6.2) — describes MCP before its later revisions, which have one.
- **Exploits with powerful tools** (Halloran et al.): "we show that industry-leading LLMs may be coerced to use MCP tools and compromise an AI developer’s system through a wide range of attacks, e.g., malicious code execution, remote access control, and credential theft." (abstract). Guardrails are no defence to rely on: "Directly testing the ability of an LLM’s guardrails to prevent these attacks can thus produce false positives which, in turn, may provide a false sense of security against such attacks." (§1).
- **Tool poisoning, measured** (MCPTox): "MCPTox is constructed upon 45 live, real-world MCP servers and 353 authentic tools." (abstract). Its setting is the chat MathTrail lives in: "This setup simulates a realistic scenario where an agent is connected to both a trusted MCP server and a malicious one." (§3.4). "The overall results reveal a widespread and significant vulnerability to Tool Poisoning attacks across a diverse range of popular models, with an average ASR for all model settings was 36.5%." (§4.2); "We found that the Implicit Trigger - Parameter Tampering paradigm was the most successful, achieving an average ASR of 46.7%." and "The model with the highest refusal rate was Claude-3.7-Sonnet, and even it rejected the attack in less than 3% of cases." (§4.4). The rate leaves out invalid outputs: "our ASR is calculated as the number of successful attacks divided by the total number of valid outputs." (§4.1).
- **The post that named it** (Invariant Labs): "A Tool Poisoning Attack occurs when malicious instructions are embedded within MCP tool descriptions that are invisible to users but visible to AI models."; "Rug pull: a malicious server can change the tool description after the client has already approved it."; "In these scenarios, a malicious server can poison tool descriptions to exfiltrate data accessible through other trusted servers."
- **The hosts' warnings and rules.** Anthropic: "Be aware of prompt injections: Malicious MCP servers may include hidden instructions that try to make Claude perform unintended actions." (`anthropic2026customconnectors`); "G. Instructional Software must not contain hidden, obfuscated, or encoded instructions. All behavioral guidance must be human-readable and clearly presented." (`anthropic2026directorypolicy`). OpenAI: "Plugin and tool metadata must not seek secrets or protected context, direct unauthorized data transfers or actions, override platform instructions or safeguards, conceal behavior, or impersonate another party." (`openai2026pluginguidelines`); "OpenAI periodically fetches your MCP server's tools and compares them with the published definitions, including their descriptions, schemas, and annotations." (`openai2026appreview`).

**What applies to MathTrail, channel by channel.**

| Threat | MathTrail's channel | What MathTrail has | What remains |
|---|---|---|---|
| Injection through data the model reads | The parent's free-form notes, up to 500 characters, in every package [C092] | The rule never reads the notes [C097]; a note cannot change what the solver checks, though it reaches the model that writes both the key and the solver [C026] | The notes reach the model that talks to the child; a goal planted there, such as asking for a real name, is a matter of the conversation, which no check of a task sees |
| An injection that persists | `save_profile` writes the notes, which return with every later task | The model calls it at the adult's request; whether the host asks for confirmation is the host's choice | An injection from elsewhere in the chat could write itself into the notes and come back in every session — the memory persistence Greshake et al. describe. A question for the author (Q71) |
| Poisoning or shadowing by another server in the same chat | Another connector's descriptions could alter `submit_answer`'s answer or `save_profile`'s fields, or send away the child's grade, interests and notes | On a card the answer is recorded by the card itself, outside the model [C039] | In text mode the model records the answer. MCPTox measured this setting — an agent with a trusted server and a malicious one — and found tampering with the parameters of the trusted server's calls the most effective attack. The defences — pinning, reviewing descriptions, limiting flows between servers — are the hosts' |
| MathTrail's own descriptions read as poisoning | Its instructions to the model are imperative by design | Plain, readable text; nothing hidden or encoded | Reviewers look for imperative wording; the instructions must stay about MathTrail's own tools |
| Leaks through the card | The card holds the task and, through the arguments of the call that drew it, the key [C096] | No external connections from the card [C068] | Nothing leaves for an outside origin; text rendered as text is the barrier against injected script |
| Leaks of the profile through the model | The model holds the pseudonym, grade, interests and notes once it has read the profile | No real name, birth date or school is kept [C069]; logs hold no content [C036] | Any other tool in the chat can receive what the model holds; the parent's choice of connectors is the defence |

None of the works measures injection through a field like the notes, in a delimited block, in Claude or ChatGPT as they are in 2026; MCPTox's rates come from its own pipeline, and the rest are demonstrations. Paper A cites the literature for the kind of risk and the benchmark for "often", not for a rate in MathTrail's hosts.

## 4. The hosts' rules for children

**Claude.** "Minimum age. You must be at least 18 years old or the minimum age required to consent to use the Services in your location, whichever is higher." and "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else. You also may not make your Account available to anyone else." (`anthropic2025consumerterms`, §2). Enforcement: "We have safety systems in place to detect if people under 18 may be using Claude and we’ll disable accounts based on indicators of minor activity." (`anthropic2026ageassurance`); and on phones, "If you're seeing this message, it means the app store on your device (App Store or Play Store) has identified you as under 18 based on your account information." (`anthropic2026minagerestriction`). Products built on Anthropic's models that serve minors have their own rules: "Products serving minors, including organizations providing minors with the ability to directly interact with products that incorporate our API(s), must comply with the additional guidelines outlined in our Help Center article." (`anthropic2025aup`); "It is the responsibility of organizations to comply with all applicable child safety and data privacy regulations, such as the Children's Online Privacy Protection Act (COPPA) in the United States." (`anthropic2026minorsguidelines`). Custom connectors, the way MathTrail reaches Claude today: "Free users are limited to one custom connector." (`anthropic2026customconnectors`).

**ChatGPT.** "Minimum age. You must be at least 13 years old or the minimum age required in your country to consent to use the Services. If you are under 18 you must have your parent or legal guardian’s permission to use the Services." and "You may not share your account credentials or make your account available to anyone else and are responsible for all activities that occur under your account." (`openai2026terms`). For children under 13: "ChatGPT is not meant for children under 13, and we require that children ages 13 to 18 obtain parental consent before using ChatGPT." and "if you are using ChatGPT in the education context for children under 13, the actual interaction with ChatGPT must be conducted by an adult." (`openai2026safeallages`). Enforcement by age prediction: "The model looks at a combination of behavioral and account-level signals, including how long an account has existed, typical times of day when someone is active, usage patterns over time, and a user’s stated age." and "When we are not confident about someone’s age or have incomplete information, we default to a safer experience." (`openai2026ageprediction`). Parental controls start at 13: "Link their account with their teen’s account (minimum age of 13) through a simple email invitation." (`openai2025ageprediction`). Apps in the directory: "Plugins must be suitable for general audiences, including users aged 13–17. Plugins may not explicitly target children under 13." (`openai2026pluginguidelines`), unchanged since at least December 2025: "Apps must be suitable for general audiences, including users aged 13–17. Apps may not explicitly target children under 13." (`openai2025submissionguidelines`).

**The regulator.** The FTC's inquiry into companion chatbots asks about "limit or restrict children’s or teens’ use of these platforms, or comply with the Children’s Online Privacy Protection Act Rule" (`ftc2025companions`); it is a study, not a rule, and it concerns companion-style use.

**What paper A takes.**
- Neither host admits a child of primary age as a user: Claude's users must be at least 18 and ChatGPT's at least 13, with a parent's permission under 18; both forbid making the account available to anyone else. Only OpenAI's help centre addresses a child beside the adult, and only by asking that the adult conduct the interaction.
- MathTrail's terms make the adult the user, who runs the lesson; the child does not sign in and has no account [C098]. Its card still lets the child press an answer and type a question that goes into the chat in the child's own words (the field "Ask a question about the task", SPEC 8.3 at the pin) — the point where the child acts directly. How that sits with "conducted by an adult" is the author's to weigh, and perhaps a host's review.
- Enforcement can land on the parent: Claude disables accounts on signs of a minor's use, and ChatGPT's age prediction reads patterns of use; lessons for a child in a parent's account are the kind of use that could trip either. Neither text says what happens to a connected app.
- A listing in ChatGPT's directory has to answer "may not explicitly target children under 13"; Anthropic's directory policy has no rule on audiences beyond its usage policy. A custom connector needs no listing.
- Paper A states that the hosts admit only the adult and that MathTrail is designed for a lesson the adult conducts, signs in only the adult and keeps no identity of the child [C069, C098]. It does not claim that the hosts permit a child's use, or that the adult's account makes the child's use compliant. The law is S16's (`privacy-law.md`).

## Answers

**1. The protocol.** Since 2026-07-28 MCP is stateless: every request stands alone, cross-call state is an explicit handle, sessions are gone, and `Origin` must be checked. Authorization, when used, is OAuth 2.1 with tokens bound to their server and never passed through. MathTrail follows this design [C040, C062]; two points of literal conformance are for the author.

**2. MCP Apps.** A card is a sandboxed page whose policy admits only the domains it declares, receives the complete arguments of the call that drew it and that call's whole result, and can call its own server's tools. MCP Apps and ChatGPT disagree on whether a result's structured part reaches the model; the safe reading is that it does. MathTrail's card declares none, so it makes no external connections, and it holds the key in memory without showing it.

**3. Attacks.** Indirect injection, tool poisoning, rug pulls, shadowing and tool chaining are documented; a benchmark found poisoning effective often, and no defence is foolproof. For MathTrail the open channels are the parent's notes, which reach the model that talks to the child and can be rewritten by the model, and other servers in the same chat; its design keeps the notes from deciding anything, and the card records answers outside the model.

**4. The hosts' rules.** Neither host admits a child of 7–12 as a user; MathTrail is designed for a lesson the adult conducts, and the child's own presses and typed questions on the card are the point to weigh. Paper A does not claim that the hosts permit a child's use. ChatGPT's directory bars apps that explicitly target children under 13.

## Remarks

- **How the notes were made.** One model session read the pages and papers, saved their texts and checked its quotations by script; the executor read its report in full, checked the card and the rule in the product's code at the pin, and checked every quotation of these notes again against the saved texts.
- **For the author (G6), none decided here** (Q71): whether the card should stop being drawn by `submit_task`, so that the key does not reach it [C096] — raised as K10; how the card's field "Ask a question about the task", which sends the child's own words to the chat [C100], sits with OpenAI's "the actual interaction with ChatGPT must be conducted by an adult"; registration kept as a fallback, which the revision deprecates though it remains for compatibility; whether a change to the parent's notes should need the adult's confirmation or carry a mark that the adult wrote it; `_meta.ui.domain`, which ChatGPT requires of a listed plugin with UI and the card does not set; `destructiveHint` of `save_profile`, which overwrites what the parent wrote, while OpenAI counts overwriting as destructive and says that undo does not justify `false`; the CSRF nonce cookie set before consent, and refresh tokens rotated without retiring the one presented; timestamps and handles in payloads, which OpenAI asks to justify as strictly required; ChatGPT's coarse location and anonymised ids sent with every call, which the server does not read — the privacy policy could say so; and the parent's account, which a host's age signals could disable or move to a teen's experience.
- **Versions.** The MCP Safety Audit (Halloran et al.) was read in its arXiv version, by Radosevich and Halloran; the published version adds Black as an author and puts Halloran first. MCPTox's version 2 is not consistent on the number of its risk categories.
- **Not read.** OAuth 2.1 (draft 13) and RFC 9700, which the specification cites; MCPTox's table of rates per model, lost in conversion; guidance of the ICO or Ofcom on chatbots.
- **Leads not followed.** CaMeL (Debenedetti et al. 2025), which separates control flow from untrusted data — the formal form of keeping the notes from deciding anything; AgentDojo and InjecAgent, the injection benchmarks MCPTox compares against; a systematisation of security in the MCP ecosystem (arXiv 2512.08290); attacks of malicious remote MCP servers across platforms (Electronics 2026); the NSA's information sheet on MCP security (June 2026); OpenAI's teen protections in its Model Spec.
