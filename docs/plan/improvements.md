### T94. Интересы ребёнка — в каждой третьей задаче

- **Цель:** интересы ребёнка из профиля достаются только каждой третьей задаче, по очереди. Две задачи из трёх получают обычный сюжет, который модель выбирает сама, без интересов.
- **Почему:** в моём профиле интересы «роботы, космос» (2026-10-10), и все задачи шли про роботов и космос. Это раздражает. Правило брало интерес для каждой задачи, а пакет для модели нёс весь список интересов. Прогон T64a видел то же самое: модель держала сюжет интереса во всех 118 задачах (`docs/live/10-variety.md`).
- **Решения автора (2026-10-10, при планировании):** частота постоянная, одна задача из трёх, без настройки в профиле. Пропущенная задача считается так же, как отвеченная. Интерес получает первая задача из каждых трёх, поэтому в новом профиле уже первая задача построена на интересе.
- **Сделать:**
  - правило (`tutor.setting`) даёт интерес первой задаче из каждых трёх и берёт интересы по очереди. Задачи считаются по пройденным, это `ratings.answers` и `skipped` всех тем. Задача на карточке без ответа тоже считается пройденной, потому что бриф, построенный в это время, пишется для задачи после неё: заранее или вместо неё;
  - пакет для модели больше не несёт список интересов. В `child` остаются класс и заметки родителя, а интерес задачи приходит в `brief.setting`;
  - в инструкции модели при пустом `setting` сюжет свой и без интересов ребёнка, даже если модель знает их из чата;
  - тесты, описания схем, полей `save_profile` и `edit_profile`, комментарии;
  - документы: R283, пометки к R63, R205 и R235, SPEC, архитектура, главная страница сайта (en, ru), `docs/catalogs.md`, заметка эталонов прототипа, PRODUCT (только локально, О-73).
- **Как проверить:** `just ci-lint`, `just ci-test`, `just learners-lint`, `just learners-test`, `just ci-learners`, `just ci-site`. Точечно: `go test ./internal/domain/tutor/ -run 'Interest|Skipped|Ahead|Worked|Reference' -v`.
- **Стоимость:** $0. Живой урок в задачу не входит, он тратит лимиты подписки.
- **Сделано (2026-10-10):**
  - правило: константа `tutor.InterestEvery = 3` и счёт пройденных задач `tasksBehind`. В счёт входят ответы, пропуски всех тем и задача на карточке, пока она ждёт ответа. Бриф строится до того, как пропуск этой задачи записан, поэтому без неё задача вместо пропущенной повторила бы её очередь. Отрицательный счёт из испорченного файла считается нулём. Интерес `interests[(n / 3) % len]` выдаётся при `n % 3 == 0`;

  - инструкция модели `task_writing.md`: свой сюжет без интересов, даже известных из чата. Версия инструкций сменилась сама, поэтому задача, написанная заранее по старой инструкции, один раз отбросится и напишется заново;

Из трёх задач подряд ровно одна с интересом, за круг каждый интерес встречается по разу, пропуск считается как ответ. Пример SPEC 3.5 теперь даёт `dinosaurs`. ### T95. Разбор сразу на карточке, без пересказа в чате, и чат без прыжка

- **Цель:** после ответа на карточке разбор появляется сразу и на той же карточке, без просьбы в чат. Модель не пересказывает разбор текстом. Новая карточка не уезжает, пока Claude дописывает следующую задачу.
- **Почему:** мой урок в Claude на v0.5.0 (2026-10-10, снимки).
  - После ответа карточка клала «Разбери ответ» в поле ввода под предупреждением Claude «Use caution before running this prompt», и разбор приходил только после Enter.
  - На верный ответ модель не вызвала `show_result` и написала разбор обычным текстом. На неверный она нарисовала карточку разбора и пересказала её текстом ниже. Пересказ ей велели наши же слова «объясни в двух-трёх фразах рядом с карточкой».
  - После «Другой задачи» чат уезжал вниз, пока Claude дописывал следующую задачу. Под карточкой оставалась пустая полоса.
- **Решено автором (2026-10-10, при планировании):**
  - карточка задачи сама становится разбором: условие и варианты уходят, на их месте разбор под той же шапкой. Вторая карточка под задачей в той же рамке и разбор под вариантами отвергнуты;
  - чат уезжает не в момент, когда появляется задача, а позже, пока Claude работает под карточкой.
- **Сделать:**
  - сервис: ответ `submit_answer` несёт карточке всё, что несёт `show_result`, и собирают его одной функцией;
  - карточка: после ответа разбор встаёт на место задачи, внизу «Другая задача» и выбор темы, в чат ничего не уходит;
  - слова для модели, инструкции и строка карточки: разбор на карточке не пересказывать, `show_result` нужен только для ответа, данного в чате;
  - отступы хоста: карточка берёт только боковые;
  - превью, снимки README и каталога, демо и тексты сайта, инструмент нагрузки, пакет ChatGPT, документы.
- **Как проверить:** `just ci-lint`, `just ci-test`, `just ci-web`, `just web-layout`, `just ci-site`, `just load-lint`, `just load-test`. В `just web-preview` я смотрю сцены `answered, …`. После выката проверяю урок в Claude в вебе и на телефоне.

### T96. Картинка решения в каждом разборе

- **Цель:** разбор каждой задачи показывает картинку решения, и после верного ответа тоже. Сервис не принимает задачу без картинки решения, а модель в каждом пакете видит эталон с нарисованным решением.
- **Почему:** мой урок в Claude на v0.5.2 (2026-10-10, снимки).
  - Четыре задачи на перебор (монеты, двузначные числа, башни из кубиков, роботы) разобраны без картинки, и верные ответы, и неверный. Пятая, про флажки, картинку решения нарисовала: для флажков в пакете темы есть пример вида.
  - Код разбора исправен: сервис отдаёт картинку решения, карточка её рисует. Модель её просто не писала. Поле было необязательным (R276), руководство разрешало не рисовать, «когда нечего показать», а ни у одного из 603 эталонов картинки решения не было.
  - В прогоне 22 решение нарисовали 22 задачи из 37, и ни одна задача на перебор, рыцарей и лжецов, порядок и принцип Дирихле.
  - После T95 картинка задачи уходит вместе с условием, поэтому разбор без картинки решения остаётся совсем без картинок.
- **Решено автором (2026-10-10, при планировании):**
  1. сервис требует картинку решения у каждой задачи во всех темах, в арифметике тоже;
  2. образцы — эталонные задачи: в каждой теме на каждом уровне одна эталонная задача получает картинку решения, всего 35, и пакет всегда показывает такую задачу;
  3. прыжок чата я проверяю в DevTools и присылаю снимок;

### T101.1. Модель ученика: долг за ошибку — стенд

- **Цель:** проверить на стенде учеников правило, при котором одна ошибка почти не сбивает рейтинг, а рейтинг остаётся честным и умеет опускать ребёнка, поставленного слишком высоко.
- **Почему:** чистый Эло при цели 77,5 % делает ошибку в 3,4 раза дороже верного ответа: одиночная ошибка сбивает полоску темы на 23–36 % ранга, и ребёнок боится ошибаться. Простое смягчение штрафа завышает рейтинг, а отдельный «мягкий» показ я считаю обманом. Исследование и симуляции — в разговоре 2026-10-11 и в документе «Сто задач, четыре модели».
- **Решения автора (2026-10-11, при планировании):**
  1. ошибка, r-я подряд в теме, снимает сразу долю штрафа Эло: 0,1, затем 0,4, с третьей — полный штраф. Остаток уходит в долг: общий, для общего уровня, и темы, для её поправки;
  2. верный ответ, пока есть долг, отдаёт 80 % награды на гашение один к одному, без прощения, а 20 % всегда поднимают уровень. Вариант «гашение вдвое быстрее» отвергнут: он навсегда прощает 40 % каждой ошибки;
  3. пробная серия долга не ведёт; один уровень θ + δ читают все — коридор, освоение, экран, карточка, журнал;
  4. цена принята: пока долг открыт, ребёнок показан чуть выше настоящего, и после завышенного старта спуск медленнее;
  5. правило выбирается критерием, записанным до первого прогона, как требуют R163 и R175. Цели экрана: падение карточки после ошибки не больше половины нынешнего, верных, после которых карточка стоит, не больше 10 %. Не хуже нынешней модели: ошибка через 200 ответов, коридор, ложные освоения, отставание, скачок, ошибка после 10 ответов и самая длинная серия неудач. Смещение у G0 через 200 ответов не больше +0,15 ранга. Кандидаты: первая доля 0,1 (основной) и 0,2 (запасной).
- **Сделать:**
  - меры экрана `r8_wrong_fall_W` и `r8_right_still_W`; ни одно прежнее число стенда не двигается;
  - правило с долгом в копии шага стенда; серии считаются и в пробной серии, как `wrong_streak` в продукте;
  - выбор долга: критерий, кандидаты, сравнения без права победить (гашение всей наградой, гашение 2x, освоение по уровню без долга), наборы прогонов: пробный, решающий на 4000 детей и подтверждение на новых отложенных детях (seed 20261012);
  - прогоны и итог в `docs/learners.md`. Если ни один кандидат не прошёл, решение записывается как отвергнутое с числами, и T101.2 не начинается.
- **Как проверить:** `just learners-lint`, `just learners-test`, `just ci-learners` без `-update`.
- **Стоимость:** $0.
- **Сделано (2026-10-11):**
  - меры экрана `r8_wrong_fall_W` (насколько карточка падает после ошибки, в очках) и `r8_right_still_W` (доля верных, после которых карточка показывает то же число); прежние числа стенда не сдвинулись: снимок малого прогона, перенесённые строки, данные страницы и guard зелёные без `-update`;

- **Почему:** 2026-10-25 CI на `main` после #157 упал на тесте `TestMeasurementsAreNotDeliveredTwiceInAnInterval` из `internal/telemetry` с ошибкой `ForceFlush() error = … net/http: HTTP/1.x transport connection broken: http: CloseIdleConnections called`. Выпуск пропустился и прошёл только после перезапуска CI. Причина в тестах, а не в коде сервиса:
  - тестовый клиент телеметрии слал запросы через общий транспорт Go `http.DefaultTransport`, и так же слали тестовые клиенты пакета MCP;
  - тестовый сервер Go, закрываясь в конце любого теста, закрывает и простаивающие соединения этого общего транспорта;
  - на ответ без тела транспорт возвращает соединение в пул раньше, чем отдаёт ответ запросу. Если соседний тест закроет свой сервер в этот промежуток, запрос, на который сервер уже ответил, получает ошибку. Без тела отвечают сборщик в тестах телеметрии и сервис MCP на уведомление (202).

  В работающем сервисе этого нет: у него одна телеметрия на процесс со своим клиентом и нет тестовых серверов. Сбой редкий. Среди 44 красных прогонов CI с 21 сентября он один. У меня его не дали ни 40 полных прогонов пакета телеметрии, ни 48 000 запросов временной программы, которая всё время закрывала простаивающие соединения общего транспорта.
- **Решения исполнителя (2026-10-25):**
  - задачу я завёл по просьбе автора и сделал сразу, поэтому она уходит в архив той же правкой;
  - в задачу вошли и тесты MCP. Сбой там не случался, но риск тот же: каждое подключение шлёт уведомление и получает ответ без тела;
  - запросы идут через собственного клиента тестового сервера (`httptest.Server.Client()`). Транспорт у него свой, и Go закрывает его только вместе с этим сервером. Копия общего транспорта в каждом тесте сделала бы то же, но клиент сервера заведён в Go как раз для этого;
  - через общий транспорт шлют ещё несколько мест: помощники `register` и `get` в тестах `oauth`, три запроса `http.Get` в `internal/app/app_test.go` и браузер в тестах входа нагрузочного инструмента. Остальные тесты этих пакетов уже шлют через клиента своего сервера. В этих местах каждый ответ несёт тело, а соединение возвращается в пул только после того, как тело прочитано, и ответ к тому времени уже отдан. Поэтому они не менялись. Если там появится ответ без тела, их нужно так же перевести на клиента сервера;
  - сам сервис в тестах тоже ходит через общий транспорт: его клиенты Drive (`internal/infra/drive`) и Google (`internal/infra/googleauth`) построены без транспорта своего.
