## Фаза 3. Контент и доменная логика

Чистый Go, тесты, $0. Правила тестов — в CLAUDE.md. Тесты прототипа из `prototype/tests/` переносятся по смыслу, не построчно.

### T23. Контент в бинарнике

- **Сделать:**

  - каталоги тем, навыков и ловушек (из `prototype/data/catalogs/` с изменениями SPEC);

- **Тесты:** из `test_catalogs.py` и `test_examples.py` прототипа; версия не зависит от порядка файлов.
- **Разделы:** SPEC 1.2–1.5; PRODUCT 4.6.

### T24. Шифрование `seal`

- **Цель:** одно место для всего, что шифруется ключом сервиса (О-7, О-25).
- **Сделать:** `internal/infra/seal`:
  - XChaCha20-Poly1305 со случайным 192-битным nonce, подключ на каждое назначение через HKDF-SHA256;
  - конверт `mt1.<назначение>.<key id>.<base64url>`; key id выведен из самого ключа;
  - additional data: назначение, key id и привязка вызывающего (например, пользователь и задача);
  - связка из текущего и предыдущего ключей из env.
- **Тесты:** шифрование и расшифровка; подмена байта; чужая привязка; чужое назначение; неизвестный key id; ротация (старое читается, новое пишется новым ключом); неверная длина ключа при старте.
- **Разделы:** SPEC 9.3; PRODUCT 4.4, 6.

### T28a.1. Телеметрия: провайдеры и экспорт

- **Цель:** трассы и метрики сверх логов — пока код мал и инструментировать его дёшево. Метрики как агрегаты по логам (О-16) никуда не деваются: это второй слой, а не замена. Эта половина строит и отправляет; инструментирует T28a.2.
- **Сделать:**
  - `internal/telemetry`: провайдеры трасс и метрик, ресурс (`service.name`, версия из `internal/version`, определение Cloud Run — ревизия, регион, экземпляр — через `contrib/detectors/gcp`), обработчик ошибок SDK через zap, `ForceFlush` и `Shutdown`; подключение в `app.NewContainer` рядом с контентом и связкой ключей;
  - экспорт **стандартным OTLP** на `https://telemetry.googleapis.com` с учётными данными ADC — `otlptracehttp` и `otlpmetrichttp`; проект в атрибуте ресурса `gcp.project_id` и в заголовке `X-Goog-User-Project`;
  - сэмплирование `ParentBased(TraceIDRatioBased)`: Cloud Run уже трассирует входящие запросы сам и ставит `traceparent`, наши спаны цепляются к этим трассам;
  - **сброс до ответа**: `ForceFlush` с коротким сроком, метрики — не чаще раза в интервал, плюс `Shutdown` при закрытии контейнера;
  - экспорт выключен по умолчанию вне развёртывания — `just run` и тесты не требуют учётных данных Google; провайдер строится всегда, инструментирующий код о переключателе не знает. Ни отсутствие учётных данных, ни отсутствие проекта не мешают сервису стартовать;
  - четыре переменные в `internal/config`;
  - `infra/terraform`: включить `telemetry.googleapis.com`, выдать рантайм-аккаунту `roles/telemetry.writer` и `roles/serviceusage.serviceUsageConsumer`, передать `MATHTRAIL_GCP_PROJECT_ID`; `infra/bootstrap.sh` — `roles/resourcemanager.projectIamAdmin` той личности, которой применяется конфигурация;
  - SPEC 12.5 — подраздел про трассы и метрики, SPEC 11.2 — четыре строки в таблицу; `docs/decisions.md` — решение со всеми числами ниже.
- **Тесты:** экспортёр против `httptest`, говорящего OTLP; сбой экспорта (503, таймаут, нет учётных данных, нет проекта) не меняет ответ и не роняет процесс; метрики не уезжают дважды за интервал; выключенная телеметрия не делает ни одного исходящего запроса; metadata-сервер не опрашивается, когда экспорта нет.
- **Как проверить:** после деплоя в Cloud Trace наш спан висит под автоспаном Cloud Run.
- **Риски и ограничения, снятые до начала:**
  - фирменные экспортёры Google для Go (`exporter/trace` v1.38.0, `exporter/metric` v0.62.0) объявлены устаревшими и будут заархивированы после 1 января 2027 — брать их нельзя, они сами отправляют на стандартный OTLP;
  - сайдкар-коллектор отпадает по деньгам: 0.25–0.5 vCPU и 256–512 МБ на экземпляр против 180 000 vCPU-секунд бесплатного лимита Cloud Run;
  - `cpu_idle = true` в `service.tf` означает, что после ответа процессор отбирают и фоновая отправка спанов не успевает — отсюда сброс до ответа;
  - бесплатные лимиты, в которые всё это должно уложиться: системные метрики Cloud Run и его автотрассы не тарифицируются вовсе; Cloud Logging — 50 GiB/мес; Cloud Trace — 2.5 млн спанов/мес; свои метрики — 150 MiB/мес. Метка метрики с идентификатором пользователя или задачи выносит за последний предел, поэтому метки — только закрытые словари;
  - с 1 сентября 2026 Cloud Monitoring берёт $0.35 в месяц за каждую метрику в политике оповещения. Бюджетное оповещение T20 — это Billing и оно бесплатно; решение по оповещениям на метриках принять до T64.
- **Разделы:** SPEC 11.2, 12.5; PRODUCT 6 (О-16, О-21).

### T28a.3. Телеметрия в облаке: право, мерж и первая трасса

### T39b. Класс задаёт только старт

- **Цель:** класс — только стартовая точка. С него начинается короткая пробная серия, а дальше ребёнок идёт по одной лестнице задач 1–6 классов: вниз, если не справляется, вверх, если справляется. Больше класс ни на что не влияет.
- **Почему:** сейчас класс решает всё — набор тем (`TopicsAt(grade)`), смысл сложности 1–5 (она своя у каждого уровня, SPEC 1.1), пределы читаемости и эталоны для модели. Отсюда три дефекта:
  - ребёнку, которому задачи его класса не по силам, некуда спуститься: ниже сложности 1 своего уровня задач нет;
  - при смене класса рейтинг переносится как есть. На следующем уровне θ завышен, ребёнок получает задачи, которые в основном проваливает, и выправляется это только чередой провалов — шаг K к тому времени уже узкий;
  - отметки «тема освоена» с младшего уровня переезжают на старший, где тема труднее, и тема выпадает из ротации, ни разу не встретившись на новом уровне.
- **Решено автором (2026-09-25):**
  1. **пробная серия:** первые 5 задач — по разным темам. После каждого ответа уровень заново оценивается по всем пробным ответам сразу, поэтому ошибающийся ребёнок уже со 2–3-й задачи получает заметно более простые. После серии — обычный режим;
  2. **класс меняется когда угодно и остаётся подписью:** рейтинг, стартовую точку и пробную серию смена не трогает;
  3. **пределы читаемости — по уровню задачи**, а не по классу ребёнка;
  4. **одна шкала рейтинга для всех:** число — место на общей лестнице. Звания той же ширины (один коридор, 166 очков) покрывают всю лестницу, поэтому их около одиннадцати, а не пять. Во время пробной серии рейтинг не показывается.
- **Устройство** (предложение; числа окончательно фиксирует T39b.1):
  - **общая лестница:** задача по-прежнему — уровень (`1-2`, `3-4`, `5-6`) и сложность 1–5 внутри него, но все пятнадцать пар стоят на одной шкале: β = сдвиг уровня + (сложность − 3).
    - Сдвиг `1-2` — 0, поэтому числа прототипа, разобранные примеры SPEC 2.6–2.7 и `testdata/golden/ratings.json` остаются верными.
    - Каждый следующий уровень сдвинут на 2,5: две верхние сложности младшего уровня перекрываются с двумя нижними старшего, а точки не совпадают.
    - 2,5 — догадка без данных. Она записывается решением и пересматривается на живых прогонах;
  - **старт:** θ₀ = сдвиг уровня класса — 0, 2,5 или 5. Первая задача новичка — сложность 2 уровня его класса, как сейчас. θ₀ пишется в профиль при создании, и смена класса его не двигает;
  - **пробная серия:** пока ответов меньше пяти:
    - тема каждый раз новая — правило и так ставит вперёд темы, которых ещё не было;
    - повтора после ошибки нет;
    - после каждого ответа θ = самая вероятная оценка по θ₀ и всем пробным ответам. Априорная оценка — нормальная с центром θ₀ и разбросом в один сдвиг уровня; разброс проверяется симуляцией;
    - δ тем в серии не двигаются, а счётчики и ловушки пишутся как обычно;
  - **темы по силам:**
    - тема открыта, когда её самая лёгкая точка (нижний уровень темы, сложность 1) решается с шансом не ниже 0,70 при уровне ребёнка в теме θ + δ;
    - коридор выбирает из всех точек темы ту, чей шанс ближе к 0,775;
    - модель по-прежнему может выбрать сама, с причиной (SPEC 3.4), тему, уровень и сложность — из тех, что есть в каталоге;
  - **освоение помнит уровень:** тема, освоенная на одном уровне, возвращается в ротацию, когда рекомендуемая точка по ней переходит на уровень выше;
  - **читаемость:** предел длины предложения — по уровню задачи, как сейчас; Flesch–Kincaid — младший класс уровня + 3 (4, 6, 8). Эталоны `5-6` уже держатся за 5-й класс (SPEC 1.6);
  - **класс в пакете для модели** остаётся, но только как возраст ребёнка — для слов и сюжета. На уровень и пределы он не влияет. Если на проверке T39b.1 я решу иначе — убрать;
  - **файл профиля:**
    - новые поля: в `ratings` — стартовая точка; в ТЗ, текущей задаче и ответах окна — `grade_level`; у темы — уровень, на котором она освоена;
    - версия схемы остаётся 1: файлов v1 ещё никто не писал — инструменты профиля появятся в T43, хранилище в Drive — в T50;
    - фикстуры `testdata/profiles` переводятся на новую шкалу: θ профилей 3–4 класса + 2,5, уровень в каждом ответе. Золотые файлы не трогаются.
- **Разбита на пять частей** (правило 12): решение и документы, затем рейтинг, профиль, правило, пакет с проверками — по направлению зависимостей.
