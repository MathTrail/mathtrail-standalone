# Локальный прогон в Claude Code (T46)

**Статус: закрыто.** 2026-09-27. Четыре сценария из `testdata/live/scenarios.json` пройдены целиком. Модель написала 15 задач, 13 из них проверки приняли с первой попытки, две — со второй. Все 15 при ручной проверке решаются однозначно; в одной есть двусмысленная формулировка, которую проверки не видят. Прогон нашёл у хоста два свойства, из-за которых урок не шёл или шёл не по правилам. Оба исправлены в рамках задачи: R102 и R103.

## Что это

Первый урок, который ведёт настоящая модель по новым инструкциям, в текстовом режиме, без карточек:

- **Сервер.** Собран из рабочего дерева, запущен в devcontainer с dev-входом. Профиль в памяти, у каждого сценария свежий. Лог в JSON — источник всех чисел ниже.
- **Чат.** Claude Code 2.1.280 в режиме `-p`, модель Sonnet (`claude-sonnet-5`), подключён по HTTP через `.mcp.json`. Прогоны шли под псевдонимом модели `sonnet`; теперь `just play` называет её точным id, чтобы повторный прогон попал на ту же модель. Своих инструментов у чата нет: ни файлов, ни shell, ни веба. Папка прогона лежит вне репозитория, так что модель не видит ни кода, ни эталонов.
- **Роли.** Родителя и ребёнка играл исполнитель задачи (Claude), по шагам сценария. Правильную букву для ответа брал из того, что модель сдала в `submit_task`.

**Стоимость.** $0 деньгами; расходовались лимиты подписки автора. Всего 29 вызовов `claude -p` и около 11 минут работы модели. По собственному счёту Claude Code это около $9 в пересчёте на API, но по подписке это не списывается.

## Как повторить

В двух терминалах devcontainer:

```bash
just play-server   # сервер урока: dev-вход, новый ребёнок, лог в ~/mathtrail-play/server-<время старта>.jsonl
just play          # чат в Claude Code: модель — репетитор; сообщения пишете вы
```

Для прогона без участия человека, сообщение за сообщением:

```bash
printf '%s' 'Давай задачу!' | just play -p --output-format stream-json --verbose --session-id "$(cat /proc/sys/kernel/random/uuid)"
printf '%s' 'B' | just play -p --output-format stream-json --verbose --resume <та же сессия>
```

Журнал урока строится из лога сервера, последнего по времени:

```bash
jq -c 'select(.message|test("task_(requested|accepted|skipped)|task_submitted|answer_recorded"))' "$(ls -t ~/mathtrail-play/server-*.jsonl | head -1)"
```

У каждого сценария свой сервер и свой лог: профиль живёт в памяти процесса, так что перезапуск и есть «новый ребёнок». Сервер останавливается Ctrl+C в его терминале. Из скрипта — по pid процесса, который слушает порт 8080 (`ss -ltnp`). Имя процесса для этого не годится: у `go run` путь к бинарнику меняется, свежая сборка запускается из временного каталога, повторная — из кэша сборки. А `pkill -f` по строке команды задевает и сам скрипт.

## Что показал хост

| Что | Claude Code 2.1.280 |
|---|---|
| Протокол | 2026-07-28, stateless; в логе клиент `claude` |
| Список инструментов | шесть инструментов урока; `read_progress` (`visibility: ["app"]`) модели не показан |
| Инструкции сервера | попадают в контекст модели, в отдельном напоминании «MCP Server Instructions», но **только первые 2048 символов** (находка 2) |
| Описания инструментов | тоже **обрезаются до 2048 символов** (находка 2) |
| Результат инструмента | если в результате есть `structuredContent`, модель получает его, сериализованным, и **не получает текст** рядом с ним (находка 1) |
| Карточки | не рисуются: урок идёт текстом, модель читает вслух вопрос и варианты |

Всё это подтверждено дважды. Во-первых, стенограммами сессий: Claude Code кладёт их в `~/.claude/projects/-home-vscode-mathtrail-play/`, инструкции там лежат вложением `mcp_instructions_delta`. Во-вторых, кодом самого CLI. Предел задаёт функция, которая читает `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`, по умолчанию 2048. Длина считается как в JavaScript, в единицах UTF-16. Обрезанный текст кончается на «… [truncated]». Один и тот же код режет «Server instructions» и `Tool "…" description`.

## Находка 1: пакет `next_task` не доходил до модели (R102)

Первая попытка сценария first-lesson. Профиль создан, и дальше модель 15 раз за 28 секунд вызвала `next_task` и не написала ни одной задачи. Она получала `{"request_id": …, "screen": "waiting"}` и решила, что задачу готовит сервис. Пакет с заданием на задачу ехал только в тексте, а текст Claude Code ей не показал.

**Исправление (решение автора).** `next_task` отвечает только словами, payload нет: абзац для модели и сразу за ним пакет. Payload остался только у отказа: его `status` помечает отказ для модели и для лога. SPEC 7.1, 7.3 и замечание 45; `docs/architecture/03-flows.md`.

После исправления урок пошёл, и все последующие прогоны открывали запрос с первого вызова.

Ответ на повторный `next_task` теперь тоже только в словах. После прогонов, по ревью, в нём поменялся порядок: сначала «если задача написана — сдай её», и только потом «если нет, например ход оборвался, пиши её по пакету». Это возвращает то, что обещает 03-flows: вторая просьба не должна стать второй генерацией. И модель не прочтёт «задача уже пишется» как «её пишет сервис». Живьём повторный вызов в прогонах не встретился.

## Находка 2: инструкции и описания обрезаются до 2048 символов (R103)

В first-lesson инструкции были длиной 5298 символов. Модель видела из них «The child», «The profile» и начало первого шага «A task»; всё остальное отрезалось, в том числе «держи ответ при себе», разделы про ответ и про следующую задачу. В first-grader, после первых правок, инструкции выросли до 5878 символов, и до модели дошли только «The child» и «The profile». То же самое модель не получала и из результатов: слова `submit_answer` («начни с ловушки», «разбери решение») Claude Code не показывает (находка 1). Отсюда поведение первых двух сценариев:

- после каждого разбора модель сама просила следующую задачу («Идём дальше.», «Готовим следующее!»), хотя ребёнок об этом не просил;
- первый неверный ответ модель начала разбирать с правильного ответа и решения, а ловушку назвала последней; второй начала с ловушки;
- на «Не знаю» модель сразу назвала правильный ответ, а решение дала после него.

Описание `next_task` было длиной 2780 символов, и хвост списка тем (темы 5–6 классов) до модели не доходил.

**Исправление.** Инструкции теперь открываются разделом «Always». В нём правила, которые должны соблюдаться в любом хосте:

- только псевдоним, и никогда в тексте задачи;
- язык чата и слова, по которым не видно пол ребёнка;
- ответ, решение и объяснения скрыты до ответа ребёнка, подсказка — только по просьбе;
- сначала ответ записывается, потом объяснение; «Не знаю» — это `?`;
- неверный ответ разбирается с текста ловушки, правильный вариант звучит в конце решения;
- следующая задача — только когда её просит ребёнок;
- перед словами о текущей задаче — `last_answer` из только что вызванного инструмента.

В прогонах после правки инструкции до конца этого раздела занимали 1818 символов, и раздел дошёл до модели целиком: обрез пришёлся на начало «The profile». После прогонов ревью поправило в «Always» три фразы, и раздел вырос до 1914 символов. Живьём эти три фразы не проверялись:

- записывать ответ самой модели нужно, только когда ребёнок отвечает в чате, — ответ на карточке записывается без неё;
- перед словами о задаче модель вызывает инструмент и читает в результате «последний записанный ответ», а не по памяти; и не поле `last_answer`: у `next_task` этого поля нет, там фраза;
- «`next_task` только по просьбе ребёнка» относится к тому, что идёт после разбора ответа. Если три попытки не удались, модель по-прежнему сама просит новую задачу: ту, прежнюю, ребёнок уже просил. Разделы ниже объясняют, как проходит урок, и хост, который режет, может их потерять. Список тем в `next_task` теперь даёт только id и уровни, как и записано в SPEC 7.2, и описание стало длиной 1303 символа. Два теста держат бюджет:

- `TestWhatAlwaysHoldsIsKeptByAHostThatCuts`: «Always» идёт первым разделом и укладывается в 2048 символов;
- проверка в `TestTheToolsOfTheLessonAreListedAsTheyAreMeant`: каждое описание инструмента не длиннее 2048.

Оба краснеют, если вернуть старый текст.

**Что изменилось.** Сценарии own-choice и english шли на новых инструкциях (версия `088936400bdd`). После каждого разбора модель предлагала следующую задачу и ждала: «Хочешь следующее?», «Want another task?». Единственный неверный ответ этих прогонов она начала с ловушки и закончила правильным вариантом. «I don't know» разобрала по шагам и назвала правильный вариант в конце.

## Замечания

1. **Двойные формы вместо нейтральных.** После R103 модель не присваивала ребёнку пол, но писала «готова(-ов)», «выбрал(а)». Это видно, но неуклюже. Правило можно дополнить: «и не форма с двумя окончаниями». Не сделано: без ещё одного прогона правку нечем проверить. **Для:** T62.
2. **О записанном ответе — по памяти.** В own-choice на повторную букву модель сказала «ответ уже записан», не вызвав инструмент. Это нарушает правило «Always» — перед словами о задаче читать `last_answer`. Здесь безвредно, но в хосте с карточкой ответ мог записать и виджет. **Для:** T62.
3. **«Потруднее» только по метке.** Задача, которую модель выбрала со сложностью 4, — всё то же рукопожатие четырёх, что правило в других прогонах давало на сложности 3. Проверки не могут подтвердить, что задача на заявленной сложности. **Для:** T62–T64 и калибровки уровней (SPEC, замечание 34).
4. **Правка под читаемость может убить смысл.** В english 2 модель сократила вопрос и выбросила «different», и задача стала двусмысленной. В руководство по написанию задач просится строка «сокращая фразу, оставь каждое слово, от которого зависит ответ». То же руководство стоило бы дополнить про подсказки (first-lesson 3 и 4): подсказка называет первый шаг, а не действие, которое сразу даёт ответ. Не сделано: это правка `task_writing.md` без прогона, который её проверит. **Для:** T58 или следующего живого прогона.
5. **Одни и те же сюжеты у разных детей.** Рукопожатие четырёх встретилось в трёх прогонах из четырёх; рыцари и лжецы в схеме «один говорит очевидный факт, другой его обвиняет» — в трёх. Проверка на почти-дубликаты работает внутри профиля одного ребёнка, так что для урока это не дефект. Но похоже, что модель держится за образцы из пакета. **Для:** T64a, где разнообразие мерят.
6. **Умножение в задаче уровня 1-2.** В english 2 решение умножает 2 × 3 × 2. У ребёнка 4-го класса запретов нет, а уровень задачи 1-2: перебрать 12 вариантов можно и без умножения, но это тяжело. Проверки смотрят только исключённые навыки. Наблюдение, не дефект.
7. **Что сделают другие хосты — неизвестно.** Режет ли инструкции и описания Claude в вебе и ChatGPT, и если режет, то где, нигде не написано (SPEC, замечание 46). **Для:** T62, T63.
8. **Список инструментов в `just play` задан руками.** `PLAY_TOOLS` повторяет имена шести инструментов урока. Инструмент, добавленный на сервер, модель в живом прогоне не получит, пока его не впишут. В Claude Code есть правило на весь сервер (`mcp__mathtrail`), но проверить его можно только живым прогоном, поэтому оно не поставлено.
9. **Язык этого отчёта.** CLAUDE.md и правило 11 RUN.md требуют английский для всего в `docs/`, а предыдущие отчёты в `docs/live/` написаны по-русски. Этот отчёт следует соседям. Нужно решение автора: переводить отчёты или записать `docs/live/` в исключения.

## Метод и его пределы

- **Один ход — один `claude -p`.** Следующий ход продолжает ту же сессию через `--resume`. В выводе `-p` остаётся только последний текстовый блок, поэтому промежуточные реплики модели читались из `stream-json`.
- **Пропуск лишних шагов.** В first-lesson и first-grader модель сама переходила к следующей задаче. Поэтому шаг сценария «Давай следующую» пропускался, если задача уже была на экране; из-за этого в first-lesson 8 ходов вместо 11. В own-choice и english каждый шаг сценария отправлен как есть.
- **Выборка мала.** Одна модель, по одному прогону на сценарий: это наблюдения, а не частоты. «Держится» значит «держалось в этих прогонах».
- **Ученика играет модель.** Ответы шли по сценарию, так что проверяется урок, а не ребёнок: как модель понимает детские формулировки, этот прогон не показывает.
