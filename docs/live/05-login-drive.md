## Находки

1. **Claude не отправляет сообщение карточки сам: он просит подтверждения под красным предупреждением.** 2026-09-30, 01:20 UTC, блок Б. Нажатие «Create a profile» на карточке первого входа отправило хосту `ui/message`. Карточка получила успешный ответ и написала «Sent to the chat». Claude показал «Use caution before running this prompt. Malicious content could trick Claude into attempting harmful actions or sharing your data», и ход модели не начался: после `get_profile` в логе нет ни одного вызова. Так поступать хосту разрешает спецификация MCP Apps: для `ui/message` «Host MAY request user consent» (версия 2026-01-26). Документация Claude не даёт способа снять это подтверждение для своего коннектора. Похожее подтверждение для внешних ссылок снимается только у коннекторов из каталога, про сообщения там не сказано ничего. Дизайн-гайдлайны Claude относят к полю ввода чата всё, что требует ответа модели (свободный ввод, уточнения, просьбы переделать или дать новое), и советуют не делать в приложении поле ввода, повторяющее чат. На карточках MathTrail через `ui/message` идут четыре действия: «Create a profile», «Edit profile», «Другая задача» с «Попросить ещё раз» на ожидании и вопрос из поля. Оценка автора: почти блокер, с таким предупреждением кнопками пользоваться не будут. «Изменить профиль» в 01:26 повела себя так же. Решение автора: кнопки в карточке нужны («я хочу нажимать на кнопки»), переделка — отдельной задачей. Направление: действия, которые сервис выполняет сам, делаются прямым вызовом инструмента из карточки, без сообщения в чат, как уже записывается ответ; создание и правка профиля — формой в карточке. Для «Другой задачи», которой нужен ход модели, решение выбирается после блока Г, по тому, как ChatGPT обходится с той же кнопкой. Прогон продолжается: то, что должно дойти до модели, автор пишет в чат сам.
2. **Приложение Google Auth Platform было в статусе Testing.** Вход аккаунта автора упирался в `403 access_denied` («has not completed the Google verification process»): в Testing пускают только вписанных тестировщиков. Руководство (`docs/self-hosting.md`, раздел 3) требует In production, при настройке это было пропущено. Для публикации Google потребовал Branding: главную страницу, политику, условия и почту разработчика. Логотип не загружен: с ним приложение ушло бы на проверку Google.
3. **Блок «Ваши данные» на карточке профиля читается странно** (слова автора: «странный текст после Отправлено в чат»). Заголовки — глаголы («Забрать», «Удалить», «Отключить доступ», «Убрать приложение»), похожие на кнопки, которые ничего не делают, и блок стоит сразу под «Отправлено в чат», как продолжение ответа.
4. **Claude отправляет части задачи строками, и `submit_task` отклоняет задачу.** 2026-09-30, 01:30:15 UTC, блок В: попытка 1 — `bad_structure`, решатель не запускался (`solver_steps` 0). В схеме `submit_task` поля `brief`, `task` и `self_check` объявлены без типа — так решено в R100, чтобы ошибку структуры описывали наши слова, а не библиотека (remark 36). Клиент Claude передал их строками с JSON внутри, а проверка структуры ждёт объекты. Модель сама описала причину и не стала тратить вторую попытку: повтор ушёл бы в том же виде. Урок в Claude на этом остановлен; карточка ожидания отработала как задумано — шаги, разминка, через 120 секунд слова, что задачу не готовят. Автор решил чинить сразу: часть задачи, пришедшая строкой с JSON, читается как этот JSON, а описания полей говорят, что каждое — JSON-объект (R137). Схема с типом object отвергнута: строку тогда отклоняла бы библиотека, цитируя всю задачу с ответом (remark 36).
5. **Экспорт метрик отклоняется.** 01:30:13 UTC: `telemetry_flush_failed`, Google Cloud Monitoring ответил `FAILED_PRECONDITION` — точки метрики `http_request_duration` пишутся чаще допустимого периода (между двумя записями 4,8 секунды). Урок это не задевает; сколько метрик теряется, покажет журнал за весь прогон.

## Замечания

1. **Язык отчётов в `docs/live/`.** CLAUDE.md требует английский для всего в `docs/`, а отчёты живых прогонов 01–04 написаны по-русски. Этот отчёт следует им; какое из двух правил верное, решает автор.
2. **Два сброса соединения.** Во время проверок без браузера два запроса из devcontainer к `/oauth/authorize` оборвались на TLS-рукопожатии (`Connection reset by peer`), до сервиса не дойдя; `/health` в те же минуты отвечал, а повторы прошли. В логах сервиса этих запросов нет. Похоже на сеть по пути, а не на сервис; при живом прогоне стоит заметить, повторится ли.

## Метод и его пределы

Проверки без браузера повторяются этими командами из devcontainer; тестовые клиенты DCR ничего не хранят на сервере.

```bash
base=https://mcp.mathtrail.app
enc() { jq -rn --arg v "$1" '$v|@uri'; }
redirect=https://example.org/t53-2/consent/check/cb
client=$(curl -sS -H 'Content-Type: application/json' \
  -d "{\"redirect_uris\":[\"$redirect\"],\"client_name\":\"T53.2 check\"}" $base/oauth/register | jq -r .client_id)
challenge=$(head -c 32 /dev/urandom | base64 | tr '+/' '-_' | tr -d '=\n' |
  openssl dgst -sha256 -binary | base64 | tr '+/' '-_' | tr -d '=')
authorize="$base/oauth/authorize?response_type=code&client_id=$(enc "$client")&redirect_uri=$(enc "$redirect")&code_challenge=$challenge&code_challenge_method=S256&state=t53"

# Экран согласия и кука входа: адрес возврата с путём, Set-Cookie __Host-mt_csrf.
curl -sS -c jar -D - -o consent.html "$authorize&scope=mcp" | grep -i '^set-cookie'
grep -o '<bdi>[^<]*</bdi>' consent.html

# Кука одобрения: форма с решением «Разрешить», ответ 303 на Google без перехода.
request=$(grep -o 'name="request" value="[^"]*"' consent.html | sed -E 's/.*value="([^"]*)"/\1/')
curl -sS -b jar -D - -o /dev/null --data-urlencode "request=$request" --data-urlencode decision=allow \
  $base/oauth/consent | grep -iE '^(HTTP|set-cookie)'

# Ошибка неодобренного клиента — страницей: ждём 400 и пустой Location.
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' "$authorize&scope=$(enc 'mcp admin')"

# Клиент на компьютере родителя слышит ту же ошибку сам: ждём 302 на его адрес с error=invalid_scope.
loopback=http://127.0.0.1:33418/cb
home_client=$(curl -sS -H 'Content-Type: application/json' \
  -d "{\"redirect_uris\":[\"$loopback\"],\"client_name\":\"T53.2 loopback\"}" $base/oauth/register | jq -r .client_id)
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' \
  "$base/oauth/authorize?response_type=code&client_id=$(enc "$home_client")&redirect_uri=$(enc "$loopback")&code_challenge=$challenge&code_challenge_method=S256&state=t53&scope=$(enc 'mcp admin')"

# Темп по адресу, дописанному платформой: после всплеска — 429, как ни меняй две строки X-Forwarded-For.
# Шесть запросов выше потратили весь всплеск; пауза даёт ему восполниться.
sleep 20
for i in $(seq 1 30); do
  curl -sS -o /dev/null -w '%{http_code} ' -H "X-Forwarded-For: 198.51.100.$i" -H "X-Forwarded-For: 203.0.113.$i" \
    $base/.well-known/oauth-authorization-server
done; echo
```

Блок прогнан как записан 2026-09-29 в 15:44–15:45 UTC и дал ровно то, что в таблице выше, с теми же строками лога.

Темп по адресу — один на все пути входа: 20 запросов в минуту, всплеск 6. Поток из 30 запросов исчерпывает его для адреса, с которого идёт, примерно на полминуты — на сам поток и 18 секунд, пока всплеск восполнится. Поэтому его не запускают, пока с этого адреса кто-то входит.

Чего эти проверки не показывают:

- что браузер принимает куки: `curl` видит только то, что сервер отправил, а принятые браузером куки смотрит блок А;
- вход в Google и Drive: запрос останавливается на `303` к Google, остальное проходит чек-лист;
- темп на нескольких экземплярах: темп считается в памяти каждого экземпляра, а поток, судя по шести пропущенным запросам, пришёлся на один.

Логи читаются так, за окно времени в UTC:

```bash
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="mathtrail"
  AND timestamp>="<от>" AND timestamp<="<до>" AND NOT logName:"run.googleapis.com%2Frequests"' \
  --project mathtrail-prod --order asc --format=json
```
