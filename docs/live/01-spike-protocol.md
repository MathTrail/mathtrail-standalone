## Что это

Одноразовый Go MCP-сервер на `github.com/modelcontextprotocol/go-sdk` и виджет на TypeScript + Vite (`@modelcontextprotocol/ext-apps`, без Preact), поднятые за туннелем `cloudflared` без авторизации. Проверяем: подключаются ли Claude и ChatGPT к серверу MCP 2026-07-28 без сессий, и как у них работают виджеты MCP Apps.

Три тестовых инструмента:

| Инструмент | Что проверяет |
|---|---|
| `echo` | обычный инструмент: `content` + `structuredContent`, без виджета |
| `widget_poke` | `_meta.ui.visibility: ["app"]` — вызывается только из виджета, должен быть скрыт от модели в `tools/list` |
| `show_widget` | `_meta.ui.resourceUri` — по его результату хост должен отрисовать виджет |

Виджет показывает контекст хоста (`locale`, `platform`, `theme`, `containerDimensions`, `safeAreaInsets`, `displayMode`), текстовый рисунок 30 символов шириной, и три кнопки: вызвать `widget_poke` (`callServerTool`), отправить `ui/message` (`sendMessage`), обновить контекст модели (`ui/update-model-context`, `updateModelContext`).

## Версия go-sdk

PRODUCT-V1 называет v1.7.0; на 2026-09-16 актуальна **v1.8.0** (14.09.2026) — патч-релиз без изменений протокола («no new protocol revision: the supported set is unchanged, and `2026-07-28` remains the newest version the SDK negotiates»), только устойчивость транспорта (лимиты на размер SSE-события, тела запроса, глубину JSON), `ServerOptions.SupportedProtocolVersions` для режима «только 2026-07-28», и явный JSON-RPC-код `-32022` вместо голого 400 при обращении statful-сервера версией 2026-07-28. Для спайка закреплена **v1.8.0** — она строго новее и полностью совместима. *Решение записать в `docs/decisions.md` в T05.*

Пакет `@modelcontextprotocol/ext-apps` взят версией **2.0.0** (последняя на npm) — актуальнее спецификации apps.mdx 2026-01-26 в части `ui/message`/`ui/update-model-context`: в библиотеке `content` — всегда массив блоков (`ContentBlock[]`), а не одиночный объект, как в тексте спецификации. Код ориентирован на библиотеку (реальный рантайм), а не на текст спеки.

## Подтверждено без хостов (curl)

Проверено `curl`-запросами напрямую к локальному серверу (см. историю разработки, не автоматизированный тест — спайк одноразовый):

- `server/discover` и `tools/list` отвечают по протоколу 2026-07-28 в stateless-режиме (`StreamableHTTPOptions.Stateless = true`);
- протокол 2026-07-28 требует на каждый запрос `_meta` с `io.modelcontextprotocol/{protocolVersion,clientInfo,clientCapabilities}`, а также HTTP-заголовки `Mcp-Method` и (для `tools/call`/`resources/read`/`prompts/get`) `Mcp-Name` — сервер их проверяет и отклоняет запрос без них (SEP-2243, HTTP standardization);
- `_meta.ui.resourceUri` и `_meta.ui.visibility` корректно отдаются в `tools/list` — но сервер **не фильтрует** `widget_poke` из списка по видимости: по спецификации это обязанность хоста («Host MUST NOT include tools in the agent's tool list when their visibility does not include "model"»). Это ровно то, что проверяет пункт матрицы «вызов из виджета»/скрытие app-only инструмента;
- `resources/read` отдаёт собранный виджет (`text/html;profile=mcp-app`, один файл, без внешних доменов);
- `tools/call show_widget` отдаёт и `content`, и `structuredContent` с текстовым рисунком;
- лог пишет `protocol_version` и `client_name`/`client_version` на каждый запрос (требование T03).

## Известный риск: `*.trycloudflare.com` — только IPv6 (не подтвердился на практике)

`cloudflared tunnel --url` выдаёт поддомен `trycloudflare.com`, который в DNS отвечает **только AAAA-записью** (проверено `getent ahosts`, в отличие от `www.cloudflare.com`, у которого есть и A, и AAAA). Из devcontainer (сеть Docker без исходящего IPv6) он поэтому недоступен по `curl`.

**На практике с телефона это не проблема**: при живом прогоне (Claude, попытка добавить коннектор с телефона) UI показал ошибку `530` на шаге «Connecting to the server», но прямое открытие `https://<поддомен>.trycloudflare.com/healthz` в браузере с того же телефона и той же сети сразу отдало `ok`. Значит IPv6 для конечного устройства не проблема; 530 (код именно от Cloudflare edge, не от нашего сервера) больше похож на разовую гонку — проверка коннектора Claude попала в момент, когда `cloudflared` ещё не успел до конца зарегистрироваться на edge сразу после старта. **Лечится простым повтором через 10–20 секунд после того, как `just spike-a`/`spike-a-strict` напечатал URL** — не переподключением или сменой способа туннелирования.

Если при повторной попытке 530 повторяется — тогда стоит проверить `curl -6`/`curl -4` с той же сети, как описано раньше, но пока для этого нет оснований.

## Инструкция: как подключить

1. В devcontainer: `just spike-a` (первый прогон соберёт виджет и займёт около 20 секунд на `npm install`). Оставить команду работать — она держит сервер и туннель, печатает URL:
   ```
   MCP endpoint:   https://<случайное-имя>.trycloudflare.com/mcp
   Health check:   https://<случайное-имя>.trycloudflare.com/healthz
   ```
   Проверить со своей машины (не из devcontainer): `curl https://<случайное-имя>.trycloudflare.com/healthz` → должно вернуть `ok`. Если добавляете коннектор сразу после старта и Claude/ChatGPT отвечают ошибкой соединения (например, `530` от Cloudflare) — подождите 10–20 секунд после появления URL и попробуйте снова: туннелю нужно время зарегистрироваться на edge Cloudflare (см. «Известный риск» ниже).
2. Для режима «только 2026-07-28» (после первого прогона в обычном режиме): `just spike-a-strict` — сервер будет отвечать `-32022 CodeUnsupportedProtocolVersion` на согласование более старых версий. (Не `just spike-a strict=1` — `just` понимает только позиционные аргументы, `strict=1` целиком ушёл бы в порт; это отдельный рецепт ровно поэтому.) **Уже проверено на Claude: в этом режиме шаг «Connect» при добавлении коннектора падает с `status 400`** — подробности и рекомендация в разделе «Находка» ниже; для добавления коннектора используйте обычный `just spike-a`.

### Claude

- **Веб** (claude.ai): Настройки → Коннекторы → Добавить свой коннектор → вставить `https://<поддомен>.trycloudflare.com/mcp` → добавить без авторизации.
- **Телефон** (мобильное приложение Claude): проверить, виден ли там вообще пункт добавления своего коннектора (не только каталог) — согласно PRODUCT-V1 9.3, это не подтверждено документацией и указано как «проверить руками». **Подтверждено: виден**, экран «Add custom connector» открывается.
- **Шаг «Checking the server...» почти наверняка покажет ошибку** (в живых прогонах — 530 и 400 в разные разы) на пункте «Connecting to the server» с текстом «Couldn't determine how this server signs in». Это ожидаемо: у T03-спайка нет OAuth вообще (он появится в T04), автоопределение способа входа не может ничего найти. **Нажать «Continue anyway»** — диалог сам предлагает эту кнопку ровно для такого случая, дальше коннектор добавляется и работает без авторизации.
- В любом окружении: попросить модель вызвать `echo`, затем `show_widget`, затем поговорить о `widget_poke` (не должен быть в списке доступных модели инструментов).

### ChatGPT

- **Веб, режим разработчика**: включить Developer mode (Settings → Apps & Connectors → Advanced → Developer mode, требует Plus/Pro), добавить коннектор по тому же URL.
- **Телефон**: режим разработчика официально только в вебе (PRODUCT-V1 9.3) — тем не менее открыть мобильный веб-браузер на chatgpt.com и проверить, доступен ли там тот же коннектор, привязанный к аккаунту.

**Не проверено — решение автора.** Developer mode в ChatGPT требует платной подписки (Plus/Pro, PRODUCT-V1 9.3); автор решил не оформлять её ради этой проверки. Вся строка ChatGPT в матрице ниже остаётся `?`. Значит для главного риска фазы 0 (**О-20**, PRODUCT-V1 9.4) подтверждён только один из двух целевых хостов — Claude; по ChatGPT решения из блога Anthropic/справки OpenAI (раздел 9.3 PRODUCT-V1) остаются единственным источником, эмпирики нет. Это не блокирует переход к фазе 1 (SPEC не зависит от того, какой конкретно хост проверен — протокол один и тот же), но стоит перепроверить перед приёмкой в ChatGPT (T63) и до подачи в каталог (T61–64), когда/если появится платная подписка.

### На каждой поверхности проверить и отметить в матрице ниже

1. Подключение прошло, какая версия протокола видна в логе сервера (`protocol_version` в JSON-логе).
2. Виджет `show_widget` отрисовался (не текстовый фоллбэк).
3. В виджете видны `locale`, `platform`, `theme`, `containerDimensions`, `safeAreaInsets`, `displayMode` — реалистичные значения, не `undefined`.
4. Кнопка «Call widget-only tool» работает, ответ появляется в логе виджета.
5. Кнопка «Send ui/message» — сообщение появляется в чате.
6. Видит ли модель `structuredContent` результата `show_widget` (например, спросить модель, что было в `drawing`).
7. Видны ли пользователю (в интерфейсе хоста) аргументы вызовов инструментов — открыть журнал/детали вызова и посмотреть, показывается ли тело запроса.

9. Как выглядит текстовый рисунок на телефоне — не съезжает ли моноширинный блок, помещается ли по ширине экрана.

### Результаты: Claude, веб (первый живой прогон)

**Главный вывод: Claude (веб) подключается по MCP 2026-07-28.** В логе сервера (`just spike-a`, `strict_protocol: false`) все настоящие MCP-запросы после установления соединения несут `"protocol_version":"2026-07-28"` — `server/discover`, `tools/list`, `resources/list`, `resources/read`, `tools/call`. Это первое прямое подтверждение для главного риска фазы 0 (PRODUCT-V1 9.4, **О-20**): по крайней мере один из двух целевых хостов уже поддерживает 2026-07-28 в проде, не только «скоро» из блога Anthropic. ChatGPT пока не проверен — решение по **О-28** (запасная версия протокола) стоит принимать в T05 уже с этим фактом.

Детали из лога:
- Перед реальной сессией — два коротких подключения с `"method":"initialize","protocol_version":""` (легаси-хендшейк, 22:20:44 и 22:21:01), не приведших к дальнейшим запросам. Похоже на проверку доступности эндпоинта при добавлении коннектора в UI Claude, до того как основная сессия перешла на `server/discover`. Не мешает и не является ошибкой.
- Дальше — **три разных `clientInfo`** в одной и той же сессии добавления коннектора: `Anthropic/Toolbox` v1.0.0 (одиночный `server/discover`+`tools/list`, похоже на предпросмотр/валидацию коннектора), `Anthropic/ClaudeAI` v1.0.0 и `claude-ai` v0.1.0 — оба делают полный набор (`discover`, `resources/list`, `tools/list`), но затем расходятся: `Anthropic/ClaudeAI` шлёт `tools/call` в 22:22:36 и 22:24:14 (похоже на вызовы от лица модели — `show_widget`, затем `echo` из скриншота), а `claude-ai` — `resources/read` в 22:22:35 (чтение HTML виджета) и отдельный `tools/call` в 22:22:41 (по времени сразу после первой отрисовки виджета — похоже на нажатие кнопки «Call widget-only tool» в самом виджете, то есть проксированный `callServerTool` для `widget_poke`). **Похоже, что у Claude отдельные клиентские идентичности для вызовов от модели и для вызовов, инициированных виджетом** — стоит перепроверить на втором прогоне, прежде чем считать это надёжным паттерном.
- Ровно **три** `tools/call` за всю сессию — согласуется с тем, что было в скриншотах (вызов `show_widget`, проксированный `widget_poke` из кнопки виджета, вызов `echo`); «попытка прочитать контекст виджета» (подписанная в UI как `widget_poke`, см. ниже) в лог не попала вовсе — значит она не доходит до сервера, это чисто хостовый механизм.
- Виджет отрисован полностью, не текстовый фоллбэк; контекст хоста реалистичен: `locale: "en-US"`, `platform: "web"`, `theme: "dark"`, `displayMode: "inline"`, `containerDimensions: {maxHeight: 5000, width: 736}`, `safeAreaInsets` — все нули (ожидаемо для веба).
- **Найден и исправлен баг рисунка**: строки содержимого были на 1 символ шире рамки (33 против 32) — заметил сам Claude в диалоге, отвечая на вопрос о виджете. Источник — рамка и контент собирались раздельно без проверки длины. Исправлено в `main.go` (`spikeDrawing`) и `widget/src/main.ts` (`DRAWING`): теперь обе константы дают ровно 30 рун на строку, сгенерировано и проверено скриптом, а не на глаз.
- **`widget_poke` (app-only) действительно недоступен модели напрямую.** Модель не смогла его вызвать: попытка «прочитать контекст виджета» ушла как `tool_name: "MathTrail:show_widget"` (это идентификатор виджета-источника, не вызов `widget_poke`), и в ответе модель сама написала: «If the poke was meant to update it, nothing new came through. Or did you want `widget_poke` sent through echo?» — прямое подтверждение, что инструмента `widget_poke` в её списке нет.
- **Названия инструментов хост префиксует именем коннектора**: `tool_name` в интерфейсе — `"MathTrail:show_widget"`, а не просто `"show_widget"`. Это Claude-специфичное пространство имён, стоит учесть при описании инструментов в PRODUCT/SPEC (модель обращается к ним с префиксом, ребёнок/родитель префикс не видит).
- **`hostcontextchanged` несёт полное определение инструмента**, включая `_meta`: в логе виджета видно `toolInfo.tool` целиком (`name`, `description`, `inputSchema`, `outputSchema`, `_meta.ui.resourceUri`) плюс `styles.variables` темы (`light-dark(...)` CSS-переменные). Полезно для T14 (что класть в пакет виджету).
- **Аргументы и тело вызова инструмента видны пользователю буквально** — в интерфейсе Claude под заголовком «Reading widget context» открыт блок «Request» с сырым JSON. Прямое подтверждение риска из **О-27**.
- **Модель видит `content`/`structuredContent`**: на `echo` с аргументом `"echo"` модель точно процитировала `echo: echo` из ответа инструмента.
- Не проверено ещё: несколько виджетов за один ход, `ui/message` визуально в транскрипте.

### Результаты: Claude, телефон (мобильное приложение)

Коннектор, добавленный в вебе, доступен и на телефоне (тот же аккаунт, тот же сервер за туннелем — отдельно подключать не пришлось). Виджет `show_widget` отрисован полностью, без текстового фоллбэка. Контекст хоста корректно отличается от веба:

```json
{
  "locale": "en-US",
  "platform": "mobile",
  "theme": "light",
  "displayMode": "inline",
  "containerDimensions": { "maxHeight": 5000, "width": 353 },
  "safeAreaInsets": { "top": 0, "right": 0, "bottom": 0, "left": 0 }
}
```

- `platform: "mobile"` (на вебе было `"web"`) — хост правильно различает поверхность.
- `width: 353` (на вебе — `736`) — контейнер подстроен под ширину экрана телефона, а не под какое-то фиксированное значение.
- `theme: "light"` (на вебе было `"dark"`) — тема берётся из реальной настройки конкретного устройства/приложения, не глобально с аккаунта.
- `safeAreaInsets` — все нули, как и на вебе; ожидаемо для `displayMode: "inline"` (виджет — карточка внутри ленты чата, а не полноэкранный режим, где отступы под notch/home indicator были бы актуальны).
- **Рисунок (30 символов) читаем**, помещается по ширине карточки без горизонтальной прокрутки и без переносов — после исправления бага с рамкой (см. выше) визуально ровный.

### Находка: `SupportedProtocolVersions` только `["2026-07-28"]` ломает добавление коннектора в Claude

Проверено напрямую: тот же коннектор (URL, «No sign-in»), тот же браузер — на обычном `just spike-a` шаг **«Connect» проходит**, на `just spike-a-strict` — **падает с `status 400`** («AA is set up as not requiring sign-in, but the server asked for sign-in when checked (status 400)»).

Разбор лога обоих прогонов показывает одинаковое начало сессии: два коротких подключения `"method":"initialize","protocol_version":""` (легаси-хендшейк) перед основной сессией `server/discover` → `tools/list` → `resources/list`/`resources/read` → `tools/call`, все уже на `2026-07-28`. В обычном режиме эти два легаси-`initialize` проходят молча и не мешают; при `SupportedProtocolVersions: []string{"2026-07-28"}` они, видимо, и оказываются той самой точкой отказа — в логе `mcp_request` для них при этом ничего не появляется даже в момент сбоя (ошибка возникает на транспортном уровне, до нашей логирующей middleware, поэтому доказательство косвенное — по отсутствию записи и совпадению по времени, не по прямой ошибке в логе).

**Значит для v1 сужать `SupportedProtocolVersions` до одной версии не стоит**, даже если реальные разговоры и так всегда идут по 2026-07-28 (это видно в обоих прогонах одинаково) — само подключение коннектора у Claude, похоже, полагается на способность сервера ответить на legacy-совместимый пробный запрос при первой настройке, и наглухо отказывать в более старых версиях эту настройку ломает. Стоит учесть в **О-20/О-28** при решении в T05: держать сервер permissive (SDK сам предпочитает 2026-07-28 при согласовании), а не форсировать «только 2026-07-28».
