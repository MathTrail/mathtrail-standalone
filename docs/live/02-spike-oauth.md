# Спайк B: заглушка OAuth (T04)

> Код — [spike/oauth/](../../spike/oauth/) (удаляется в T17). Запуск — `just spike-b` из корня репозитория, внутри devcontainer.

**Статус: закрыто.** Колонка Claude в матрице заполнена целиком: CIMD, `resource`, PKCE, обновление токена, step-up по scope, `401` посреди разговора и полный отзыв доступа — всё проверено живыми прогонами и подтверждено логом сервера. ChatGPT не проверялся — решение автора, та же причина, что и в T03 (нужна платная подписка для режима разработчика). Возврат к нему — перед T63/T61–T64.

## Что это

Одноразовый Go-сервер, который играет одновременно роль сервера авторизации и защищённого MCP-ресурса — как и будет устроен настоящий сервис (T47–T49), но без входа через Google и без шифрования токенов: **одобряет всех**, без единого экрана логина. Проверяем: как Claude и ChatGPT на самом деле проходят регистрацию клиента, `/authorize`, `/token`, обновление токена и реакцию на `401` посреди разговора — до того как проектировать реальный сервер авторизации.

Эндпоинты:

| Путь | Что делает |
|---|---|
| `GET /.well-known/oauth-protected-resource` | RFC 9728 — метаданные защищённого ресурса |
| `GET /.well-known/oauth-authorization-server` | RFC 8414 — метаданные сервера авторизации, включая `client_id_metadata_document_supported: true` и `authorization_response_iss_parameter_supported: true` |
| `POST /register` | RFC 7591 — динамическая регистрация клиента (DCR) |
| `GET /authorize` | сразу редирект с `code`, `state`, `iss` — без экрана согласия |
| `POST /token` | `authorization_code` (с проверкой PKCE S256) и `refresh_token` (с ротацией) |
| `GET /mcp` / `POST /mcp` | защищённый MCP-эндпоинт, `401` с `WWW-Authenticate` без токена |

Три тестовых инструмента, все требуют `mcp:advanced` (кроме `whoami`), который сервер авторизации никогда не выдаёт (см. «Замечания»), поэтому вызов детерминированно демонстрирует нехватку scope:

| Инструмент | Механизм отказа |
|---|---|
| `whoami` | обычный, `securitySchemes: oauth2, scope mcp` — просто успешный вызов |
| `whoami_advanced` | **HTTP 403** + заголовок `WWW-Authenticate: Bearer error="insufficient_scope", scope="mcp:advanced", ...` — механизм core MCP-спеки (раздел «Scope Challenge Handling») |
| `whoami_advanced_metaerror` | `CallToolResult{isError:true}` с `_meta["mcp/www_authenticate"]` — задокументированный механизм ChatGPT Apps SDK, отдельно от core-спеки |

Изначально был реализован только последний вариант; первый живой прогон в Claude показал, что это неверный выбор по умолчанию — см. «Результаты» ниже.

## Сверка с документацией перед реализацией

Код написан по актуальной спецификации MCP authorization 2026-07-28 (`/specification/2026-07-28/basic/authorization/{index,authorization-server-discovery,client-registration,security-considerations}.mdx`, скачано напрямую из репозитория `modelcontextprotocol/modelcontextprotocol`), а не по памяти:

- **CIMD теперь приоритетнее DCR.** С 2026-07-28 Dynamic Client Registration формально **deprecated** («retained for backwards compatibility»); приоритет — Client ID Metadata Documents (клиент использует HTTPS URL как `client_id`, сервер сам обязан зафетчить документ по этому URL). Сервер поддерживает оба пути.
- `iss` в ответе `/authorize` — по RFC 9207, обязателен к отправке, если объявлен `authorization_response_iss_parameter_supported: true` в метаданных AS (объявили).
- `securitySchemes` — расширение ChatGPT/OpenAI, ещё **черновик** ([SEP-1488](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1488), не в стабильной спеке). Первоисточник (сам текст SEP) описывает поле как **верхнеуровневое** на дескрипторе инструмента; `go-sdk` v1.8.0 такого поля на `Tool` не имеет (проверено `go doc` — там только `Meta`, `Annotations`, `Description`, `InputSchema`, `Name`, `OutputSchema`, `Title`, `Icons`, без catch-all). Значит кладём `securitySchemes` в `_meta.securitySchemes` — задокументированный запасной формат для обратной совместимости. **Не проверено вживую** (ChatGPT не тестируется, см. ниже) — если когда-нибудь появится доступ, стоит свериться, что ChatGPT действительно читает вложенный вариант, а не только гипотетический верхнеуровневый.
- `_meta["mcp/www_authenticate"]` — формат подтверждён документацией OpenAI Apps SDK: массив строк (не одна строка) внутри `_meta` результата вызова инструмента с `isError: true`.
- Для `/mcp` использован `mcp.StreamableHTTPOptions.DisableLocalhostProtection: true` — иначе включённая по умолчанию защита от DNS rebinding блокирует ровно тот трафик, что идёт через `cloudflared` (запрос приходит с 127.0.0.1, но с настоящим публичным `Host`). Для этого спайка сознательно **не** применяется трюк T03 с `--http-host-header` — наоборот, нужен настоящий `Host`, чтобы сервер мог вычислить свой issuer динамически (см. ниже). **Только для спайка**; в проде (T47–T49) сервис слушает свой настоящий домен и эту защиту не отключает.

## Архитектурное решение спайка: issuer без знания собственного URL

Сервер не знает свой публичный адрес при старте — `cloudflared` выдаёт случайный поддомен уже после того, как процесс слушает порт (та же проблема курицы и яйца, что и в T03). Решение: **каждый обработчик вычисляет issuer из заголовка `Host` входящего запроса** (`issuer(r) = "https://" + r.Host`), а не из переменной окружения. Поскольку `--http-host-header` в этот раз не используется, `cloudflared` пробрасывает настоящий публичный `Host` — проверено локально (`curl -H "Host: <домен>" localhost:8082/...` отдаёт метаданные с этим доменом как `issuer`). Это устраняет саму проблему, а не обходит её костылём с перезапуском после получения URL.

## Подтверждено без хостов (curl)

Полный цикл прогнан вручную (см. историю разработки — не автоматизированный тест, спайк одноразовый):

1. DCR (`POST /register`) → `client_id`, без секрета (`token_endpoint_auth_method: "none"`).
2. `GET /authorize` с PKCE S256 → редирект с `code`, `iss`, `state`.
3. `POST /token` (`authorization_code`) с верным `code_verifier` → `access_token` (TTL 90с — специально коротко, чтобы живой прогон успел увидеть обновление) + `refresh_token`.
4. `tools/call whoami` с токеном → успех, видно `clientId`/`scopes`/`expiresAt`.
5. `tools/call whoami_advanced` → HTTP `403` c `WWW-Authenticate: Bearer error="insufficient_scope", scope="mcp:advanced", ...`; `tools/call whoami_advanced_metaerror` → HTTP `200`, `CallToolResult{isError:true}` c `_meta["mcp/www_authenticate"]` — оба перепроверены после исправления (см. «Результаты»).
6. `POST /token` (`refresh_token`) → новые `access_token`+`refresh_token`; повторное использование старого `refresh_token` → `invalid_grant` (ротация работает).
7. Ожидание истечения `access_token` (90с) → следующий `tools/call` → `401` с `WWW-Authenticate` (реакция на «401 посреди разговора»).
8. Неизвестный `client_id` на `/authorize` → `400 invalid_client`; неверный `code_verifier` на `/token` → `400 invalid_grant` (PKCE действительно проверяется).

Лог сервера подтверждён без секретов: пишутся `client_id`, `redirect_uri`, `resource`, `requested_scope`/`granted_scope`, `code_challenge_method`, причины отказов — но не сами токены, коды или `code_verifier`.

**Путь Client ID Metadata Documents проверен на настоящем документе Claude** (`curl` до `https://claude.ai/oauth/mcp-oauth-client-metadata`, затем `/authorize` с этим `client_id` — не искусственный тест, реальный документ, реальный `redirect_uri`). Заодно нашёлся баг спайка: первый живой прогон дал `invalid_client: context deadline exceeded` — `fetchCIMD` не укладывался в 5 секунд (скорее всего медленный первый DNS-резолв внутри процесса, не сам эндпоинт: отдельный `curl` в тот же момент отработал за 0.2с). Исправлено: таймаут увеличен до 10с и добавлен один retry (`oauth.go`). Проверено повторно на исправленной версии — работает.
Заодно видно, что документ Claude заявляет `grant_types` из трёх значений: `authorization_code`, `refresh_token` и `urn:ietf:params:oauth:grant-type:jwt-bearer` — последнее наш `/token` не поддерживает (только `authorization_code`/`refresh_token`); не помешало живому прогону, но стоит иметь в виду для T47–T49.

## Инструкция: как подключить

1. В devcontainer: `just spike-b` (без аргументов — порт 8082 по умолчанию). Сервер и туннель печатают:
   ```
   MCP endpoint:   https://<случайное-имя>.trycloudflare.com/mcp
   Health check:   https://<случайное-имя>.trycloudflare.com/healthz
   ```
   Как и в T03, если сразу после старта хост отвечает ошибкой соединения (например, `530`) — подождите 10–20 секунд и попробуйте снова (туннелю нужно время зарегистрироваться на edge Cloudflare).
2. Добавьте коннектор тем же URL, что и в T03. На экране аутентификации (если хост его показывает, как Claude в T03) выберите **«Sign in now»** или **«Sign in when needed»** — в этот раз сервер РЕАЛЬНО требует OAuth (в отличие от T03, где было «No sign-in»). Пройдите вход — экрана логина не будет, сервер сразу редиректит с кодом.
3. Спросите модель вызвать `whoami`, затем `whoami_advanced` и `whoami_advanced_metaerror` по очереди (у обоих ожидается отказ по нехватке scope, но разными механизмами — интересно, отреагирует ли хост на них по-разному), затем — ничего не делайте **90+ секунд** и снова попросите `whoami`: интересно, обновит ли хост токен сам (через `refresh_token`) до вызова, или сначала получит `401` и лишь затем обновится.
4. **Проверка `401` посреди разговора.** Ждать истечения токена бесполезно — хост обновляется по `expires_in` и до `401` не доводит (см. «Результаты»). Поэтому токены отзываются принудительно, эндпоинтом спайка (отвечает и на `GET`, так что можно открыть прямо в браузере, в том числе с телефона):
   - `https://<поддомен>.trycloudflare.com/spike/revoke` — стирает только access-токены. Refresh остаётся живым, так что хост *может* обновиться молча. **Вопрос прогона:** заметит ли пользователь хоть что-нибудь, или всё пройдёт прозрачно.
   - `https://<поддомен>.trycloudflare.com/spike/revoke?what=all` — стирает и refresh. Обновиться нечем, `/token` ответит `invalid_grant` — это имитация «родитель отозвал доступ» из T07. **Вопрос прогона:** предложит ли хост переподключиться сам, и не потеряется ли при этом разговор.

   После каждого отзыва попросите модель снова вызвать `whoami` и смотрите в лог сервера: `token_unknown` — это и есть пойманный `401`.

### На каждой поверхности проверить и отметить в матрице ниже

1. Какой способ регистрации клиента хост выбрал — CIMD (в логе сервера появится `registration=cimd`, а не `dcr`) или DCR (`POST /register` в логе).
2. `redirect_uri`, который хост присылает на `/authorize` — `localhost`/`127.0.0.1` (нативное приложение) или что-то ещё.
3. Прошёл ли хост экран согласия без сучка (мы никого не спрашиваем, сразу редиректим) — не запутался ли хост в отсутствии реального логина.
4. `resource` — прислал ли хост параметр вообще, и что именно (RFC 8707).
5. `scope` — что запросил хост (сервер всё равно всегда выдаёт только `mcp`, см. «Замечания» — интересно само значение запроса).
6. Частота обновления токена — обновляет ли хост `access_token` заранее (до истечения) или только после первого `401`.
7. Реакция на `401` при вызове инструмента посреди разговора — тихо переавторизуется и повторяет вызов сам, или показывает пользователю, что нужно перелогиниться.
8. Реакция на `whoami_advanced` (`insufficient_scope` через `_meta["mcp/www_authenticate"]`) — показывает ли хост это как приглашение к повторной авторизации (step-up), или просто как ошибку инструмента.

### Результаты: Claude (три живых прогона)

- **CIMD подтверждён вживую** — `client_id: https://claude.ai/oauth/mcp-oauth-client-metadata`. Первое живое доказательство того, что новый приоритет CIMD над DCR (2026-07-28) — не только на бумаге: Claude.ai реально им пользуется, а не откатывается на DCR.
- **`resource` пришёл точно** — `https://<поддомен>.trycloudflare.com/mcp`, ровно canonical URI нашего MCP-эндпоинта (RFC 8707 соблюдён).
- **Отзыв access-токена при живом refresh проходит незамеченным — и даже без `401`.** Через `/spike/revoke` стёрты access-токены, refresh оставлен. Со стороны чата: `whoami` → `expires_at 14:22:48`; отзыв; `whoami` → снова успех, `expires_at 14:24:04`. Выглядело как «получил 401 и молча обновился», но лог показывает другое:
  ```
  14:21:18  token_refresh                      токен живёт до 14:22:48
  14:21:52  spike_revoke  access=2 refresh=0
  14:22:34  token_refresh                      обновился сам, за 14с до истечения
  ```
  Записи `token_unknown` между отзывом и следующим вызовом **нет** — значит `401` не наступил: хост обновился по сроку раньше, чем пользователь успел попросить `whoami`. Практический вывод: пока у хоста жив refresh-токен, отзыв одного лишь access-токена для пользователя невидим.
- **Настоящий `401` виден только при отзыве всего.** `/spike/revoke?what=all` — и порядок действий хоста в логе однозначен:
  ```
  14:23:32  spike_revoke  access=1 refresh=1
  14:24:41  token_reject  grant_type=refresh_token  "unknown or expired refresh token"
  14:24:41  token_unknown                      ← вот он, 401 на вызов инструмента
  14:24:58  authorize + token_issue            ← после нажатия Connect
  ```
  То есть: сначала пробует обновиться (получает `invalid_grant`), потом всё равно идёт в `/mcp` со старым токеном и ловит `401`, и только тогда показывает пользователю **кнопку «Connect» прямо в карточке инструмента** — не отправляет в настройки коннектора. После нажатия — обычный полный цикл авторизации в отдельном окне, вызов срабатывает, **разговор не теряется**. Это живая репетиция сценария «родитель отозвал доступ» из T07, и выглядит она мягче, чем ожидалось.
- **Обновление токена — по сроку, а не по `401`.** За три живых прогона в логе нет ни одной записи `token_expired`, то есть ни один запрос с уже истёкшим токеном до сервера не дошёл: хост опирается на `expires_in` и обновляется перед вызовом. `token_refresh` при этом случается и с запасом до истечения, и с опозданием на несколько секунд после него (TTL 90с, refresh на T+99 в одном прогоне) — но даже «опоздавший» refresh происходит до попытки сходить в `/mcp`, поэтому `401` посреди разговора так и не воспроизвёлся. Проверить реакцию на него получится только искусственно: например, отзывом токена на стороне сервера (в T04 не делали).

### Главная находка: step-up работает, но только через HTTP 403

Это выяснилось в три захода, и промежуточные выводы дважды оказывались неверными — стоит прочитать целиком, прежде чем на них опираться.

1. **Первая версия спайка** сигналила нехватку scope только через `_meta["mcp/www_authenticate"]` в обычном `CallToolResult` (документированный путь ChatGPT Apps SDK). Живой прогон: Claude показал это как обычную ошибку инструмента, никакой реакции на auth. Модель сама указала на механизм из основного раздела MCP-спеки «Scope Challenge Handling» — **HTTP 403 + заголовок `WWW-Authenticate`**. Перепроверено по тексту спеки: она права.
2. **Исправлено** (`main.go`, `requireToolScope`): `whoami_advanced` теперь отвечает настоящим HTTP 403 на транспортном уровне, а `_meta`-механизм вынесен в отдельный инструмент `whoami_advanced_metaerror`, чтобы сравнить оба пути на одном хосте. Повторный живой прогон дал сравнение:
   - **HTTP 403** — Claude распознаёт как проблему прав: подменяет текст ошибки на своё «This connector requires additional permissions. The user needs to reconnect it from connector settings».
   - **`_meta`-путь** — полностью игнорируется как auth-сигнал: до модели доходит сырой текст ошибки сервера.
   По видимой в чате картине это выглядело как «step-up нет ни там, ни там» — и это был **неверный вывод**.
3. **Лог сервера показал обратное.** После отказа `whoami_advanced` Claude сам, без участия человека в чате, сходил на `/authorize` второй раз — уже с `requested_scope: "mcp mcp:advanced"`:
   ```
   00:35:16 authorize  requested_scope="mcp"                granted_scope="mcp"
   00:55:29 authorize  requested_scope="mcp mcp:advanced"   granted_scope="mcp"
   ```
   То есть **step-up у Claude есть и он честно запрашивает именно тот scope, который был назван в челлендже**. Не замкнулся цикл по вине самого спайка: `/authorize` жёстко выдавал константу `"mcp"`, игнорируя запрошенное, поэтому новый токен приходил без `mcp:advanced` и инструмент падал снова. Модель этого не видела — с её стороны просто «ничего не изменилось».
4. **Исправлено**: `/authorize` теперь выдаёт запрошенный scope (`oauth.go`), fallback на `mcp` при пустом. Демо осталось детерминированным: хост в первый раз всё равно просит только `mcp`, так что первый вызов `whoami_advanced` по-прежнему падает и по-прежнему запускает step-up.
5. **Живой прогон после исправления замкнул цикл целиком**, полностью автоматически:
   ```
   14:08:44  authorize    requested="mcp"               granted="mcp"
   14:08:45  token_issue  scope="mcp"
   14:11:47  token_refresh
   14:11:59  authorize    requested="mcp mcp:advanced"  granted="mcp mcp:advanced"
   14:12:00  token_issue  scope="mcp mcp:advanced"
   ```
   Последовательность в чате была: `whoami` → `["mcp"]`; `whoami_advanced` → **успех**; `whoami_advanced_metaerror` → **успех**. То есть на `403` хост сам сходил за новым токеном с запрошенным в челлендже scope и **сам повторил неудавшийся вызов** — ответ на вопрос, оставленный открытым в п.4: **повторяет автоматически, участие человека не требуется**.

**Важное следствие: модель step-up не видит.** Для неё `whoami_advanced` выглядит как один успешный вызов — ни 403, ни повторной авторизации, ни retry в её контексте нет. В этом прогоне модель из-за этого сделала прямо противоположный (неверный) вывод: «`whoami` отдаёт scopes `["mcp"]`, но advanced-инструменты проходят → проверка scope на сервере сломана, надо чинить». На самом деле оба показания верны, просто относятся к разным токенам: `whoami` вызывался до step-up, `whoami_advanced` — уже после. Проверено, что проверка scope при этом исправна: с токеном `scope=mcp` оба инструмента по-прежнему отказывают (`403` и `200`+`insufficient_scope`).

Для T47–T49 это значит: **в логах сервера и в том, что видит модель, состояние авторизации может расходиться**, и расхождение выглядит как баг сервера. Если какой-то инструмент MathTrail когда-нибудь начнёт требовать отдельный scope, его текст ошибки для модели должен это учитывать.

Вывод для T47–T49: индивидуальные требования к scope у инструментов сигналить **HTTP 403 + `WWW-Authenticate`**; `_meta["mcp/www_authenticate"]` можно добавлять дополнительно ради ChatGPT, но как единственный механизм он для Claude бесполезен.

## Замечания к PRODUCT/SPEC

- **Методологическое, для всех последующих живых прогонов (T46, T53, T62–T64): по видимой в чате картине выводы делать нельзя.** В этом спайке она трижды подряд оказывалась ложной, причём каждый раз убедительной:
  1. «Claude игнорирует scope-челлендж и step-up не делает» — а в логе был второй `/authorize` с расширенным scope.
  2. «Проверка scope на сервере сломана, advanced-инструменты проходят с базовым токеном» (вывод самой модели) — а на деле между вызовами прошёл полный step-up, и токены были разные.
  3. «Хост поймал `401` и молча обновился» — а `401` вообще не наступал, хост обновился по сроку.
  Причина одна: хост проводит переавторизацию прозрачно, и **модель видит только конечный результат** — ни 403/401, ни повторной авторизации, ни retry в её контексте нет. Единственный надёжный источник — лог сервера. Для приёмочных задач это значит: снимать лог обязательно, и не принимать за факт то, что модель «увидела» в чате.
- Сервер выдаёт ровно тот scope, который запрошен (никого ни о чём не спрашивая — «одобряет всех»), с fallback на `mcp`. Первая версия жёстко выдавала константу `mcp`; чем это обернулось — в «Главной находке» выше. В реальном сервисе (T47–T49) нужна настоящая логика выдачи прав, а не эхо запроса.
- `jwks_uri` в `/.well-known/oauth-authorization-server` сериализуется как пустая строка (`"jwks_uri":""`), а не отсутствует — поле в `oauthex.AuthServerMeta` у go-sdk без `omitempty`, хотя по RFC 8414 оно необязательно для непрозрачных (не-JWT) токенов, как у нас. Не должно мешать (хосты, не проверяющие JWT, просто не полезут по этому URL), но стоит перепроверить вживую — если оно создаёт проблемы, придётся не использовать структуру `oauthex.AuthServerMeta` напрямую для сериализации ответа.
- Это прямая эмпирическая проверка вопроса **О-7** (как держать состояние OAuth без БД — здесь используется просто память процесса, для прод-версии — зашифрованные самодостаточные токены) и даёт материал для T07 (реальная схема входа с Google) и T47–T49 (реализация).
- **Новая находка, не из брифа T04**: при недостатке scope у конкретного инструмента нужно отвечать HTTP `403` + `WWW-Authenticate` (core MCP-спека, раздел «Scope Challenge Handling»), а не только `_meta["mcp/www_authenticate"]` в `CallToolResult` (это отдельный, ChatGPT-специфичный путь). Живой прогон в Claude на первой версии спайка это прямо показал: инструмент, отвечавший только вторым способом, для Claude выглядел как обычная ошибка без приглашения к повторной авторизации. T47–T49 должны реализовывать оба механизма для инструментов с индивидуальными требованиями к scope, а не только один.
