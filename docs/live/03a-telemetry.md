# Телеметрия в облаке (T28a.3)

**Статус: закрыто.** 2026-09-23 трассы и метрики доезжают до Google Cloud Observability, наш спан виден вложенным в автоспан Cloud Run, строка лога и трасса связаны в обе стороны. Расход — ноль, бюджетное оповещение молчит.

> Репозиторий публичный, поэтому в отчёт идут поведение и числа, а не идентификаторы, которые не обязаны быть публичными: идентификатор экземпляра Cloud Run назван, но не выписан.

## Что даёт этот прогон

T28a.1 и T28a.2 написали телеметрию и закрыли её тестами, но ни одного спана в облаке не видели. Этот прогон отвечает на три вопроса, которые до него были бумажными:

1. **Долетает ли вообще** — достаточно ли того, что описано в `infra/terraform`, чтобы данные не просто ушли, а сохранились и открылись.
2. **Работают ли обещания приватности на живом трафике** — затирание адреса клиента и узла, закрытые словари меток, отсутствие сырого пути в имени спана.
3. **Кто решает, сохранять ли трассу** — R49 и SPEC 12.5 утверждают, что Cloud Run своим `traceparent`, а наша доля только страховка.

## Руками, по одному разу

| Шаг | Готово | Заметки прогона |
|---|---|---|
| `roles/resourcemanager.projectIamAdmin` личности `mathtrail-tf@` | [x] | Одной командой, до мержа. Без неё `apply` упал бы с 403 на первых в конфигурации привязках IAM уровня проекта, а из-за `needs: infra` не выкатился бы и образ: зелёный PR, красная доставка |

Больше ручного не понадобилось — и это главный вывод, потому что по дороге казалось иначе (см. «Ошибка прогона»).

## Что показал прогон

**Доставка.** Сервис отдаёт коммит мержа, ревизия `mathtrail-00021-kqf`. Три задания CD зелёные, включая `apply`, который создал две привязки IAM рантайм-аккаунту. У него ровно `roles/telemetry.writer` и `roles/serviceusage.serviceUsageConsumer` и ничего сверх.

**Двух API не хватало.** Первая проверка нашла то, чего не нашли ни тесты, ни ревью: `apis.tf` включал только `telemetry.googleapis.com`. Это **приём** данных, и он ничего не решает про их хранение — метрики отвергались с 403 «Cloud Monitoring API has not been used in project», трассам было некуда ложиться. Добавлены `cloudtrace.googleapis.com` и `monitoring.googleapis.com`.

Отказ при этом выглядел ровно так, как задумано: **одна** строка `telemetry_export_failed` через наш обработчик, и сервис продолжил отвечать. Телеметрия не стала причиной отказа — то, ради чего в T28a.1 спорили с внешним разбором про Fail Fast.

**Вложенность.** Трасса `e39852…2cfb2`:

```
(родитель во фронтенде Google, в проект не экспортируется)
└── /check-1     204.011 мс   /component: AppServer   ← автоспан Cloud Run
    └── GET      274.734 мкс  service: mathtrail      ← наш
```

Наш спан — 0,1% времени запроса. Остальное платформа.

**Затирание работает на живом трафике.** На спане `client.address: redacted` и `network.peer.address: redacted`. Имя спана — `GET`, без пути: сырой путь в имя не попадает.

**Ресурс собран детектором верно:** `cloud.region: us-central1`, `faas.version` — ревизия, `faas.instance` — настоящий идентификатор экземпляра, `gcp.project_id` на месте.

**Зонды исключены.** В Trace Explorer спаны `/health` есть, но все они принадлежат Cloud Run; нашего спана на зонд нет ни одного, и в метриках `/health` не появляется.

**Метрики доехали** как `prometheus.googleapis.com/http_request/delta` и `.../http_request_duration/histogram:delta` — дельта-темпоральность на месте. `solver_run_steps` нет и не должно быть: песочницу пока никто не вызывает, инструменты приходят в T41–T45.

**Лог и трасса связаны в обе стороны.** Кнопка «View Logs» на спане собрала запрос по `trace` и `spanId` и нашла ровно одну строку — наш `http_request` со статусом 404 и severity Warning.

**Стоимость: ноль.** Привязки IAM и включение API не тарифицируются, весь трафик прогона — в бесплатных лимитах, оповещение на $1 молчит.

## Ошибка прогона

Стоит записать, потому что она стоила правок в трёх документах, которые пришлось откатывать.

Первые чтения трассы отвечали `_Trace bucket not found in project mathtrail-prod`. В документации Google нашлось объяснение, которое идеально ложилось: спаны Cloud Run, в отличие от других источников, **не** создают хранилище, его провижинят кнопкой в Trace Explorer или вызовом Observability API. Я записал это как пятый ручной шаг в `docs/self-hosting.md`, в задачу и в R49.

Ничего этого не потребовалось. Хранилище завелось само, минут за двадцать после включения API; Observability API в проекте так и не включён, кнопку никто не нажимал. Ошибка была в нетерпении: я читал раньше, чем провижининг закончился, и принял временное состояние за постоянное — тем охотнее, что нашлась документация, которая его объясняла.

**Что из этого осталось в документах:** не ручной шаг, а предупреждение, что на проекте, который телеметрии ещё не получал, ей надо дать минут двадцать, и что `_Trace bucket not found` в это время — провижининг, а не поломка.

## Замечания

- **Сэмплирует наша доля, а не платформа.** 3 сэмплированных запроса из 68 — это ≈4,4% при нашей доле 0.1, а не картина решения Cloud Run. Похоже, что для трафика через domain mapping `traceparent` с решением не приходит, и `ParentBased` падает на долю. Если так, R49 и SPEC 12.5 утверждают неверное, и само число 0.1 надо пересматривать: у страховки и у основного регулятора расхода спанов разная цена ошибки. 68 запросов — не статистика; записано в T64.
- **`http.route` на спане пустой** для несовпавшего маршрута — так его ставит `otelgin`. На спане это безвредно: цена рядов есть только у метрик, а там ставится `other`, и это закрыто тестом.
- **`network.peer.port` не затёрт**, хотя адрес рядом затёрт. Эфемерный порт источника сам по себе никого не называет, а затирать число строкой значит менять тип атрибута ради сокрытия того, чего он не сообщал. Причина записана в `internal/telemetry/redact.go`, чтобы это не выглядело недосмотром.
