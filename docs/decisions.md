# Implementation decision log

> Why the service is built the way it is. Every entry says what was decided, why, what was rejected, and where it lives.
>
> **The rule:** do not re-propose something rejected here without new evidence. If a decision has to change, ask the author and update this file.
>
> Product decisions live in [PRODUCT-V1.md, section 12.1](../PRODUCT-V1.md#121-settled) under the numbers О-…; this file holds implementation decisions, R01… The first entries were collected in T05 from the phase 0 spikes: [T03 — protocol and widget](live/01-spike-protocol.md), [T04 — the OAuth stub](live/02-spike-oauth.md). The prototype's decisions D01–D45 are in [docs/prototype/decisions.md](prototype/decisions.md) and are cited as "D43 of the prototype".

## Protocol and SDK

**R01. Go SDK — v1.8.0.** PRODUCT 7 named v1.7.0; as of 2026-09-16 the current release is v1.8.0 (14.09.2026), a patch release with no protocol changes: the same set of supported versions, with 2026-07-28 still the newest. It adds limits on SSE event size, body size and JSON depth, the `ServerOptions.SupportedProtocolVersions` setting, and an explicit `-32022` code in place of a bare 400. Spike T03 was built and verified on it. — *Why:* strictly newer and fully compatible; there is no reason to stay on the previous patch. — *Where it lives:* `go.mod` (T17), PRODUCT 7.

**R02. The server does not narrow the set of protocol versions.** We work only over 2026-07-28 (О-20, О-28), but `SupportedProtocolVersions` is left at its default: the SDK already prefers the newest version when negotiating. — *Why:* in strict mode Claude fails to add the connector. Before the main session the host sends two short legacy `initialize` requests with an empty version, and rejecting them by version breaks the "Connect" step (status 400); in the default mode the same runs go entirely over 2026-07-28 — not one real request negotiated an older version. — *Rejected:* a strict "2026-07-28 only" transport; a stateless 2025-11-25 fallback path (О-28). — *Where it lives:* T41; to be re-checked in ChatGPT in T63.

## Sign-in and permissions

**R03. Client registration is CIMD, with DCR kept as a fallback.** The authorization server metadata declares `client_id_metadata_document_supported: true`, and the server fetches the document itself over an HTTPS `client_id`; `/register` (RFC 7591) is still supported for backwards compatibility. — *Why:* as of 2026-07-28 DCR is formally deprecated, and Claude showed up live with CIMD (`client_id: https://claude.ai/oauth/mcp-oauth-client-metadata`) without ever falling back to DCR; the ChatGPT documentation also recommends CIMD, though that has not been verified live. — *Where it lives:* T07, T47–T49.

**R04. Insufficient permissions on a tool return HTTP 403 with a `WWW-Authenticate` header.** The `_meta["mcp/www_authenticate"]` field in the call result is sent in addition, for ChatGPT's sake, but it cannot be the only mechanism. — *Why:* the live run in T04: on a 403 Claude went to `/authorize` for the wider scope and retried the failed call by itself, with no human involved; a tool that answered only through `_meta` looked to it like an ordinary error. — *Consequence:* the model never sees the step-up — in its context there is a single successful call — so its account of the authorization state is unreliable and only the server log can be trusted. The same rule applies to every acceptance run. — *Where it lives:* T47–T49.

**R41. `seal` hands out a key ring, not an interface.** `seal.NewKeyRing` returns the concrete `*seal.KeyRing`, against the convention that a constructor returns the interface its package offers. — *Why:* there is one way to seal a value and there will be one; the package is pure computation with no I/O, so a caller under test runs the real sealer and gets a real ciphertext, which is a better test than a fake that returns a fixed string. The convention exists so that mockery always has something to generate from, and here there is nothing worth faking. — *Rejected:* an interface with a single implementation, which would be a name for the same thing and one more file of generated mocks nobody calls. — *Where it lives:* `internal/infra/seal`, CLAUDE.md ("Interfaces").

**R42. The domain asks the catalogs for what it needs, and the content answers.** A domain package that needs the catalogs declares an interface of its own — `tutor.Catalog` is the first, with three methods that speak in identifiers — and `*content.Content` satisfies it by gaining the matching accessors. No domain package imports `content`. — *Why:* the dependency rule of CLAUDE.md, applied to a package that is data rather than infrastructure: the rule of section 3 needs three facts about the catalogs and nothing else, and saying so in three method signatures is both the smallest contract and the honest one. It also buys a test: the rule's own cases are written against a catalog of three topics and four traps, which states what is being tested, where the four hundred and fifty reference tasks of the binary would only obscure it. The grade crosses that line and the level does not — the domain knows what school year a child is in, and what years are grouped into stays with the catalogs. — *Rejected:* importing `content` from the domain, which is simpler by one interface and would have made every rule test depend on the shipped content; an adapter type in between, which would be a name for the same three methods. — *Where it lives:* `internal/domain/tutor`, `content`, and the same shape is what T32, T35 and T36 use when they need the catalogs.

**R43. The tool for mocks is kept and the mocks are not written.** mockery v3 is pinned, configured and checked by CI, and `.mockery.yaml` lists no packages: an interface is tested against the real implementation where that implementation does no I/O, and against a hand-written fake of a few lines where a test has to force an outcome. — *Why:* the two interfaces the service has are pure computation, and for both a mock would prove less. `profile.Sealer` exists so that a sealed task is tied to one child and one task and refuses to open anywhere else; a mock returning a fixed string cannot show that, while the real key ring is six lines to build and shows it exactly. `tutor.Catalog` exists so the rule can be run against a catalog of three topics written out in the test, which states what the test assumes in one place — as expectations on a mock, the same assumption is scattered across every case and has to be reassembled by the reader. — *Rejected:* generating mocks for those two now, which would weaken both sets of tests; removing mockery along with its recipes and its CI job, which would have to be put back the first time an interface earns one. — *Consequence:* the CI job runs against an empty config and says so in a second; the recipes notice `packages: {}` themselves. — *What would change it:* the first interface whose real implementation reaches outside this process, and that is the storage. The profile lives in the parent's Drive (T50, T51), so `store.Storage` is the first interface here whose real half needs a network, a token and somebody else's service to answer. Two things about it do not change: its implementations are still held to one contract test set, and the Drive one still runs against `httptest`, because that is what shows the two are interchangeable and a mock shows nothing of the sort. What changes is the tools above it — a test of what a tool does when a write lost the revision race, when the file was deleted, or when the parent took the grant back has to make that happen rather than wait for it, and `EXPECT().Save(...).Return(store.ErrConflict)` says which case it is in one line where a hand-written fake grows a flag per outcome and a fake Drive has to speak Google's error bodies. That is when `.mockery.yaml` gains its first package and the committed mocks start being checked. — *Where it lives:* CLAUDE.md ("Tests"), `.mockery.yaml`, `justfile`, `.github/workflows/ci.yml`.

## Tools and environment

**R05. There is no separate tool-versions file.** Each exact version is pinned where the tool is installed: an `ARG` in `.devcontainer/Dockerfile`, a literal in `devcontainer.json` and `devcontainer-lock.json`, a module version in `go.mod`, an exact version plus a lockfile for npm, a commit SHA for GitHub Actions. — *Why:* one source of truth per tool; a separate versions file would have to be kept in sync with those same places by hand, and the build reads the versions from them anyway. — *Rejected:* a shared versions file; checksum verification beyond what `go install` already does. — *Where it lives:* CLAUDE.md ("Exact versions only"), T01.

**R47. The ceiling on copying a value is moved once rather than excepted at every site.** `gocritic`'s `hugeParam` fires at eighty bytes, which is exactly what the five option texts of a task weigh, and they are passed by value from the rule through the sandbox and into every test around it. `.golangci.yml` moves the ceiling to eighty-eight. — *Why:* the five options are one value on purpose — nothing between the rule and the interpreter can change the task under whoever asked about it, and the array states in the type that a task has exactly five options. Writing the same exception out at eight call sites would say less than one line saying it once. Eighty-eight is where the next value up in this repository sits, so `Answered`, `Student` and `Corridor` keep the exceptions they already carry and nothing else changed verdict. — *Rejected:* a `//nolint` at every site, which is the noise above; switching the check off, which would stop catching the values it was put there for; a slice instead of an array, which saves fifty-six bytes and loses both the count and the promise that nobody else holds a reference to it. — *Where it lives:* `.golangci.yml`.

## The full checks

**R38. What blocks a merge, and what only reports.** Three checks can turn a pull request red on their own: the coverage of the changed lines, held at 90% by `codecov.yml`; CodeQL with the `security-extended` queries; and Trivy over the runtime image at HIGH and CRITICAL, run through `just ci-image-scan` from its own pinned image so the same command gives the same verdict on a laptop. Everything else stays a reading: SonarCloud as R31 left it, OpenSSF Scorecard as a public measure of how the repository is run, and the total coverage, which moves for reasons a single change does not control. — *Why:* the service is written around children's data, and the bar has to hold without depending on anyone remembering it. Coverage of the patch rather than of the project is what a change can actually be held to: `cmd/sitegen` and `cmd/sitecheck` sit at 19–26% and leave entirely in T66, so a project-wide floor would either be set so low it proves nothing or block work it has nothing to do with. CodeQL follows values across functions and files, which is the one thing the linter's own security checks cannot do, and it is what will matter once sign-in, Drive and the HTTP surface are real. — *Consequence:* Trivy reports a vulnerability of the Go standard library from the version stamped in the binary, without asking whether the code reaches it, so it can go red where `govulncheck` stays silent; the fix is a newer Go in the `Dockerfile`, and anything that cannot be fixed that way goes into `.trivyignore` with its reason. The patch status needs the repository's branch protection to require it, which is a setting rather than a file. A pull request from a fork gets no Codecov upload and therefore no patch status. — *Rejected:* a floor on total coverage, for the reason above; Snyk, which needs an account and a token for what CodeQL and `govulncheck` already answer; gating on the Sonar quality gate, which R31 settled. — *Where it lives:* `codecov.yml`, `.github/workflows/codeql.yml`, `.github/workflows/scorecard.yml`, `justfile`, `README.md`.

**R39. Invariants are tested with gopter, and a check is proven by breaking it.** Computation that holds an invariant — the ratings, `seal`, trigram similarity, readability, the solver contract, and the copies the content hands out — is tested by naming the invariant and letting the library hunt for the input that breaks it. The library is `github.com/leanovate/gopter`, and a new check is not called covered until its test has been seen to fail with the check switched off. — *Why:* worked examples prove what somebody already thought of. The shallow copy in `content` is the case in point: three hand-written examples passed while a caller could still rewrite an option inside the binary's own content, and the property that a copy shares nothing finds it by itself. Breaking the check by hand is the same idea applied to the tests: it costs a minute and catches the test that passes because it never ran the code it names. — *Rejected:* `pgregory.net/rapid`, whose API and shrinking are better but whose licence is MPL-2.0 against a list of five permissive ones — a test-only dependency never reaches the shipped binary and `go-licenses` does not even see it, but an exception to the licence rule would have to be explained for as long as the repository exists, and gopter costs ten more lines per test instead; `testing/quick`, which cannot shrink a counterexample, so a failure arrives as a wall of random input; a mutation-testing tool — `go-mutesting` is abandoned and `gremlins` is slow and noisy, and the rule above buys the same thing where it matters. — *Where it lives:* `content/property_test.go`, `go.mod`, CLAUDE.md ("Tests").
**R20. The checks run inside the development image, published to GHCR and pinned by digest.** `.devcontainer/Dockerfile` has two stages: `toolchain` — Go, Node, `just`, `golangci-lint`, `mockery` — and `devcontainer`, which adds the editor tooling, cloudflared, the compose plugin and the Claude Code CLI on top. A first job installs `just` and calls `ci-toolchain-image`, which tags the image with a hash of the Dockerfile, publishes it if nothing is published for that hash yet, and prints the digest to run the checks in; every other job runs inside that digest. `govulncheck`, `gitleaks` and `go-licenses` stay Go programs run straight from their modules at versions pinned in the justfile. Every step of the workflow is a `just` recipe or a pinned action, with one line of wiring to carry the reference between jobs. — *Why:* the author's decision, replacing an earlier arrangement where a script installed tools onto the runner. One description of the environment now serves both a laptop and a pull request; a tag computed from content means a change to the environment needs no second commit to point CI at it; and a recipe rather than a block of shell in the workflow is what the other services in the platform do. — *Consequence:* the first run after a change to `.devcontainer/Dockerfile` pays for one image build; a pull request from a fork cannot publish, so such a change has to reach `main` before a fork can be checked against it. The `image` job stays on the runner, because the docker client reaches the development environment through a devcontainer feature and a plain build does not apply features. A checkout inside a container belongs to a different user than the one running the job, and Go looks for its caches under a home directory the job does not control, so `safe.directory` and the two cache locations are set once for the whole workflow through the environment, where they hold for every step whatever user and home it gets. — *Rejected:* `latest` or any moving tag, which the rule of exact versions forbids; building the image on every run; a copy of the tool versions inside the workflow; a build cache for an image that is only ever built when its one layer has already been invalidated. — *Where it lives:* `.github/workflows/ci.yml`, `.github/actions/just/`, `.devcontainer/Dockerfile`, `justfile`, T18.

**R21. `THIRD_PARTY_LICENSES` is generated from the dependency graph, and the checks compare the two.** `just licenses` rewrites the file; `just ci-licenses` fails when a dependency carries a license outside the permissive list (MIT, BSD-2, BSD-3, Apache-2.0, ISC) or when the committed file no longer matches the graph. — *Why:* the repository owes its readers a current list of what it ships and under what terms (PRODUCT 8), and a list that is written by hand stops being true at the first dependency bump; this is the same contract the generated mocks already have. — *Consequence:* each line links the license text of the exact version in `go.mod`, so a dependency update fails the check until the file is regenerated — one command, and it is what keeps the links pointing at the text that actually ships. — *Rejected:* a list without versions, which would never need regenerating and would never be exactly true either. — *Where it lives:* `justfile`, `THIRD_PARTY_LICENSES`, T18; the npm side arrives with T42.

**R22. Nothing checks the wording of the repository.** There is no list of forbidden terms, no secret holding one and no job searching for them. This withdraws one half of the prototype's D36, the half about never naming the contest the project started from; its other half — difficulty as a level from 1 to 5 inside the grade level — stands, and lives in SPEC 1. — *Why:* the author's decision. That was a note about how the research preceding the project was written, not a rule this repository inherits, and a check with a secret list was machinery for a problem that does not exist. — *Where it lives:* nowhere; the rule is gone from CLAUDE.md and from T18.

**R31. SonarCloud reads every branch and pull request, and gates nothing.** A job sends the sources and the coverage profile the tests already measured to the organization the platform's other services report to, and the five measures in the README's second row are what it answers. It runs on the runner rather than inside the development image, because the scanner installs itself and has no business in the environment the code is built in; it takes the coverage as an artifact instead of running the tests a second time; and it is skipped for a pull request from a fork, which is given no secrets and could not pass it. Automatic Analysis is switched off on the project's side: it reports no coverage and refuses to coexist with an analysis that arrives from a workflow. — *Why:* the author's decision — the same badges and the same organization as the platform's other services, so that a person moving between them reads the same summary of a repository in the same place. The coverage was already being measured and uploaded; this gives it a second reader that also says something about duplication, complexity and the shape of the code. — *Consequence:* a merge is not blocked by the quality gate — the job fails only when the analysis itself fails, and the gate arrives as its own check from Sonar's GitHub app — so blocking on it would be a decision of its own. A third party now reads the sources: they are public and MIT, and neither a child's data nor a secret has ever been in this repository. The project has to exist in the organization and `SONAR_TOKEN` has to be among the repository's secrets, or the job is red. — *Rejected:* Automatic Analysis, which needs no workflow and sees no coverage; running the tests again inside the analysis job, which would double the slowest check for a number that already exists. — *Where it lives:* `.github/workflows/ci.yml`, `sonar-project.properties`, `README.md`.

**R40. Every green `main` publishes signed binaries, and nobody tags anything by hand.** `.github/workflows/release.yml` waits for the checks to pass on `main`, works out the next version — the newest tag with its patch number raised, `v0.1.0` when there are none — builds the server for `linux/amd64` and `linux/arm64` through `just release-artifacts`, writes `SHA256SUMS`, signs every file with keyless cosign, and publishes the lot as a GitHub release whose tag it creates itself. A button with a version field exists for the release that deserves a number of its own. The service itself is still delivered the way it always was: a merge to `main` builds an image and Cloud Run serves it. — *Why:* the author's decision, taken while raising the repository's OpenSSF Scorecard, and shaped by the reference service, which releases from every push to `main` and asks nobody to type a git command. The number it moves is Signed-Releases, but the thing underneath is worth having on its own: the certificate records which workflow, which repository and which commit produced a binary, so "this is the code that was running" stops being a claim and becomes something anybody can check. A side effect earns its keep too — with tags in the repository, `git describe` finally returns a version, so `/health` and the startup log say `v0.1.4` instead of a commit nobody can order. — *Consequence:* a release per merge, which is forty of them before RUN.md is finished; the version is semantic but its patch number counts merges rather than fixes. Signing happens before anything is published, because a release that appears without its signatures scores zero on a check that would otherwise not apply at all — worse than having no releases. The release runs from the commit the checks passed on, not from whatever `main` points at by then, and only when that commit is this repository's own: a pull request from a fork runs the checks here too, and the branch filter matches on the name of the branch the run came from, so a fork whose branch is called `main` would otherwise have had its code built, signed and published under our identity — the job requires the triggering run to be a push from this repository, which is what closes it. — *Rejected:* a tag pushed by hand, which is the manual step this replaces; the reference's own scheme of naming a release after the commit, which fails the questionnaire's `version_semver`; the SLSA generator, whose reusable workflow must be referenced by tag rather than by commit — it would break the rule that every action is pinned by SHA and lower Pinned-Dependencies to buy a stronger provenance format; a third-party action for creating the release, where `gh release create` with the workflow's own token adds nothing to the supply chain; signing the image that actually reaches production, which is the more useful thing and remains open — Scorecard does not look at it, and it belongs with the deployment rather than with a release. — *Where it lives:* `.github/workflows/release.yml`, `justfile`, `docs/openssf-best-practices.md`.

## Widget build

**R06. The `@modelcontextprotocol/ext-apps` package, version 2.0.0; the library is the reference, not the text of the specification.** Where the MCP Apps 2026-01-26 specification disagrees with the library — in `ui/message` and `ui/update-model-context` its `content` field is always an array of blocks, not a single object — we follow the library. — *Why:* its code is the actual runtime the hosts run; the discrepancy was found in T03 while building the widget. — *Where it lives:* T42, `web/package.json`.

## Instructions for the model

**R07. Text written for the model never relies on an exact tool name.** Claude prefixes tool names with the connector name (`MathTrail:show_widget`). The instructions describe tools by purpose and by their unprefixed name, without requiring an exact match; text shown to the child and the adult mentions no tool names at all. — *Why:* the prefix is added by the host and differs from host to host, so an instruction tied to an exact name breaks when the host changes. Found during the live run in T03. — *Where it lives:* T36; to be re-checked in ChatGPT in T63.

## Content for the model

**R08. Solver templates live in `content/solvers/`, one or two per topic.** A template is a short program following the solver contract, with marked slots for the numbers of the task, generalized from a solver already written for a reference task; the id of that reference task is in a comment. The package builder includes only the templates of the chosen topic and stays within the size budget, and the instructions call a template a sample one may depart from. — *Why:* the solver is the only programmatic guarantee that there is exactly one correct option (PRODUCT 4.3), and an error in it costs the child a whole attempt; a worked-through example of the typical enumeration removes the most common cause of `solver_error` for a weaker model. — *Rejected:* a mandatory skeleton, which would have made tasks bend towards whatever the template can do; and having no templates at all (О-43). The risk of sameness is countered by the rule rotating topics (T27) and by the duplicate check (T32). — *Where it lives:* T36a, T36.

**R09. Text drawing frames live in `content/drawings/`.** A frame is generic, carries no numbers from any particular task, and comes with a structural description of its objects and their relations; the model fills in the numbers and the labels. Every frame passes the format check at the default limits itself — otherwise it is not a frame. — *Why:* the drawing stops depending on what the model happens to remember about box-drawing characters, and the format check (О-11а) passes on the first attempt more often. — *Rejected:* drawing rules in the instructions with no ready-made frames (О-44); free-hand drawings remain allowed and are checked against the same limits. — *Where it lives:* T36b, T36; once the limits are calibrated, the frames are re-checked in T58.

**R16. The child's notes are data, never instructions.** `child.notes` is written by the parent and read by the chat's model, so it travels in the package inside a delimited block that the instructions introduce as information about the child, followed by the rule that nothing inside it changes what the task must be; `save_profile` strips control characters and anything that could close the block, and checks the 500-character cap after stripping. — *Why:* it is the only field in the product written by a person and read by a model, which is the shape of a prompt injection; found in the external review of 04-profile. — *What makes it survivable:* the rule never reads the notes, so a note cannot choose the topic or the difficulty, and the solver decides what is correct — the worst a note can do is steer the tone (О-31). — *Rejected:* dropping the field (it is what lets the model pitch a task at the child); trying to detect instructions in it by pattern. — *Where it lives:* SPEC 4.1.2, [04-profile](architecture/04-profile.md), T36, T43.

**R37. The JSON schemas are the written contract, and Go does the checking.** `content/schemas/` holds `brief.json`, `task.json` and `self_check.json`, embedded in the binary and checked at startup for being schemas at all; what a submitted task is actually measured against is Go — a strict decode that refuses a field the format does not have, plus the explicit checks of T32 and T35. The reference tasks get no schema of their own: the `Example` type and the loader in `content/` are their format. — *Why:* a schema library would have to earn a dependency, and here it would buy the weaker half of the work. The checks that matter — five options a child can tell apart, a distractor for exactly the four wrong ones, a trap from the catalog, a level the topic is taught at — are not expressible in JSON Schema, and the refusal a model is sent has to name what to fix in words it can act on (SPEC 5.9), which a schema error is not. The schemas stay because they are the one place the three formats are written down in full, and because a later consumer — a tool description, a generated document — needs them machine-readable. — *Consequence:* the schemas and the Go types can drift, and nothing but review catches it; they sit next to each other in the same package for that reason, and a format change touches both in one commit. — *Rejected:* `santhosh-tekuri/jsonschema` or `kaptinlin/jsonschema` as the single source of truth, which leaves the catalog and option checks in Go anyway and so buys two validation paths instead of one; dropping the schemas, which SPEC 4 requires to be in the binary. — *Where it lives:* `content/schemas/`, `content/`, T23, T32, T35.

## Task checks

**R10. The explanation behind a wrong option is checked deterministically, with no judgement of meaning.** Four conditions: the texts of the four distractors are pairwise distinct; a text neither equals nor is a prefix of the solution or the hint; a text is not the verbatim description of the trap from the catalog; and a text is not shorter than the minimum for its writing system (words, or characters for CJK and Thai). A rejection gets its own code and names the option that needs fixing. — *Why:* "a wrong answer is a diagnosis" is one of the three pillars of the product (PRODUCT 1), and in text mode the explanation is the main thing the child gets. — *Rejected:* instructions and reference tasks alone with no programmatic check; and any heuristic for "meaningfulness" — with a median generation time of 69 seconds, extra strictness costs the child another attempt (О-46). — *Where it lives:* T32a; the rejection code is defined in T12.

**R44. The solver's contract is a domain package and the interpreter is infrastructure.** `internal/domain/solver` holds the statuses, the five option texts, the shift that relabels them, the comparison a computed answer is looked up by, and the rule that turns two runs into one verdict; it declares a `Runner` interface of one method. `internal/infra/starlark` is what implements it. — *Why:* what two runs mean together is the whole point of the check, and it is arithmetic over two results — it can be written down, read and tested with no interpreter anywhere near it, which is what its properties do against two fakes of four lines each. It also keeps the dependency rule honest rather than aspirational: nothing under `internal/domain` may import `go.starlark.net`, and the linter says so. — *Rejected:* one package under `internal/solver`, as the line in RUN.md first said, which would have put a rule of pure arithmetic behind an embedded language and made every test of it a test of the sandbox as well; leaving the two runs to the pipeline of T35, which would give the bench of T29 no way to run a reference solver the way a submitted one is run. — *Where it lives:* `internal/domain/solver`, `internal/infra/starlark`, `.golangci.yml`, RUN.md T28.

**R45. Everything the sandbox predeclares caps itself at a million elements and charges the step budget for them.** The cap and the charge cover our own helpers and twelve built-ins of the language besides — `list`, `tuple`, `sorted`, `set`, `dict`, `reversed`, `zip`, `enumerate`, `min`, `max`, `any` and `all` are declared again with the cap on them — and the charge happens before the call does any work, so a call nothing could pay for is refused rather than half-built. The ceiling and the price are counted differently: the ceiling counts the elements of the list a solver ends up holding, and the price counts the values inside them, so a hundred thousand tuples of twenty costs two million steps rather than a hundred thousand. — *Why:* the interpreter counts its own instructions and looks for a cancellation only between them, so neither the step budget nor the clock can reach inside a single call. A lazy range is the way in: `range(1000000000)` costs nothing to make, `list` of it is sixteen gigabytes built where nothing is watching, and `min` of it is ten seconds of Go with both limits asleep. The length is known before the walk starts, which is what makes a refusal possible at all. — *Consequence:* the operators stay open. `[0] * 100000000` allocates through the language's own `*`, where there is no name to stand in front of, and starlark-go's own guard there stops only at 2³⁰ elements — more memory than an instance has — so a solver written that way takes the instance down rather than the request. There is no power operator in this dialect, which closes the other half of the same hole, and nothing else turns something small into something huge in one step. — *What would change it:* the gap ever being seen in the aggregate log; the fix is a solver in a process of its own with a memory limit on it, which is a change of shape rather than a setting. — *Rejected:* capping `range` itself, which would forbid a loop of two million iterations that the step budget pays for happily; charging a list of tuples by its length alone, which reads simpler and lets a product of nineteen pairs through — half a million tuples, ten million values and a hundred and sixty megabytes, against a ceiling that saw five hundred thousand; a memory limit in Go, which has none per goroutine — `debug.SetMemoryLimit` makes the collector work harder and refuses nothing. — *Where it lives:* `internal/infra/starlark/vocabulary.go`, SPEC 6.5 and 6.6.

**R46. A recursive solver is `error`, not `bad_source`.** The dialect keeps the recursion check on; the check belongs to the interpreter and fires when the recursive call happens, not when the file is parsed, so the status is the one for a program that failed while running. — *Why:* the alternative is to promise the parser catches something the parser does not look at. A pass over the syntax tree before the run could name the direct case, but a name in Starlark can be reassigned — the dialect allows it — so the pass would be an approximation that still does not replace the check underneath it. The model reads the same sentence either way, because every status reaches it as one refusal; the status is read by the aggregate log, and there "it failed while running" is exactly what happened. — *Rejected:* the pre-pass above; matching on the text of the library's error, which is the library's to reword. — *Where it lives:* `internal/infra/starlark/dialect.go`, SPEC 6.3 and 6.4.

**R48. A helper refuses what the solver got wrong rather than quietly mending it.** A string handed to a helper expecting a sequence is refused, and so is a date that never happened — the thirtieth of February, a thirteenth month, a year outside the four digits. Each refusal says what to write instead. — *Why:* both mendings are available and both are worse. This language does not iterate a string, so a helper that accepted one would teach a second rule that holds nowhere else in the dialect, and the model would learn the wrong one; the porting table of SPEC 6.8 carries the one line it costs instead. A month of thirteen is January of the year after, and answering about it would give a solver a confident wrong number — the one failure this whole check exists to catch. — *Rejected:* taking a string as its characters, the way Python does, for the reason above; normalising a date the way the standard library does by default, which turns a solver's bug into a plausible answer. — *Where it lives:* `internal/infra/starlark/calendar.go`, `internal/infra/starlark/vocabulary.go`, SPEC 6.5 and 6.8.

## Configuration

**R18. Viper reads the configuration, and nothing but the environment feeds it.** `internal/config` declares every variable once — name, default and type — and unmarshals it into `Config`; `Validate()` then refuses with a message that names the variable. No file, no remote source and no flag is registered. — *Why:* the author's decision, reversing the earlier "no Viper" note in CLAUDE.md. The table of SPEC 11 grows to around twenty variables as the sign-in, the limits and the solver arrive, and hand-rolled parsing grows a branch per type as it goes; Viper keeps that in one declaration and matches how the platform's other services read their configuration, so a person moving between them reads the same code. — *Rejected:* `os.Getenv` with hand-written parsing, which is what this replaced; registering a config file "for later", which would quietly break the rule that a deployment is configured by its environment alone (PRODUCT 6). — *Consequence:* an empty variable reads as unset, because Viper's `AllowEmptyEnv` stays off — the one behaviour worth knowing when a deployment sets a variable to the empty string and expects it to override a default. — *Where it lives:* `internal/config`, SPEC 11, CLAUDE.md ("Config").

**R19. gin serves the HTTP surface, and it stays in `internal/transport/http`.** The router, the handlers and the middleware follow the shape of the platform's other services: a handler is a struct with its dependencies and a constructor, a route is one line in `NewRouter`, an error answer is `apierror.Response`, and every request passes a request id, a panic recovery and a request log. — *Why:* the author's decision. The surface grows to the MCP endpoint, five OAuth endpoints and three metadata documents, each with its own middleware needs; routing groups, parameter binding and one recovery path are worth more than the standard multiplexer once that is true, and a person moving between this service and the others reads the same code. — *Consequence:* the domain packages must stay free of it — the linter denies `gin` and `net/http` inside `internal/domain`, which is the one place this service deliberately differs from the reference. An `http.Handler` from the MCP SDK mounts with `gin.WrapH`. — *Rejected:* `net/http`'s multiplexer, which is what this replaced; handlers inside domain packages, as the reference does it. — *Where it lives:* `internal/transport/http`, `.golangci.yml`.

## Limits and storage

**R15. A ceiling on failed generations, separate from the daily limit.** `daily.failed` in the profile counts requests that ended in `attempts_exhausted`, and `next_task` refuses with `limit_reached` once it reaches its ceiling — five a day by default, the number set in T52. — *Why:* О-35 deliberately makes a refusal cost nothing, which alone leaves a model that keeps failing the checks free to loop — three refusals, a new request, three more — with only a per-instance rate limit in the way (О-24). Each round costs the family a turn of a free-tier chat limit and six Drive calls; it costs us no tokens at all, since the service makes no LLM calls (PRODUCT 4.3). Found in the external review of 03-flows. — *Rejected:* charging the daily limit for refusals, which would redefine О-35 and make a bad model cost the child their lesson; leaving the loop to the rate limit alone. — *Where it lives:* SPEC 5.10, [03-flows](architecture/03-flows.md), [04-profile](architecture/04-profile.md), T43, T52.

**R17. The profile is recovered through pinned revisions, and pinning has two triggers.** A damaged file is recovered from at most five revision bodies: the four newest **plus the newest pinned one**. Pinning fires on every fiftieth write by our own `revision` counter **or** on the first write of a new day, seen from the `updated_at` already in the file. — *Why:* Drive purges unpinned revisions at a hundred, which is about a day and a half of use, so the pinned snapshot is the one guaranteed to exist — and a recovery that only looked at the last five would step straight past it after six broken writes in a row. The calendar trigger exists because a write lost in the write race takes its revision number with it, and a trigger that fires only on an exact multiple can miss. Found in the external review of 05-storage. — *Rejected:* pinning every write (200-pin ceiling, and the parent's storage quota); a deeper recovery window (more bodies fetched on a path that is already rare). — *Where it lives:* [05-storage](architecture/05-storage.md), T51.

## The cloud

**R26. Terraform owns every cloud resource, and the three things it must not hold stay out of it.** `infra/terraform/` describes the enabled APIs, the image repository with its cleanup policies, the two secrets, the runtime identity, the Cloud Run service, its public invoker binding, the domain mapping, the spend alert and the federated identity a deployment arrives as. What it does not describe: the **values** of the secrets, which are added with `gcloud` by hand; the **project, its billing and the Google OAuth client**, which exist before the first apply; and **domain ownership and DNS**, which live with the registrar. Because a revision cannot start before its secrets hold something, the first apply is two passes — the secrets, then everything else — and that order is the self-hosting page's spine. — *Why:* a state file holding the sealing key is a copy of the key in a bucket that anyone with state access can read, and the key is the one secret whose loss forges every token; a project or an OAuth client recreated by a tool takes the parents' `drive.file` grants with it, and those cannot be recovered. — *Rejected:* `google_secret_manager_secret_version` resources with the values in variables, which puts both secrets in the state; a bootstrap module creating the project and the billing link, which makes a `destroy` capable of deleting the one thing that must never be recreated. — *Where it lives:* `infra/terraform/`, [self-hosting](self-hosting.md), T20.

**R27. The custom domain is a Cloud Run domain mapping in `us-central1`, and the platform's own address is withdrawn.** The region is chosen by two constraints at once: only a handful of regions offer domain mappings at all, and the free allowance is a discount at first-tier prices. The mapping is in Terraform, and `default_uri_disabled` is a variable that is turned on as a step of its own once the domain answers — Cloud Run asks for a domain to be mapped before its own address is withdrawn, and until the certificate is issued that address is the only way to reach anything. — *Why:* PRODUCT 7 asks for our own domain and PRODUCT 6 for $0, and a domain mapping is the only thing that satisfies both — a global external Application Load Balancer bills a forwarding rule by the hour whether or not anybody visits. One entrance also means one issuer, which is what the sign-in metadata depends on. — *Consequence:* Google labels domain mappings a preview feature and says they are not production-ready, citing latency; that is accepted for v1 and recorded as О-52, to be judged on the numbers from the live runs rather than on the label. If the latency turns out to be real, the escape hatch is a load balancer and a monthly bill. — *Rejected:* a load balancer from the start, which breaks the cost requirement before a single child has used the service; serving on the `run.app` address, which PRODUCT 7 rules out. — *Where it lives:* `infra/terraform/service.tf`, [self-hosting](self-hosting.md), PRODUCT 12.2 (О-52).

**R28. gcloud is installed for x86_64 only.** Its x86_64 archive carries a Python interpreter of its own and runs straight out of the tarball; the arm archive expects to find a system Python, and this image has none. On arm the same commands are run from Google's own `google-cloud-cli` image. Terraform, being one static binary, is installed on both. — *Why:* the alternative is a distro Python from `apt`, which would be the only unpinned thing in an image where everything else is an exact version, and an exact `apt` pin breaks on the day Ubuntu supersedes the package. Running a tool from a pinned container image is what this repository already does for everything that is not Go. — *Where it lives:* `.devcontainer/Dockerfile`, [self-hosting](self-hosting.md).

**R29. The deployment owns which image is served; the configuration owns everything around it.** `google_cloud_run_v2_service` ignores changes to `template[0].containers[0].image`, so the `image` variable is only what a newly created service starts with — the placeholder that lets a fresh project apply cleanly — and after that a deployment rolls revisions with `gcloud run services update --image <digest>`. — *Why:* two owners and no rule between them is drift by construction: a deployment publishes a digest and the next `terraform apply` puts the placeholder back. Of the two ways to settle it, this one keeps the deployment identity as narrow as T20 made it; the other — a pipeline running `terraform apply -var image=…` — would hand a workflow the state bucket and the right to change every resource in the project in order to move one string. — *Consequence:* the digest that is live is not recorded in the state, so "what is deployed" is a question for Cloud Run (`gcloud run services describe`), and a rollback is a revision — `gcloud run services update-traffic --to-revisions=…`, or the deployment run again at an older commit — never a `terraform apply`. — *Rejected:* Terraform applying from a workflow; leaving the field unignored and hoping the two owners agree. — *Where it lives:* `infra/terraform/service.tf`, `.github/workflows/deploy.yml`, T21.

**R30. A deployment is configured by repository variables, one per Terraform output, and holds no secret at all.** *(The variables half is superseded by R33: the configuration moved into the repository, and the only repository setting left is one secret. What stands is the rest — the triggers, and the federated token as the only credential.)* Six variables carry the target — the identity provider, the deployment identity, the image repository, the service, its region and the public address — and each is a copy of one output of the configuration that created it. The only credential is the federated token the workflow mints for itself; there is no service account key anywhere, and nothing in the repository or in its settings is secret. A deployment starts on a push to `main`, which is what a merged pull request produces, or by hand, and then it deploys whatever branch it was started from. — *Why:* variables rather than secrets, because none of these values is one and pretending otherwise makes them harder to read when a deployment misbehaves; one variable per output, because then the question "where did this value come from" has one answer. Pushes to `main` are the trigger because the checks gate the pull request that produced them, and running the same checks again in the deployment would double every merge for a verdict already given. — *Consequence:* a commit pushed straight to `main`, past a pull request, is deployed without the checks having finished — so the branch is protected, and the previous revision is one command away. — *Where it lives:* `.github/workflows/deploy.yml`, [self-hosting](self-hosting.md), T21.

**R32. The cloud is delivered by the pipeline, and what the pipeline signs in through is not the pipeline's to create.** `terraform apply` runs on every push to `main` and on a manual run from any branch; a pull request that touches `infra/` gets a `plan` in its summary. What stays outside is `infra/bootstrap.sh`, run once by a person: the project and its billing, the bucket the state lives in, the federated pool with its GitHub provider, and the identity Terraform is applied as. The two secret values are seeded by the apply itself and only when they are empty — the sealing key is 32 bytes generated in the job, the Google client secret comes from the one repository secret. — *Why:* the author's decision: deployments are not done by hand. Everything Google exposes through an API therefore belongs to the pipeline, and what is left by hand is left for a reason that can be named — no API exists (the consent screen and the OAuth client), the record lives at a registrar (DNS), or it is the door the pipeline walks in by. A sealing key generated inside the job is also simply better than one pasted through a form: nobody has to be trusted with a value nobody ever sees. — *Consequence:* an apply on every merge means a change made by hand in the console is undone, silently, by the next merge; that is the intent, and it is worth knowing before somebody edits a service in the console. The identity that applies the configuration is broad within its one project — an enumerated set of roles, not Owner — and holds no key at all: only a federated token from this repository, under a condition naming the owner's numeric id. It is deliberately not the identity that rolls out images; the narrow one from R29 stays as it was. — *Rejected:* a service account key in a repository secret, which would let a workflow bootstrap itself at the price of the one thing this design does not have; Cloud DNS, so that the records could be Terraform's too, because a managed zone is billed monthly and $0 is a requirement; `terraform apply` from a laptop, which is what this replaced and which survives as the documented path for when the pipeline is unavailable. — *Where it lives:* `infra/bootstrap.sh`, `.github/workflows/deploy.yml`, `justfile`, [self-hosting](self-hosting.md), T22.

**R33. The deployment's configuration lives in the repository.** `infra/terraform/prod.auto.tfvars` (project, region, host, client id, repository and owner id, pool id), `infra/terraform/backend.hcl` (the state bucket) and `infra/ci.env` (the provider and the identity a workflow needs before it can sign in) are committed. There are no repository variables, and there are two repository secrets: the OAuth client's secret and the id of the billing account. The billing account is the one deployment fact deliberately kept out of the files — it is not a credential, and no API accepts it without IAM, but it names the account that pays and this repository is public, so it arrives from the environment as `TF_VAR_billing_account`, which Terraform reads by itself. — *Why:* changing where this service deploys is then a pull request with a diff and a reviewer, rather than a field in a settings page whose history nobody can read. None of the values is a secret — a client id travels in every authorization request, and the pool is guarded by its condition rather than by the obscurity of its name — and the REST API that would have written repository variables needs a personal access token with `repo` scope, a credential worth more than the values it would set. — *Consequence:* a public repository states which project, project number and host this deploys to; that is accepted. A fork edits three files and runs the bootstrap, and needs nothing else. — *Where it lives:* `infra/terraform/prod.auto.tfvars`, `infra/terraform/backend.hcl`, `infra/ci.env`, `.gitignore`, T22.

**R34. The liveness probe answers on `/health`, and never on `/healthz`.** The frontend that sits in front of a Cloud Run service answers the literal path `/healthz` itself, with its own HTML page, and the request never reaches the container. Measured on the first delivery, against a service that was in fact healthy: `/healthz` was intercepted on both the platform's own address and the mapped domain, while `/health`, `/healthzz`, `/healthz/`, `/livez` and `/readyz` all arrived and were answered by our router. The deployment check asks for `/health`. — *Why:* the failure it caused is the expensive kind — a green service, a red delivery, and a probe that cannot be reached from anywhere outside. It cost an afternoon to find because everything else was working, and the difference between the two paths is one letter. — *Consequence:* the path appears in the endpoint tables, in the deployment check and in the container's own comment, which says why it is not the conventional name; a copy of this service running anywhere else is unaffected, because `/health` is reserved nowhere. — *Rejected:* `/livez` or `/readyz`, which arrive today but belong to the same family of names the platform helps itself to; `/healthz/` with its trailing slash, which our router redirects and which therefore works by accident rather than by design. — *Where it lives:* `internal/transport/http/router.go`, `justfile`, SPEC 9.1, T22.

**R35. A finding from the static analysis is answered by changing the code; accepting one is the last resort and carries a written reason.** The first full sweep of the 27 findings on the new code is what set the rule, and what it changed is worth listing, because most of it was not a considered position but a line nobody had reread: every download now refuses a protocol downgrade, on itself and on redirects; the development image is installed from a registry at an exact version rather than by running an installer script off the network, and no longer defaults to root; the deployment identity holds a role of five permissions instead of a ready-made one of sixty, which had included deleting the service and opening a root shell inside a running container; the site's footer navigation is named for a screen reader; and two shell scripts name their parameters. One finding stayed and is marked in place: the `"http://"` in the site check is the string that check searches for, and removing it removes the check. A second pass merged the two remaining adjacent `RUN` instructions and stopped there, because both other findings turned out to cost more than they were worth, and the cost was measured rather than assumed. Installing the editor's Go tools the way the rule wants means a second Go module in the repository with a `go.sum` of its own to keep current, for versions that are already exact and already verified against the Go checksum database; it was written, read, and taken back out. Forbidding every npm install step means the Claude Code CLI loses the native binary that step puts in place and starts through a Node wrapper instead, every time it runs. Both are marked, and those are the reasons. — *Why:* a mark makes the number go down and leaves the reason where it was, and this sweep found that the reasons were mostly real. The one exception is what a mark is for: an analyser that cannot tell a protocol from a search term. — *Consequence:* the identity that applies the configuration gained the right to write roles, because the configuration now defines one; a deployment that never had to delete a service can no longer do so, and if some later step turns out to need a permission the five do not cover, it fails in the delivery and the list grows by one. — *Where it lives:* `.devcontainer/Dockerfile`, `infra/terraform/deploy.tf`, `infra/bootstrap.sh`, `site/templates/page.html`, `internal/site/check/check.go`.

**R36. The environment asks nothing of the host beyond Docker itself, and that is a rule, not a convenience.** Whoever opens this repository installs Docker and VS Code and reopens in the container; no builder plugin, no daemon configuration, nothing edited as root. Two things follow. The image is written for any builder — no `RUN --mount`, no heredocs — so build caches are what the builder happens to offer rather than something the file depends on. And the network the container runs on is created before it starts, by `.devcontainer/host-network.sh` through `initializeCommand`, carrying the MTU of the host's own default route; `post-start` mirrors that value onto the docker running inside the container, which would otherwise hand its own networks 1500 again. — *Why:* a tunnel on the host — a VPN, in practice — makes the real limit smaller than the 1500 Docker assumes, and then a container's large downloads stop after a few kilobytes while small requests answer normally; nothing in the error names the network, and the hours go into the Dockerfile instead. The first fix written for it was a daemon setting applied by hand on one machine, which is exactly the kind of instruction this project does not get to give. Detecting the host's MTU and building the container's network with it costs twenty lines and holds for anyone, not just the machine it was debugged on. — *Consequence:* the container runs on a named network rather than the default bridge, and that network is created on every start — a host without `bash`, such as Windows outside WSL, cannot run the script and needs the network made by hand. A host whose tunnel appears or disappears keeps the MTU the network was built with: the script says so and names the one command that clears it, because a network in use cannot be changed from under a running container. Downloads inside the image go through one helper with `--retry-all-errors`, because the failure this was all written for — a transfer that dies partway — is not one a plain `--retry` repeats. — *Rejected:* cache mounts and the BuildKit-only syntax they need, which bought faster rebuilds at the price of a plugin the host had to have; telling each person to set `default-network-opts` in their daemon, which is the same fix written as a chore. — *Where it lives:* `.devcontainer/host-network.sh`, `.devcontainer/devcontainer.json`, `.devcontainer/post-start.sh`, `.devcontainer/Dockerfile`.

**R49. Traces and metrics go straight to the platform's standard endpoint, and a request pays for its own delivery.** `internal/telemetry` builds a tracer provider and a meter provider on every start, and attaches OTLP-over-HTTP exporters to them only where there is somewhere to send: `https://telemetry.googleapis.com`, signed with the credentials the platform issues, naming the project in a `gcp.project_id` resource attribute and in the `X-Goog-User-Project` header. The sampler is `ParentBased(TraceIDRatioBased(0.1))`; a sampled request delivers its spans before it finishes, with a deadline of 200 ms, and measurements ride the same delivery at most once a minute, as deltas. Off a deployment the switch is off and the providers drop everything, so no credential is needed to run the tests or the server. — *Why:* four numbers decide the shape. Google's own Go exporters (`exporter/trace` v1.38.0, `exporter/metric` v0.62.0) are deprecated and will be archived after 1 January 2027, and they post to this same endpoint, so taking them buys nothing and costs a migration. A sidecar collector wants 0.25–0.5 vCPU and 256–512 MB on every instance against 180 000 vCPU-seconds of free allowance, which is the whole budget spent on carrying telemetry rather than on answering children. `cpu_idle = true` means the processor is taken away once a response has been returned, so a batch left in memory after that is a batch that may never leave — hence a delivery inside the request. And the free allowances are what the labels are for: the platform's own system metrics and automatic traces are not billed at all, Logging gives 50 GiB a month, Trace 2.5 million spans, and custom metrics 150 MiB — a label carrying a user or a task identifier passes that last one in a week, so every label is a closed dictionary and every histogram's buckets are written out. — *Consequence:* the resource is built with `contrib/detectors/gcp`, which adds two Apache-2.0 modules and one call to the platform's metadata service at startup, and is what makes the instance identifier in a span the same one the console shows. HTTP rather than gRPC as the transport, because the credentials then attach as an ordinary `http.Client` and the collector a test posts to is an ordinary `httptest` server; it saves nothing in the binary, because the exporter's own configuration package imports gRPC whichever transport is chosen. Exporting at all costs this build 186 packages and 19 MB — 24.8 MB to 43.5 MB, measured — and that is the price of OTLP in Go rather than of anything decided here. It is also a standing maintenance cost: the image scan reads the modules linked into the binary rather than the code that runs, so a gRPC advisory now fails the build of a service that serves no gRPC, and the answer each time is to raise the version. The delivery carries its own 200 ms rather than trusting whoever asked for it to remember one, so a caller that brought no deadline still gets its goroutine back, and it is detached from the request, because a caller who hung up would otherwise take the spans with them. That deadline costs what it saves: a delivery that misses it loses its batch, since the SDK discards a batch that failed to send rather than holding it for the next attempt, and the first delivery from a new instance — the one paying for the connection — is the likeliest to miss. Accepted, because the alternative is a child waiting on a collector; the number is revisited against the latencies of T64 rather than against a guess. and the one setting that belongs to the whole binary — the handler that reports a failed delivery — is installed at the composition root beside the web framework's mode, never by the constructor, because a constructor that reaches for a global changes what every other part of the same process reports. Neither a missing project nor missing credentials stops the service: both are reported once and leave export switched off, because an image can be rolled before the configuration that names the project reaches it, and a service that refused to start over telemetry would be an outage caused by observability. Granting the runtime identity `roles/telemetry.writer` and `roles/serviceusage.serviceUsageConsumer` is the first binding this configuration makes on the project itself, so the identity Terraform is applied as gained `roles/resourcemanager.projectIamAdmin` in `infra/bootstrap.sh` — an existing project needs that grant re-run once before the first apply that carries this. — *Still open:* from 1 September 2026 Cloud Monitoring charges $0.35 a month for every metric named in an alerting policy. The spend alert of T20 is a Billing budget and is free of this; whether any of our own metrics is worth alerting on is a decision for T64. — *Rejected:* Google's own exporters, above; a sidecar collector, above; the Google Cloud Trace agent's `X-Cloud-Trace-Context` alone, which would tie the service to one platform's header instead of the standard one; relying on the periodic reader by itself, which under `cpu_idle` fires only when a request happens to wake the instance. — *Where it lives:* `internal/telemetry`, `internal/config`, `internal/app/container.go`, `infra/terraform/apis.tf`, `infra/terraform/service.tf`, `infra/bootstrap.sh`, SPEC 11.2 and 12.5.

## The public site

**R23. The site is built by a small Go program, and all of it is temporary.** `cmd/sitegen` builds `site/` into `site/dist/` with `html/template` and goldmark; `cmd/sitecheck` then judges the finished directory. Both are replaced by the widget's own Preact and Vite toolchain once that exists — the renderer first, the checker one task later, for the reason in R25. — *Why:* the privacy policy has to be live before the first deployment, because Google will not release the consent screen without it, and `web/` does not exist yet at that point. Reaching for npm here would either block the policy behind the widget build or introduce a second, throwaway JavaScript toolchain. Go is already pinned, already in the image, and already the language the tests are written in. — *Rejected:* hand-written HTML per page and per locale, which duplicates the masthead, the footer and the language switcher into every file and drifts by the third locale; a static site generator, which is a new toolchain and a new license to track for six pages. — *Consequence:* goldmark and a direct `golang.org/x/net` sit in `go.mod` for programs the service does not ship, and both leave with the programs that needed them. — *Where it lives:* `internal/site/`, `cmd/sitegen`, `cmd/sitecheck`, T19, T66, T66c.

**R24. The address scheme is decided once and never moved.** Every page lives at `/<locale>/` or `/<locale>/<page>/`; the apex is a page in its own right — the product's name, its one line and the languages it exists in — rather than a redirect. hreflang x-default points at the apex for a front page and at the reference locale for anything else. — *Why:* the addresses of the privacy policy and the terms are handed to Google for the consent screen and to the directories for the listing, and neither forgives a link that moved. The apex is what a product is listed under, and a redirect is a poor thing to list; Google also expects the policy to sit on the domain that hosts the home page, which the scheme satisfies by construction. — *Consequence:* T66 may replace the renderer but not the addresses, and `sitecheck` fails the build if a page that was published disappears. The authorized domain registered in T22 is the top private domain, which covers both the site on the apex and the service on its subdomain. — *Where it lives:* `internal/site/render`, `internal/site/check`, T19, T22, T66.

**R25. The checker outlives the renderer by exactly one task, and then the site owns no Go at all.** T66 replaces the renderer and keeps `cmd/sitecheck` untouched; T66c ports the five rules to TypeScript under `web/tools/sitecheck/` and deletes `internal/site/` and `cmd/sitecheck`. The ported checker takes a directory and nothing else, and a lint rule forbids it to import from `web/src/**`. — *Why:* the author's decision that no Go about the site survives the project. Doing it in two steps is not caution: while the renderer moves, the old checker is the only judge that has no stake in the new builder, so "the Vite output still passes the unchanged checker" is real evidence rather than a build agreeing with itself. The same reasoning is what the lint rule protects afterwards — a checker that imports the builder's `hreflang` tests that a function equals itself, and in one language that import is one keystroke away. — *Rejected:* keeping the Go checker for good, which leaves a second toolchain in the repository for one program; off-the-shelf npm checkers, which cover dead links and markup validity but not the three rules that matter most to a site in twenty-two languages — no third-party loads, a complete hreflang matrix, and no locale quietly missing a page; moving both at once, which would leave a disagreement with no arbiter. — *Consequence:* after T66 the site is no longer covered by `just ci-test`, and `just ci-site` — already on every pull request — becomes its only gate. The design tokens stay a plain CSS file rather than a bundle artefact, because the consent screen and the sign-in error pages are rendered by the service itself and read the same file (SPEC 8.9). — *Where it lives:* `web/tools/sitecheck/`, T48, T66, T66c.

## The boundaries of v1

**R14. There are no printable task sheets in v1.** There will be no tool that hands the adult 3–5 checked tasks as a single text. — *Why:* the profile stores fingerprints of past tasks, not their texts (О-40), so a sheet could only be assembled from tasks generated on the spot: 3–5 generations in a row, which is the message limit of a free tier, a daily-limit calculation of its own, and in effect a return to the cancelled task buffer (О-6). — *Where it lives:* PRODUCT 2 ("not included"); no separate task is added in phase 7 (О-47).
