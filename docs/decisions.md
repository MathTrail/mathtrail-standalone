## Protocol and SDK

**R01. Go SDK — v1.8.0.** PRODUCT 7 named v1.7.0; as of 2026-09-16 the current release is v1.8.0 (14.09.2026), a patch release with no protocol changes: the same set of supported versions, with 2026-07-28 still the newest. It adds limits on SSE event size, body size and JSON depth, the `ServerOptions.SupportedProtocolVersions` setting, and an explicit `-32022` code in place of a bare 400. Spike T03 was built and verified on it. — *Why:* strictly newer and fully compatible; there is no reason to stay on the previous patch. — *Where it lives:* `go.mod` (T17), PRODUCT 7.

**R02. The server does not narrow the set of protocol versions.** *(A request that names no version is read by the library as one of 2025-03-26, which takes a batch of messages; R126 refuses a batch before the library reads it.)* We work only over 2026-07-28 (О-20, О-28), but `SupportedProtocolVersions` is left at its default: the SDK already prefers the newest version when negotiating. — *Why:* in strict mode Claude fails to add the connector. Before the main session the host sends two short legacy `initialize` requests with an empty version, and rejecting them by version breaks the "Connect" step (status 400); in the default mode the same runs go entirely over 2026-07-28 — not one real request negotiated an older version. — *Rejected:* a strict "2026-07-28 only" transport; a stateless 2025-11-25 fallback path (О-28). — *Where it lives:* T41; to be re-checked in ChatGPT in T63.

**R83. Every tool call is observed once, at the protocol boundary, and a failure reaches the model as one sentence of ours.** The MCP package wraps every method the protocol library dispatches in a middleware of its own, the boundary. There a tool call gets a span, `tools/call <tool>`, of the server kind and a child of the request's span; it is timed; and it is written in one `tool_call` line, however it ended — answered, refused with a `status` at the top of its payload, failed, or refused by the protocol before any tool ran. The frame that `Define` builds around every tool turns any error into a failure: one English sentence from one table, which becomes the error's text, because the library sends an error's text to the model as it stands. A panic anywhere below the boundary is caught there — in any method, and in the boundary's own work around a call — and answered as an internal error. In a tool call, an error of the library that is not a protocol error, such as a payload that breaks its own output schema, becomes the general failure. A protocol error goes out as the protocol's own, in its own words rather than in those of whatever wrapped it, and the one the protocol has for a fault on this side, an internal error, counts as a failure of ours. A tool whose name the protocol would refuse, or whose input or output the library cannot derive a schema from, refuses to be built rather than being dropped or crashing the start. A request that is not a tool call is passed on as it is, together with the library's answer: its errors describe the request in the protocol's terms, such as a pagination cursor that does not decode, and a client's own mistake is not an internal error of ours. — *Why:* much of what happens to a call happens where no tool runs. The library refuses arguments that do not fit and a tool nobody defined, and fails on a payload after the tool has returned. It also runs handlers on goroutines of its own, which the HTTP layer's recovery does not reach, so an uncaught panic there ends the process. A frame inside the tool alone would miss all of that. The span's parent is the request's, not the trace context a client may put in `_meta` as the OpenTelemetry conventions for MCP suggest: one request is one tree, as the task asks, and a client does not choose what is kept (R49). A refusal is read from the result's own `status` — the field that makes it a refusal for the model and the widget — rather than reported a second time by the tool. By R73's rule for what a caller chose, the client is written as the chat host it belongs to — a word read out of its name, never the name itself — and the protocol version is held to the library's list. The library's own logging is off, since its lines are held to no list of fields. The request's cancellation is not passed to the tool: a recorded answer must not be abandoned because the host hung up, and the tool's own outbound calls carry their own deadlines. — *Consequence:* the text of an argument refusal is the library's, and it reaches the model (SPEC remark 36). The request's line has no `user`, while the call's line has it (SPEC 12.1). The library sets `no-cache, no-transform` on every answer, and the endpoint rewrites it to `no-store, no-transform` as the headers leave (the author's decision; SPEC 9.2). A handler of ours for a method that is not a tool call — the widget's resource, in T42 — answers in the protocol's own errors, because the boundary passes such an answer on as it is. — *Rejected:* observing inside `Define` alone, for the reasons above. Turning every error of a method that is not a tool call into an internal error, which the first review of T41 showed to be wrong: a client's malformed cursor became an internal error and an error line, and any client could fill the log with them. Letting a tool return an error for the library to phrase, which would put `err.Error()` in front of the model. Reading a refusal from a field the tool reports beside its payload, which would say the same thing twice. — *Where it lives:* `internal/transport/mcp/boundary.go`, `failure.go`, `tool.go`, `labels.go`, `nostore.go`, SPEC 7.4, 12.2, 12.5.

## Sign-in and permissions

**R03. Client registration is CIMD, with DCR kept as a fallback.** The authorization server metadata declares `client_id_metadata_document_supported: true`, and the server fetches the document itself over an HTTPS `client_id`; `/register` (RFC 7591) is still supported for backwards compatibility. — *Why:* as of 2026-07-28 DCR is formally deprecated, and Claude showed up live with CIMD (`client_id: https://claude.ai/oauth/mcp-oauth-client-metadata`) without ever falling back to DCR; the ChatGPT documentation also recommends CIMD, though that has not been verified live. — *Where it lives:* T07, T47–T49.

**R04. Insufficient permissions on a tool return HTTP 403 with a `WWW-Authenticate` header.** The `_meta["mcp/www_authenticate"]` field in the call result is sent in addition, for ChatGPT's sake, but it cannot be the only mechanism. — *Why:* the live run in T04: on a 403 Claude went to `/authorize` for the wider scope and retried the failed call by itself, with no human involved; a tool that answered only through `_meta` looked to it like an ordinary error. — *Consequence:* the model never sees the step-up — in its context there is a single successful call — so its account of the authorization state is unreliable and only the server log can be trusted. The same rule applies to every acceptance run. — *Where it lives:* T47–T49.

**R82. The MCP endpoint stands behind a sign-in from the start: one development account on a developer's machine, nobody on a deployment until the real sign-in.** *(Since R123 a bearer credential that is a name signs a request in as an account of that name.)* `mcpserver.NewHandler` refuses to be built without a `SignIn`, the function that decides whose account a request acts for. There are two. `DevSignIn`, switched on by `MATHTRAIL_DEV_AUTH`, lets every request in as the account `dev`, with a credential or without one. `NobodySignsIn` is the SDK's own `auth.RequireBearerToken` with a verifier that refuses every token, so every request is answered `401` with `WWW-Authenticate: Bearer scope="mcp"`. The signed-in account travels from the sign-in to the tool in the request's context, under a key of the MCP package, and from the tool's frame onwards as an argument. — *Why:* the author's decision. A deployed service must not serve tools to nobody in particular, and until the real sign-in (T49) it can issue no token. So it refuses everything, in exactly the shape in which it will later refuse a missing token. The account does not ride in the SDK's `TokenInfo`, the SDK's own carrier. Only `RequireBearerToken` can put one there, and it demands an `Authorization` header. A custom connector in Claude sends none without OAuth, so a live check through a tunnel with the development sign-in would get `401` on every call. — *Consequence:* the live check of the widget moves from the deployed service to a developer's machine behind a tunnel — in T43, where the first tool that draws a card arrives, since T42 has none to draw one with (the author's decision) — and the deployment's smoke check asks for the `401`. T49 replaces `NobodySignsIn` in the container with `RequireBearerToken` and its real verifier, plus a step that turns the verified `TokenInfo` into the account. A verifier error that wraps neither `auth.ErrInvalidToken` nor `auth.ErrOAuth` is answered `500` with its text as the body, so its errors must wrap one of the two. R80 kept the credential out of the context for the store. Here the context carries the account only across the one gap that has no argument to carry it — from the HTTP layer into the protocol library — and the store still takes the account as an argument. — *Rejected:* an open endpoint whose tools refuse a request without an account, which would answer the protocol's methods from a deployment to anybody. And the development sign-in as a stub verifier behind `RequireBearerToken`, which needs the header above. — *Where it lives:* `internal/transport/mcp/signin.go`, `internal/app/container.go`, `justfile` (`run`, `ci-smoke`), SPEC 9.4.

**R41. `seal` hands out a key ring, not an interface.** `seal.NewKeyRing` returns the concrete `*seal.KeyRing`, against the convention that a constructor returns the interface its package offers. — *Why:* there is one way to seal a value and there will be one; the package is pure computation with no I/O, so a caller under test runs the real sealer and gets a real ciphertext, which is a better test than a fake that returns a fixed string. The convention exists so that mockery always has something to generate from, and here there is nothing worth faking. — *Consequence:* the configuration checks the two keys by building a ring and dropping it, and the container builds the same ring again at start. That is two derivations of a few subkeys once per process, and it keeps the rule for a key in one place — the ring — while the configuration is the one that can name the variable a refusal is about. — *Rejected:* an interface with a single implementation, which would be a name for the same thing and one more file of generated mocks nobody calls; a lighter check of the keys beside the ring, which would be a second rule for what a key is. — *Where it lives:* `internal/infra/seal`, `internal/config/config.go`, CLAUDE.md ("Interfaces").

**R42. The domain asks the catalogs for what it needs, and the content answers.** *(Its "the grade crosses that line and the level does not" is reversed by R79: a level is part of the ladder the ratings run on, so `rating` defines the levels, and `tutor.Catalog` asks which levels a topic is taught at and the traps of a topic at a level. The rest stands.)* A domain package that needs the catalogs declares an interface of its own — `tutor.Catalog` is the first, with three methods that speak in identifiers — and `*content.Content` satisfies it by gaining the matching accessors. No domain package imports `content`. — *Why:* the dependency rule of CLAUDE.md, applied to a package that is data rather than infrastructure: the rule of section 3 needs three facts about the catalogs and nothing else, and saying so in three method signatures is both the smallest contract and the honest one. It also buys a test: the rule's own cases are written against a catalog of three topics and four traps, which states what is being tested, where the four hundred and fifty reference tasks of the binary would only obscure it. The grade crosses that line and the level does not — the domain knows what school year a child is in, and what years are grouped into stays with the catalogs. — *Rejected:* importing `content` from the domain, which is simpler by one interface and would have made every rule test depend on the shipped content; an adapter type in between, which would be a name for the same three methods. — *Where it lives:* `internal/domain/tutor`, `content`, and the same shape is what T32, T35 and T36 use when they need the catalogs.

**R43. The tool for mocks is kept and the mocks are not written.** mockery v3 is pinned, configured and checked by CI, and `.mockery.yaml` lists no packages: an interface is tested against the real implementation where that implementation does no I/O, and against a hand-written fake of a few lines where a test has to force an outcome. — *Why:* the two interfaces the service has are pure computation, and for both a mock would prove less. `profile.Sealer` exists so that a sealed task is tied to one child and one task and refuses to open anywhere else; a mock returning a fixed string cannot show that, while the real key ring is six lines to build and shows it exactly. `tutor.Catalog` exists so the rule can be run against a catalog of three topics written out in the test, which states what the test assumes in one place — as expectations on a mock, the same assumption is scattered across every case and has to be reassembled by the reader. — *Rejected:* generating mocks for those two now, which would weaken both sets of tests; removing mockery along with its recipes and its CI job, which would have to be put back the first time an interface earns one. — *Consequence:* the CI job runs against an empty config and says so in a second; the recipes notice `packages: {}` themselves. — *What would change it:* the first interface whose real implementation reaches outside this process, and that is the storage. The profile lives in the parent's Drive (T50, T51), so `store.Storage` is the first interface here whose real half needs a network, a token and somebody else's service to answer. Two things about it do not change: its implementations are still held to one contract test set, and the Drive one still runs against `httptest`, because that is what shows the two are interchangeable and a mock shows nothing of the sort. What changes is the tools above it — a test of what a tool does when a write lost the revision race, when the file was deleted, or when the parent took the grant back has to make that happen rather than wait for it, and `EXPECT().Save(...).Return(store.ErrConflict)` says which case it is in one line where a hand-written fake grows a flag per outcome and a fake Drive has to speak Google's error bodies. That is when `.mockery.yaml` gains its first package and the committed mocks start being checked. — *Where it lives:* CLAUDE.md ("Tests"), `.mockery.yaml`, `justfile`, `.github/workflows/ci.yml`.

**R104. The authorization server lives in `internal/transport/oauth`, and the fetch of a client's document in `internal/infra/cimd`.** The authorization server is a transport of its own beside the MCP server: its metadata, its registration endpoint and the reading of a client identifier now, and authorize, consent, callback, token and revoke with T48 and T49. The one request the service makes to an address a stranger chose — a client's metadata document — is an infrastructure package, as Drive and the sandbox are. The router in `internal/transport/http` mounts the server's handlers the way it mounts the MCP endpoint, and `transport/oauth` calls `infra/cimd` and `infra/seal` directly. — *Why:* the author's decision. CLAUDE.md put the OAuth endpoints in `internal/transport/http`, RUN.md named a package `internal/oauth`, and note 1 of 01-context left the choice to whichever task came first. The router's package is the whole HTTP surface in one function; five endpoints of a sign-in beside it would give it a second reason to change. A fetch that has to hold off SSRF is infrastructure with rules of its own, tested against a fake server of its own, and it would be lost among handlers. Nothing sits between an OAuth endpoint and the seal or the fetch that is not the endpoint's own logic, so an interface in between would only forward calls. — *Rejected:* one package `internal/oauth` for all of it, which mixes the network fetch with the handlers; the handlers inside `internal/transport/http`. — *Consequence:* `transport/oauth` is the first transport package that imports `infra`. The layout in CLAUDE.md names both packages. — *Where it lives:* `internal/transport/oauth/`, `internal/infra/cimd/`, `internal/transport/http/router.go`, `internal/app/container.go`; CLAUDE.md (Layout); `docs/architecture/01-context.md` note 1; RUN.md (T47).

**R105. A client's document is fetched as narrowly as it can be, and kept only when it is one.** *(Narrowed by R126: port 443 alone, the first four addresses of a name dialled, the lookup, the dials and the connection itself ended with the attempt, and at most 32 redirect URIs.)* The client identifier has to be an HTTPS address with a host and a path of its own, with no credentials, no fragment and no dot segment, before anything is resolved. The name is resolved by the service, and it is refused whole when any address it stands for is not public: loopback, private, link-local with the metadata server, unique-local, multicast, unspecified, reserved, carrier NAT, or a way into IPv4 from IPv6. The addresses that were checked are the ones dialled, never the name again, each in an equal share of the attempt's time, with no proxy and no connection kept once the document is read. No redirect is followed, only a `200` is read, and only to 64 KB. An attempt has 10 s, and one more follows a network error, a timeout or a `5xx`, never anything that would fail the same way again. A document is a client's when its `client_id` is the address exactly, it names the client and lists where to send the parent back, and it carries no shared secret. Only such a document is kept in memory: for its own `max-age` less the `Age` a cache on the way gives it, never under 5 minutes nor over 24 hours, and at most 256 of them. Of the redirect URIs a document lists, the ones no sign-in may use are dropped rather than failing the document. — *Why:* it is the one request made to an address a stranger chose. A name that points one record at a public server and another at the metadata server is a private name. Dialling the checked address is what makes a second lookup unable to rebind it. The HTTP client lets a dial outlive its request, so no deadline reaches a dial on its own: without a share each, an address that swallows every packet — a broken IPv6 route — would take the whole attempt and leave a working one untried. A connection to a host a stranger chose, kept for a fetch that will not come, only holds a socket. The retry is the spike's: the first name lookup a fresh process makes can outlast an attempt. The rules of the document are the CIMD draft's own, and it forbids keeping a failure or an invalid document. A document that serves a mobile app beside the web lists a custom scheme no sign-in here can use; dropping that one lets the web sign in, and it could never be matched anyway. — *Rejected:* an allow-list of client domains, which any new host would first have to get onto — the consent screen is the human check (02-auth); following a redirect to an address checked in turn, since the document has to be at the address the client is; accepting a name when one of its addresses is public; keeping failures; refusing a whole document over one redirect URI it cannot use. — *Consequence:* a fetch ends in one of eight outcomes, which the `cimd_fetch` line names; a native client whose document lists only a custom scheme cannot sign in, as the MCP specification wants. — *Where it lives:* `internal/infra/cimd/`; `internal/transport/oauth/clients.go` and `redirect.go`; SPEC 9.3 and 12.2.

**R106. Registration keeps nothing and registers public clients only, and the server's metadata is written by the service.** A registration (RFC 7591) is sealed under the purpose `client`, bound to the issuer, and handed back as the `client_id`; nothing else is kept anywhere. It takes JSON of at most 64 KB, one to five redirect URIs a sign-in may use, and a name of at most 100 characters. Whatever the client asks for, it is registered as a public client for the code and refresh grants and answered `201`, saying so; a refusal is `invalid_redirect_uri` or `invalid_client_metadata`, `413` past the size. The authorization server's metadata is a type of the service's own, with no `jwks_uri`; the resource's metadata is the protocol library's handler with an hour's cache on it, served under the resource's own path and not at the root. A `redirect_uri` matches a registered one byte for byte. The refusal of `/mcp` names the resource's metadata. — *Why:* RFC 7591 lets a server register other values than the ones asked for, and this server has one kind of client, so saying which it registered lets more clients connect than refusing would. Binding to the issuer keeps an identifier from opening anywhere but where it was issued. The bounds keep an identifier short, since it rides in every authorization request's URL. The library's `oauthex.AuthServerMeta` writes `"jwks_uri": ""` (note 6 of 02-auth). The MCP specification asks for exact matching. RFC 9728 has the document at the root describe the host, which is not the resource: a strict client, the protocol library's own among them, refuses the resource's document there, and the MCP specification asks a server for the challenge or one well-known address, which it has. — *Rejected:* the same document at the root as well, as SPEC 9.1 first had it (the author's decision); refusing a registration that asks for a secret; the library's type for the server's metadata; accepting any port on a loopback redirect URI, which RFC 8252 asks for and the MCP specification does not (SPEC remark 49). — *Consequence:* the protocol library's own client registers here and reads both documents, which is what the tests use as a host. R82's refusal now names the resource's metadata, and the smoke check after a delivery asks for it and for the document it names. — *Where it lives:* `internal/transport/oauth/` (`register.go`, `metadata.go`, `clients.go`, `redirect.go`), `internal/transport/mcp/signin.go`, the `ci-smoke` recipe; SPEC 9.3, 9.4 and remarks 47–50; `docs/architecture/02-auth.md`.

**R107. Google's sign-in is a package of its own, and an ID token counts only with Google's signature.** `internal/infra/googleauth` sends the parent to Google and trades Google's code for the grant: `golang.org/x/oauth2` builds the address — `openid` and `drive.file`, `access_type=offline`, `prompt=consent`, PKCE S256, a `nonce`, the sealed request as the `state` — and exchanges the code with the client secret in the body, within 10 s; `github.com/coreos/go-oidc/v3` checks the ID token that comes with the grant against Google's published keys, RS256, the issuer, our client as the audience, the expiry with a minute of skew, and the package holds the nonce to the request's and asks for a `sub`. The keys are kept and fetched again when a token names one not seen yet. What goes wrong ends in one of five refusals — the code refused, the service's own client refused, Google not answering or asking for a pause, the identity not proven, no refresh token — and none of them carries a token or Google's words; the refused client is an error of ours in the line of the callback, since every sign-in fails the same way until the deployment is fixed. The authorization server takes it as an interface, `SignIn`, with the constructor returning it; `googleauth/googletest` stands in for Google over HTTP for the tests of both packages: a token endpoint that holds a code to its request, and keys it signs with. — *Why:* the author's decision on the signature: 02-auth asks for the ID token to be verified against the JWKS, and although the token arrives over a connection the service opened itself — which OpenID Connect lets a client trust without a signature — a signature is what keeps a wrong endpoint, a proxy or a test's stand-in in production from naming whoever it likes. go-oidc is a small, widely used verifier, Apache-2.0, that fetches keys again the way the specification asks; a JWT verifier written here would be protocol code from memory. The exchange is a network call and has to be faked in the authorization server's tests to force each failure, so it stands behind an interface. — *Rejected:* trusting the token without a signature, as the channel allows; `google.golang.org/api/idtoken`, which pulls in the whole of Google's API client; a hand-written check of the JWT. — *Consequence:* two dependencies, `go-oidc` v3.21.0 and `go-jose` v4.1.5, in the license list; `just run` without Google's client serves the consent screen and stops at a page after it. — *Where it lives:* `internal/infra/googleauth/`, `internal/app/container.go`; SPEC 9.3 and 11.2; CLAUDE.md (Layout); RUN.md (T48).

**R108. The user identifier is derived in `seal`.** `KeyRing.UserID(account)` is the first 16 characters of base64url of HMAC-SHA256 over the account — `google-sub:` and Google's `sub` — under a subkey of the current key derived with HKDF from the context `mathtrail/v1/user-id`, which names no purpose. The callback computes it and puts it in the code; the `sub` goes no further. — *Why:* 02-auth derives it from the key ring "like any other purpose", and the key never leaves `seal`: the subkey is derived when the key is read, as the purposes' are, and a caller gets the identifier and never the key. It is not a purpose because nothing is sealed with it. — *Rejected:* a key of its own in the configuration, a second secret to rotate; handing the subkey out of `seal`. — *Consequence:* a rotation changes the identifier of the next sign-in, as 02-auth accepts. — *Where it lives:* `internal/infra/seal/userid.go` and `key.go`; SPEC 9.3.

**R109. The sign-in's pages are the authorization server's own, and the site shares their tokens.** The consent screen and the page a sign-in stops at are `html/template` pages embedded in `internal/transport/oauth/pages/`, with a stylesheet of their own, drawn in English or Russian by `Accept-Language` from one flat dictionary per language there; a test holds the two to the same keys and the same slots, and the service refuses to start when they differ. The design tokens are `internal/widget/tokens.css`, the draft's file with a comment added, and `widget.Tokens()` gives it to the pages, which inline it before their own styles. Every build of the site ships the same file as `assets/tokens.css`, its templates load it before `style.css`, and `style.css` has no tokens left: it reads the draft's names, `--text`, `--page`, `--border`, `--space-*`, `--font-sans`. A dictionary wording names its slots, `{client}`, `{host}`, `{terms}`, and the code fills them with text set apart, a link or plain text, so the template escapes everything. — *Why:* R94 put the tokens beside the widget so all three readers take one file, and RUN.md asks the site to move onto it in this task, so that the site and the consent screen cannot differ in colour before T66. The pages belong to the authorization server as the widget belongs to the MCP server; the widget's dictionaries in `web/locales/` are for twenty-two languages and a browser, and SPEC 8.9 narrows these pages to two. Filling slots in code rather than in the dictionary keeps a translator from writing markup and the template from trusting it. — *Rejected:* the site keeping its own tokens until T66; the pages in `internal/widget` or `content/`; `template.HTML` wordings with markup inside. — *Consequence:* the site's colours become the approved design's. The render package imports `widget`. — *Where it lives:* `internal/transport/oauth/pages.go` and `pages/`, `internal/widget/tokens.css` and `widget.go`, `internal/site/render/render.go`, `site/templates/`, `site/assets/style.css`; SPEC 8.9 and 9.2.

**R110. What a sign-in carries, where its form may lead, and a sign-in without the Drive.** *(Extended by R126: the screen shows the path of the address beside its host, and a name with three marks at most on a letter; an address on the parent's own computer is asked about every time; the cookies carry the `__Host-` prefix.)* The request in flight carries the digest of the `client_id` and how the client is known rather than the identifier, and so does the code, which carries no random id (SPEC remark 54). The browser remembers at most the newest 20 approvals, each for 180 days. The consent screen's policy lets its form lead to Google's origin and the client's, besides this server (remark 53). A grant without `drive.file` is `access_denied` to the client, with a description that asks the parent to sign in again and allow it. A server with no Google client configured shows the consent screen and stops at a page instead of going on, remembering no approval. The screen shows the redirect host in its ASCII form and the client's name without controls or invisible format characters, each isolated from the text around it. — *Why:* the author's decision on `drive.file`: a sign-in that cannot keep the file is no sign-in, and the parent, not a failure, took the permission away. An identifier this server issued carries its whole registration, and both the request and the code ride in an address. A cookie has room for a few kilobytes, and a family uses a few hosts. A browser holds the redirect that answers a form to the form's `form-action`. A lookalike letter of another script in a host, or a mark that turns text around in a name, would let a stranger's client read as a familiar one on the one screen that is to tell them apart. — *Rejected:* a sign-in that goes on without the Drive and fails at the first tool; `server_error` for it; the full `client_id` in the request and the code; `form-action 'self'` alone, which the browser would enforce against the redirect to Google. — *Consequence:* the exchange of a code (T49) compares the digest of the `client_id` it is given; whether a host shows the description of `access_denied` is for T53 (remark 52). — *Where it lives:* `internal/transport/oauth/` (`authorize.go`, `consent.go`, `callback.go`, `flight.go`, `approvals.go`, `code.go`, `pages.go`); SPEC 9.2, 9.3, 12.2 and remarks 52–54; `docs/architecture/02-auth.md`.

**R111. What the code scan reports about the sign-in is what the sign-in is for, and is answered rather than silenced.** *(Narrowed by R126: a refusal goes back to a registered address only once this browser has approved the client there.)* The sign-in drew six alerts. `go/unvalidated-url-redirection` at the redirect back to the client: an authorization server answers by sending the parent to the client's redirect URI (RFC 6749 4.1.2), and the one it sends them to is a URI the client registered, matched byte for byte before it is sealed into the request, and read back at the callback from a value only this server seals, bound to its issuer. `go/request-forgery` at the fetch of a client's document: fetching the address a client names itself by is what a Client ID Metadata Document is, and `/oauth/authorize` is where it now happens; the fetch is R105's. `go/log-injection`, four times, at the sign-in's lines: what in them comes from a request is a host, written in ASCII by `hostOf` with anything else escaped — and `url.Parse` refuses a control character in a host before that — and words this server sealed itself. Every other field is a closed word, an error of ours, or the cause of a failed exchange with Google — Google's error code, or the words its ID token was refused in — which Google's answer chose and a caller cannot; the JSON encoder escapes whatever a field carries (R50). The six are dismissed as false positives, citing this entry. T49 moved the lines of every step into one function, `ended`, and added the lines of the token endpoint and of a revocation, whose `user` is read from a code or a token this server sealed: the same two kinds of path — the host of a request this server sealed, and words it sealed itself — and the three alerts they raised on `ended` are dismissed the same way. — *Why:* the barriers CodeQL knows are a comparison with a constant, a regular expression, a host held to a list, a line break replaced and `%q`; an exact match against a list the client registered, a value sealed under the service's key and a host held to ASCII are none of them. **R112. The resource lets in the access tokens the authorization server issued, through the protocol library's check and a reader of ours.** `mcpserver.BearerSignIn` replaces `NobodySignsIn` in the container: it is `auth.RequireBearerToken`, with the resource's metadata named in the challenge, the one scope required and a clock skew of a minute, around a verifier that asks a `TokenReader` — a function from a token to the account it signs in and the time the token ends. The authorization server's `Account` is that reader: the token opens as an access token this issuer sealed, has not ended with a minute of skew, is for the canonical resource by `oauthex.MatchesResource`, and grants the server's scope; the account is its user identifier, reached with the Google access token it carries. A refused token is answered with the library's own `invalid token`, and leaves an `auth_bearer` line whose reason says why — `unreadable`, `unknown_key`, `expired`, `audience` or `scope`. The account travels from the check to the endpoint inside the library's `TokenInfo`, under a key the MCP package alone knows, and from there in the request's context as before (R82). `NobodySignsIn` is gone. — *Why:* R82 left T49 exactly this: `RequireBearerToken` with a real verifier, and a step that turns the verified token into the account. A reader that returns the account and the token's end keeps the key between the check and the endpoint in one package: the authorization server needs no word of the MCP package, nor the MCP package a word of how a token is sealed. The library holds a token to its end by its own clock as well, so it is given the same minute the reader allows, and the two cannot disagree. The reason of a refusal is what tells an expired token from a key retired too early, and it belongs in the log and not in an answer to whoever sent the token. — *Rejected:* the Google access token in the `TokenInfo` as a string, which would print wherever the information is printed, where the account keeps it out of every print; a key of `TokenInfo.Extra` shared by the two packages; the library's check without a skew, which would refuse a token in the minute the reader lets pass. — *Consequence:* a deployment lets in whoever signed in, and `ci-smoke` still asks only for the refusal of a request with no token. **R113. The token endpoint serves public clients by the rules of OAuth 2.1, and tells a host whether signing in again is what mends a refusal.** *(The minute an access token ends before the Google token inside it, and the five minutes under which that token is renewed, are three minutes and seven since R117. A verifier of another shape than RFC 7636 gives one is `invalid_request` since R126.)* `/oauth/token` takes a form of at most 64 KB, each parameter once but for the resource. A client names itself with `client_id` in the body; one that tries to prove itself in an `Authorization` header is answered `401 invalid_client` with a `Basic` challenge, and may then send the same request as a public client. The code grant holds a code to its minute — refused, too, when dated more than the skew ahead — to the digest of the `client_id`, to the verifier of its challenge, and to its `redirect_uri` and `resource` when the request names them; OAuth 2.1 drops the first from the exchange and lets a client leave it out. The refresh grant holds a refresh token to its end with a minute of skew, to its client, to a scope no wider than its own — the new tokens keep the whole of it — and to its resource. Both answer a new access token and a new refresh token for the session the code or the token carried: the access token ends in 15 minutes or a minute before the Google token inside, whichever comes first, the refresh token in 30 days, and neither later than 90 days after the sign-in; past those, a refresh is `invalid_grant`, within the skew too. The Google token inside is renewed at Google first when less than 5 minutes of it are left, and a refresh token Google gives in place of its own is carried on. A grant Google renews no more is `invalid_grant`; Google not answering, or giving a token too short to issue one with, is `503 temporarily_unavailable`; Google refusing the service's own client is `500 server_error`, an error in the line; a server with no Google client is `503` for a session that needs Google. `googleauth` renews a grant through `x/oauth2`, whose refresh keeps the refresh token Google did not replace, and a refusal of the grant is `ErrGrantEnded`. — *Why:* a public client can prove nothing but PKCE, and the protocol asks for `401` and a challenge of the scheme a client tried in a header; the library's own client, named by its document, tries a `Basic` header first and the body after a refusal, which is how it finds out (SPEC remark 56). OAuth 2.1 requires a server to accept a `redirect_uri` in the exchange and to hold it to the code's. The MCP specification has a client name the resource in the token request. `invalid_grant` is the refusal on which a client drops its tokens and signs in again — the protocol library's client does exactly that — and a failure the host may retry must not be told as one, or a moment of Google's unavailability would sign every family out. — *Rejected:* a refresh token narrowed to the scope a refresh names, which RFC 6749 6 forbids — a new refresh token keeps the scope of the one it replaces; a token issued within the 90 days that outlives them, which would stretch the one bound on a stolen refresh chain; taking `client_id` from a `Basic` header with an empty password, which would spare the library's client one refusal and give the endpoint a second way to name a client (remark 56 keeps it open for T53); requiring `redirect_uri`, which OAuth 2.1 removed; asking Google at every refresh whether the grant lives, a call every 15 minutes per family where the design asks for one an hour; `server_error` for Google not answering, which would read as a fault of ours. — *Consequence:* a code can be exchanged more than once within its minute, and a refresh token presented once still works until its own end — nothing records their use (02-auth, threats). — *Where it lives:* `internal/transport/oauth/token.go`, `grants.go`, `form.go`; `internal/infra/googleauth/grant.go`, `exchange.go`; `googletest`; SPEC 9.1–9.3 and 12.2, remark 56; `docs/architecture/02-auth.md`.

**R114. A grant ends at Google, with the Google token inside the token a host presents, and only when a host asks.** `/oauth/revoke` (RFC 7009) takes `token` and `client_id` in a form. It reads a token of either kind whatever its own end, and holds it to the digest of the `client_id` — a token issued to another client is `invalid_grant`. It asks Google to end the grant with Google's refresh token when the token is a refresh token, and with Google's access token when it is an access token; Google ends the whole grant either way. An access token whose Google token inside has ended can end nothing, and is answered `200` with nothing asked of Google, its line `ignored` as `google_token_ended`; a token that is none of this server's is answered the same. Google not answering is `503 temporarily_unavailable`, the grant not ended; Google refusing the request for another reason is `500`, an error of ours. `googleauth.Revoke` sends the token in the body, and tells Google's `invalid_token` — a token Google no longer honours — apart as `ErrNotHonoured`: nothing was ended, the host is answered `200`, and the line says `ignored` as `not_honoured` rather than revoked. The callback does not end the grant of a parent who unticked the Drive permission: it is left as Google gave it. — *Why:* a server that keeps nothing cannot take back its own tokens, so ending the grant at Google is the only revocation there is (02-auth). A token past its end may still carry a Google refresh token that is alive, and an access token past its Google token's end cannot say whether its grant lives, so a line that called it revoked would be wrong. RFC 7009 answers an unknown token with `200`, since a client can do nothing about it, and a client that is not the token's with an error, and has a client retry after a `503`. A token in an address may be kept by any hop on the way. Google ends every grant of a parent's at a service together, so ending the grant of a sign-in the parent only declined would disconnect the chats they had already connected. — *Rejected:* revoking only the tokens this server issued, which changes nothing; `200` for a token of another client; refusing a token past its end; ending the grant without the Drive at the callback, which SPEC remark 52 had left for T49 and which would cut the parent's other connections. — *Consequence:* ending a grant disconnects every chat the parent connected, and the host's own tokens keep working until the next renewal asks Google (SPEC remark 55). A refresh token always ends the grant; an access token does while the Google token inside it is honoured. A grant without the Drive stays in the parent's Google account until they remove it there or it goes unused for six months. — *Where it lives:* `internal/transport/oauth/revoke.go`, `callback.go`; `internal/infra/googleauth/grant.go`; SPEC 9.1, 9.3 and 12.2, remark 52; `docs/architecture/02-auth.md`.

**R117. An access token ends three minutes before the Google token inside it, so that a request it lets in reaches Drive in time.** *(The deadline its consequence leaves to T51 is R118's: the Google token's end travels with the account, and no call to Drive is started past it. The wait for a slot of the sandbox, which the margin below leaves open, is bounded since R122.)* The margin is three things added up: the minute the resource takes a token past its end, the minute by which the clock that checks a token may run behind the one that issued it, and the minute a tool goes on calling Drive after its request is let in — at most six calls of ten seconds each, or five beside two runs of a solver of two. A Google token's life is counted from the moment it was asked for, not from the moment the answer came, so the end the service keeps is never later than Google's. The Google token inside is renewed at either grant when less than seven minutes of it are left — the margin and four minutes more — so that an access token is good for four minutes at least whenever Google's own lasts seven. — *Why:* the author's decision, on the review of T50. With a minute of margin and a minute of allowance, the last requests of a token met a Google token that had ended, and Drive answers an ended token as it answers access taken back, with a `401`: the store reads that as `ErrAccessRevoked`, and the new sign-in T51 gives it would send a parent through Google again for nothing. The margin belongs where a token's life is set, so that every token the resource takes carries a Google token that outlives the request — and a Drive `401` then means the grant is gone. — *Rejected:* telling an ended Google token from a revoked one at the store, which Drive's answer does not say; renewing the Google token at the resource while a request waits, which needs Google's refresh token inside the access token, and 02-auth keeps it out so that one stolen buys minutes and no renewal — the refresh grant renews it ahead of time instead; a narrower allowance at the resource, which is what keeps a token from being refused by an instance whose clock runs ahead of the one that issued it. — *Consequence:* at fifteen minutes of access and an hour of Google, what a host sees changes only for a token issued near the end of a Google token, and it is renewed sooner. The minute of a tool is a fact about the tool rather than a setting: a request cut off, or answered late, does not stop it (R83), so a call to Drive given longer than its ten seconds, more calls to a tool — the retries T51 brings — or a long wait for one of the solver's slots, which nothing times, move the margin with them. What would hold the line whatever a tool takes is a deadline: the Google token's end carried with the account, and no call to Drive made past it — left for T51, which decides what a Drive `401` is told as. — *Where it lives:* `internal/transport/oauth/grants.go` and its tests (`property_internal_test.go`, `refresh_internal_test.go`, `token_internal_test.go`, `host_internal_test.go`); `internal/infra/googleauth/exchange.go`, `grant.go`, `grant_test.go`; SPEC 9.1, 9.3 and remark 55; `docs/architecture/02-auth.md`; R113.

**R123. The development sign-in names an account after the bearer credential it is given, and refuses nobody.** *(Amends R82.)* A request whose `Authorization` is `Bearer <name>` — the scheme in any case, the name 1 to 64 letters, digits, dots, dashes and underscores — acts for the account `dev-<name>`, which has a profile of its own in the store in memory and a pace of its own. Any other request acts for `dev`, as every request did before: one with no credential, and one whose credential names nobody. The switch is the same variable, and a deployment refuses it as before. — *Why:* the author's decision, taken while planning T52a. The load scenarios need several children on one instance — "one user past the limit, the others still served" cannot be shown with one account — and the real sign-in cannot issue a token without Google. A name read from the header every client already knows how to send is the smallest change that gives them, and a second switch would be a second thing to keep refused. A credential that names nobody still signs in as `dev` because `just run-signin` and `just run` serve the same address: a client that kept its token from the first would otherwise be refused by the second, try to sign in again where no Google client is configured, and stay locked out until the token was forgotten by hand. — *Consequence:* no client that was let in before is refused. Every name is a key of the account's pace, which keeps at most 4,096 of them, and of the store in memory, which lives as long as the process and only on a developer's machine. The name is written into lines as the `user`, which its alphabet makes safe. The service's own access tokens are sealed strings of hundreds of characters, so none of them is ever taken for a name. — *Rejected:* refusing a credential that names nobody with `401`, the first design, for the lock-out above — the author's decision after the review of T52a.1; minting access tokens of the real sign-in with the sealing key, which leads to Drive and needs Google; a header of the service's own, which no host's connector would ever send; a separate switch for many accounts. — *Where it lives:* `internal/transport/mcp/signin.go`, `internal/transport/mcp/devsignin_test.go`, `internal/app/container.go`, `justfile` (`run`); SPEC 9.4 and remark 24.

**R126. The security review closes what it found in the sign-in, the registration of clients, the MCP endpoint and the storage, and names what it leaves.** The code at rest was read by area, each finding checked against it, and a real one closed with a test that fails without the fix. What changed:
- The MCP endpoint refuses a body that is a batch of messages, `400`, before the protocol library reads it. The library still takes a batch from a request that names no version, and every message of one was a call of its own — logged, answered, held to the paces one by one — inside one request the paces saw once: a megabyte of them was fourteen thousand calls and as many lines of the log, and forty such requests at once held five gigabytes of an instance's memory (R02).
- The token endpoint is held to its address's pace alone. A host renews its tokens there every few minutes in the middle of a lesson, and the sign-in's pace of the instance is one a flood of anybody's could fill: renewals refused for a quarter of an hour stop every lesson (R121).
- A client identifier is fetched on port 443 alone, the first four addresses of its name are dialled, and the lookup, the dials and the connection itself — its handshake and whatever is read on it — end with the attempt. The HTTP client lets a dial outlive its request, and a server that took the connection and never answered held it, and a goroutine, for as long as it liked. A document lists at most 32 redirect URIs, since what the fetcher reads is what the cache keeps (R105).
- The consent screen shows where the parent goes back to by host and path, a long path cut in its middle so that its start and its end both show — a familiar host may serve pages anybody publishes — and a client's name with three marks at most on a letter, so that it cannot spill over the line naming the address. - A request from a known client, at an address it registered, that the server cannot grant goes back to the client once this browser's parent has approved it there, or when the address is on the parent's own computer, which sends nobody elsewhere, and stops at a page otherwise: anybody may register a client at an address of their choosing, and a refusal sent there at once made a link to this server a way to send a parent anywhere (RFC 9700 4.11.2; R111).
- The sign-in's cookies are `__Host-mt_csrf` and `__Host-mt_consent`, on the path `/` the prefix asks for: a site under the same domain could otherwise set cookies of those names in their place and carry an approval past the consent's check.

- A task is sealed again when its answer is recorded, against the letter it was given, and an answered task opens only against that. An `answered` written into the file by hand told the answer before the child had given one (R101).
- A task's texts are held to what a card shows — the question to 1,500 characters, an option to 200, the hint to 500, the solution to 2,000, an explanation to 500; what is sealed is not escaped for a web page; and no profile is written past 1 MiB, the most a store reads back. A task whose solution was a megabyte of `<` was written, read back as damage and rolled back, and each time it pinned one more revision of the history.
- Every count of the profile is held below 2^30, and a file reads only with room in each for one more: a count set by hand to the most a number holds left a file that read and could never be written.

What stays, and why:
- The seal of a task is bound to the student's id and the task's, which the file carries. Copied with both into another profile it opens there, so whoever can read a family's file and has an account of their own can learn the answer to the task on its card. Accepted by the author: the file is in the parent's own Drive, and whoever reads it is somebody the family let in.

- A restore uploads the earlier revision's bytes as they were, fields this build does not know among them, and the next write drops them; with one version of the file there is nothing else to drop.

Every call goes through the protocol library's own client — one session for each child of a run, opened with `server/discover` at 2026-07-28, each call with a deadline of its own — and the tool writes no message of the protocol by hand. A session the library finished at an older version, because the service refused the newest, counts as no session. vegeta gives the constant pace (its `Pacer`, driving a runner that sends every call in a goroutine of its own when it is due, so that a slow service gets more calls in flight rather than fewer) and the percentiles (its `Metrics`, one for each kind of answer, every call timed from the moment it was due). Children sign in through the development sign-in by names of their own (R123). An answer is told apart by what it says: a refusal by the status and code of its payload, a failure by its first sentence, the busy sandbox and a pace by theirs — and a pace that holds back a message other than a tool call by the words of its error of the protocol — and a call that got no result by the status it got, the protocol's error or the network; a call the run itself abandoned is told as stopped. The report is Markdown: the verdict first, every kind of answer with its share and times, and what one unit of the run's work cost as the platform bills it — every moment at least one call was under way, in steps of a tenth of a second, times the vCPU and the GiB of the instance, and every request the service answered, the library's own among them — against the free tier's 180,000 vCPU-seconds, 360,000 GiB-seconds and two million requests a month, naming the allowance that runs out first. What fails a run outright is what the service should never do under any load: a status of 400 or more, told by its status whatever error of the protocol rode on it, a call with no answer, an answer that belongs to another call, another version of the protocol, a failure of its own other than the busy sandbox, an error of the protocol, a kind of answer nobody has seen before — and whatever the scenario expected and did not see. A run stopped before its end is reported for the part that ran, with no verdict and held to no expectation, since it did not get to meet them, and ends as one that could not run. The tool's checks run on every pull request: `just load-lint` — `go mod tidy -diff`, `gofmt`, the linter with the root's configuration, the license check against the root's list, `govulncheck`, and the versions it shares with the service held to the service's — and `just load-test`. Dependabot proposes vegeta alone for the module: what vegeta brings moves with it, and `govulncheck` names any of it that turns out vulnerable. — *Why:* the author's decisions, taken while planning T52a. A module of its own keeps vegeta and what it brings out of the service's dependencies and out of `THIRD_PARTY_LICENSES`. It imports the product so that its tests run every scenario against the real service in the same process, and the tasks a lesson hands in are proven against the real checks, on every pull request; and so that the protocol library it speaks is the service's own, at the service's version. The library's own client, rather than requests of the tool's making, is what keeps the protocol written once: 2026-07-28 asks for headers and fields of its own on every request, and answers in a stream. Billing is counted from the time requests are under way because that is what request-based billing charges for: the allotted processor and memory while a request is served, not what the process happened to use of them. — *Consequence:* a change to the product's `go.mod`, a dependabot pull request among them, is followed by `just load-tidy`, or `just load-lint` and `just load-test` fail; that is the price of the tests against the real service. The requests a report counts are the tool's own, and a chat host sends more for every call it makes (SPEC remark 62). The billed time is counted from the client's side, and includes the network between it and the service. The runner has no user yet in this part; the scenarios that load the sandbox and the limits use it (T52a.3), and the container, the cgroup and the cold start come with T52a.4. — *Rejected:* raw HTTP through vegeta's `Attacker`, which would have the tool write the protocol's messages and read its streams itself; a load tool in a second language (k6, Locust), which would write the protocol a second time; a module without the product, whose tests would meet only a fake of the service; closing a session a call found broken at once, which would fail the calls of the same child still under way on it — it is kept until the child is done. — *Where it lives:* `tools/load/`; `justfile` (`load`, `load-test`, `load-lint`, `load-tidy`); `.github/workflows/ci.yml`; `.github/dependabot.yml`; `sonar-project.properties`; `CLAUDE.md`; `CONTRIBUTING.md`. — *Extended in T52a.3:* three attacks, each followed by a recovery — the probe answering within the timeout of a call, then a child new to the service walking a lesson of one task — reported as a run of its own. `saturation` hands in the costly `loop` at a constant rate, shared among ten children, each hand-in for a request nobody opened: the sandbox runs both runs and the service writes nothing, and a hand-in turned away as busy is the service keeping its answers in time rather than a failure. `limits` runs a greedy child and a greedy address past their paces beside three children walking lessons and three quiet addresses fetching the document once every five seconds, within theirs, and reports the four apart, each held to what its pace should have done to it; the children's calls carry no address, since only the sign-in and its documents hold an address to a pace. The greedy address fetches at the greedy child's rate — three a second, not the two first planned — so that one rate drives both. `adversarial` hands in the costly solvers one after another. Each spends 90 to 99 % of the step ceiling it is sized to (`-steps`, the service's default unless told otherwise) and points at the one right option, so both runs go whenever the clock lets the first one end: a loop, appends, sums of a million, the widest tuples the ceiling holds taken widest first, pairs, and a product of a hundred thousand numbers only the clock stops. Pairs are there because a tuple takes memory of its own that the budget does not charge: at the default ceiling one run of them holds 824 MiB, against 442 for the widest tuples the same budget buys — two products of nineteen and one of eighteen — and 381 for the two alone, which is what SPEC 6.6 measured, and with four runs at once the process reached 5.6 GiB where nothing limited its memory (SPEC remark 63, the author's decision). On the development machine the `loop` takes 0.1 s, not the 0.4 s planned, so saturation fills four slots only on a smaller processor, the one T52a.4 runs it on; the sums of `helper` run past the clock of two seconds, which stops them before the budget does. An attack that sends no call, or examines no hand-in, has tested nothing and fails; a recovery's lesson that a pace held back is walked again, by a new child after a pause twice the last, for as long as the probe may take to answer, since a pace shedding what is left of an attack is the service doing as it should. The addresses of `limits` are what the tool writes into `X-Forwarded-For`, which the service reads as the address only with nothing in front of it: against the deployed service they are all the tool's own, and the quiet ones are held back with the greedy. — *Extended in T52a.4:* a run starts the service itself, from an image, in a container of an instance's size — one vCPU and 512 MiB by default, and no swap, as the platform gives none — its port published on this machine alone, the development sign-in on, a sealing key made for it passed in the command's environment rather than on its command line, and a label by which a container a killed run left behind can be found. Its cgroup is the one the line `0::` of its process's `/proc/<pid>/cgroup` names, as docker's own driver and systemd's alike write it, read every quarter of a second; cgroups of the first version, or a daemon whose processes this machine does not see, leave the instance unmeasured rather than unrun. A container is stopped in one order: the last count of its cgroup, which goes with it; its state, which says whether it ended before; the stop, with the platform's ten seconds; its log, for the lines of a panic and every `solver_run`; and its removal, always. What the instance spent while a run went on is given to a run that went on alone — the cgroup counts the instance as a whole — and the life of an instance to the last run it served, which it fails for a panic, a kill for memory, an end of its own, or a peak above `-memory-ceiling`. The scenarios get their services from one function type, `Launch` — an image, a URL, or in the tests the service in the same process — and `adversarial` gives every variant an instance of its own; `cold` starts the service five times, and only from an image. A service that never answered its probe fails the run as a hard fact, and a container that could not be started at all is a run that could not go on. `just load <scenario>` builds the image first unless it is given `-url` or `-image`. Measured on the development machine at the default size: a lesson spends 0.017 CPU-seconds a task against the 0.36 billed; saturation at three hand-ins a second fills no slot, since the loop takes 65 ms on one processor; `appends` peaks at 436 MiB with four runs at once; and `tuples`, `pairs` and `product` each end the instance for want of memory (SPEC remark 63). A service whose instance ended is not waited for: its recovery fails at once. One that ends as it starts is a service that never came up, and its last lines go with the life of its instance; the docker commands run in a group of processes of their own, so that an interrupt at the terminal reaches the tool, which removes what it started. — *Rejected:* the Docker Engine's Go library, which would bring a large module for the six commands the tool gives; memory read from the service's own process, which is not what the platform counts or kills by. — *Extended in T52b:* an instance started from an image is told what a deployment of its size is told — a solver slot for every whole vCPU, and never fewer than one, and nine tenths of its memory as `GOMEMLIMIT` — unless `-env` names either, and its memory is 1 GiB unless `-memory` says otherwise. Two costly solvers join the others: `sets`, the tables a helper builds, among the defaults of `adversarial`; and `dicts`, dictionaries written in a loop, the memory the language takes by itself where no price reaches, handed in only when it is named. The costly solvers are sized to the price of R125. `just ci-load` runs every scenario against the image, each held to its memory and each report under the command that ran it, and exits with the worst code of them; `.github/workflows/load.yml` runs it every Monday, by hand, and on a pull request that changes the workflow, with the reports as the run's summary.

## The full checks

**R38. What blocks a merge, and what only reports.** Three checks can turn a pull request red on their own: the coverage of the changed lines, held at 90% by `codecov.yml`; CodeQL with the `security-extended` queries; and Trivy over the runtime image at HIGH and CRITICAL, run through `just ci-image-scan` from its own pinned image so the same command gives the same verdict on a laptop. Everything else stays a reading: SonarCloud as R31 left it, OpenSSF Scorecard as a public measure of how the repository is run, and the total coverage, which moves for reasons a single change does not control. — *Why:* the service is written around children's data, and the bar has to hold without depending on anyone remembering it. Coverage of the patch rather than of the project is what a change can actually be held to: `cmd/sitegen` and `cmd/sitecheck` sit at 19–26% and leave entirely in T66, so a project-wide floor would either be set so low it proves nothing or block work it has nothing to do with. CodeQL follows values across functions and files, which is the one thing the linter's own security checks cannot do, and it is what will matter once sign-in, Drive and the HTTP surface are real. — *Consequence:* Trivy reports a vulnerability of the Go standard library from the version stamped in the binary, without asking whether the code reaches it, so it can go red where `govulncheck` stays silent; the fix is a newer Go in the `Dockerfile`, and anything that cannot be fixed that way goes into `.trivyignore` with its reason. The patch status needs the repository's branch protection to require it, which is a setting rather than a file. A pull request from a fork gets no Codecov upload and therefore no patch status, and so does a run Dependabot starts while the repository keeps no Codecov token among the secrets kept for Dependabot — keeping one there is what gives such a run its patch status. — *Rejected:* a floor on total coverage, for the reason above; Snyk, which needs an account and a token for what CodeQL and `govulncheck` already answer; gating on the Sonar quality gate, which R31 settled. — *Where it lives:* `codecov.yml`, `.github/workflows/codeql.yml`, `.github/workflows/scorecard.yml`, `justfile`, `README.md`.

**R39. Invariants are tested with gopter, and a check is proven by breaking it.** Computation that holds an invariant — the ratings, `seal`, trigram similarity, readability, the solver contract, and the copies the content hands out — is tested by naming the invariant and letting the library hunt for the input that breaks it. The library is `github.com/leanovate/gopter`, and a new check is not called covered until its test has been seen to fail with the check switched off. — *Why:* worked examples prove what somebody already thought of. The shallow copy in `content` is the case in point: three hand-written examples passed while a caller could still rewrite an option inside the binary's own content, and the property that a copy shares nothing finds it by itself. Breaking the check by hand is the same idea applied to the tests: it costs a minute and catches the test that passes because it never ran the code it names. — *Rejected:* `pgregory.net/rapid`, whose API and shrinking are better but whose licence is MPL-2.0 against a list of five permissive ones — a test-only dependency never reaches the shipped binary and `go-licenses` does not even see it, but an exception to the licence rule would have to be explained for as long as the repository exists, and gopter costs ten more lines per test instead; `testing/quick`, which cannot shrink a counterexample, so a failure arrives as a wall of random input; a mutation-testing tool — `go-mutesting` is abandoned and `gremlins` is slow and noisy, and the rule above buys the same thing where it matters. — *Where it lives:* `content/property_test.go`, `go.mod`, CLAUDE.md ("Tests").
**R20. The checks run inside the development image, published to GHCR and pinned by digest.** `.devcontainer/Dockerfile` has two stages: `toolchain` — Go, Node, `just`, `golangci-lint`, `mockery` — and `devcontainer`, which adds the editor tooling, cloudflared, the compose plugin and the Claude Code CLI on top. A first job installs `just` and calls `ci-toolchain-image`, which tags the image with a hash of the Dockerfile, publishes it if nothing is published for that hash yet, and prints the digest to run the checks in; every other job runs inside that digest. `govulncheck`, `gitleaks` and `go-licenses` stay Go programs run straight from their modules at versions pinned in the justfile. Every step of the workflow is a `just` recipe or a pinned action, with one line of wiring to carry the reference between jobs. — *Why:* the author's decision, replacing an earlier arrangement where a script installed tools onto the runner. One description of the environment now serves both a laptop and a pull request; a tag computed from content means a change to the environment needs no second commit to point CI at it; and a recipe rather than a block of shell in the workflow is what the other services in the platform do. — *Consequence:* the first run after a change to `.devcontainer/Dockerfile` pays for one image build; a pull request from a fork cannot publish, so such a change has to reach `main` before a fork can be checked against it. The `image` job stays on the runner, because the docker client reaches the development environment through a devcontainer feature and a plain build does not apply features. A checkout inside a container belongs to a different user than the one running the job, and Go looks for its caches under a home directory the job does not control, so `safe.directory` and the two cache locations are set once for the whole workflow through the environment, where they hold for every step whatever user and home it gets. — *Rejected:* `latest` or any moving tag, which the rule of exact versions forbids; building the image on every run; a copy of the tool versions inside the workflow; a build cache for an image that is only ever built when its one layer has already been invalidated. — *Where it lives:* `.github/workflows/ci.yml`, `.github/actions/just/`, `.devcontainer/Dockerfile`, `justfile`, T18.

**R21. `THIRD_PARTY_LICENSES` is generated from the dependency graph, and the checks compare the two.** `just licenses` rewrites the file; `just ci-licenses` fails when a dependency carries a license outside the permissive list (MIT, BSD-2, BSD-3, Apache-2.0, ISC) or when the committed file no longer matches the graph. — *Why:* the repository owes its readers a current list of what it ships and under what terms (PRODUCT 8), and a list that is written by hand stops being true at the first dependency bump; this is the same contract the generated mocks already have. — *Consequence:* each line links the license text of the exact version in `go.mod`, so a dependency update fails the check until the file is regenerated — one command, and it is what keeps the links pointing at the text that actually ships. — *Rejected:* a list without versions, which would never need regenerating and would never be exactly true either. — *Where it lives:* `justfile`, `THIRD_PARTY_LICENSES`, T18; the npm side is `web/scripts/licenses.ts`, T42 (R85).

**R85. Every npm package the widget's lockfile pins is held to the license list, and the bundler's CSS minifier is the one exception.** `just ci-licenses` runs `web/scripts/licenses.ts`, which reads the lockfile and holds every package in it — what the widget is built from and the tools that build it — to the same permissive list as the Go modules, reading each license as an SPDX expression. `lightningcss`, under MPL-2.0, is excepted by its name and its license, together with its per-platform binaries, and only while it stays a development dependency. `THIRD_PARTY_LICENSES` lists, after the Go modules, every package the lockfile needs outside development. `just ci-vuln` holds those same packages to the published advisories, at high and above, with `npm audit`. — *Why:* the author chose Vite 8, which depends on lightningcss and cannot be installed without it. MPL-2.0 is copyleft file by file: it binds lightningcss's own files, not the CSS it minifies, and none of lightningcss reaches what is shipped. R39 declined an MPL-2.0 library for tests because a permissive one did the same work for ten more lines per test; here the alternative was the previous major version of the bundler. Holding the tools to the list too turns "only permissive dependencies" into something a check keeps rather than something a reviewer remembers, which on the Go side `go-licenses` cannot do: it sees only what is linked. The list says "built from" rather than "contains", because the lockfile's production tree is wider than the bundle — the MCP client's Node-only dependencies are in it, and the bundler drops them. `npm audit` is there because nothing else would look: `govulncheck` reads only Go, and Trivy sees no JavaScript inside the Go binary. — *Consequence:* a package moving to a license outside the list fails the check, and so does lightningcss the day it becomes something the widget is built from; a new tool under another license needs a decision of its own. `npm audit` does not ask whether the code reaches a vulnerable function, so it can go red where the widget is not affected; the answer is a bumped package, like any other. — *Rejected:* Vite 7.3.6, whose whole tree is permissive, by the author's decision to take the current major; listing only what the bundle holds, which needs a plugin in the bundler for a list the lockfile already bounds. — *Where it lives:* `justfile` (`ALLOWED_LICENSES`, `NPM_LICENSE_EXCEPTIONS`, `licenses`, `ci-licenses`, `ci-vuln`), `web/scripts/licenses.ts`, `THIRD_PARTY_LICENSES`, T42.

**R22. Nothing checks the wording of the repository.** There is no list of forbidden terms, no secret holding one and no job searching for them. This withdraws one half of the prototype's D36, the half about never naming the contest the project started from; its other half — difficulty as a level from 1 to 5 inside the grade level — stands, and lives in SPEC 1. — *Why:* the author's decision. That was a note about how the research preceding the project was written, not a rule this repository inherits, and a check with a secret list was machinery for a problem that does not exist. — *Where it lives:* nowhere; the rule is gone from CLAUDE.md and from T18.

**R31. SonarCloud reads every branch and pull request, and gates nothing.** A job sends the sources and the coverage profile the tests already measured to the organization the platform's other services report to, and the five measures in the README's second row are what it answers. It runs on the runner rather than inside the development image, because the scanner installs itself and has no business in the environment the code is built in; it takes the coverage as an artifact instead of running the tests a second time; and on a pull request whose run was given no token — one from a fork, which is given no secrets, or one Dependabot starts while the repository keeps no token among the secrets kept for Dependabot — the analysis is skipped rather than failed, since nobody could pass it: what such a pull request changes is analysed once it reaches `main`, where a missing token fails the job as it always did. Automatic Analysis is switched off on the project's side: it reports no coverage and refuses to coexist with an analysis that arrives from a workflow. — *Why:* the author's decision — the same badges and the same organization as the platform's other services, so that a person moving between them reads the same summary of a repository in the same place. The coverage was already being measured and uploaded; this gives it a second reader that also says something about duplication, complexity and the shape of the code. — *Consequence:* a merge is not blocked by the quality gate — the job fails only when the analysis itself fails, and the gate arrives as its own check from Sonar's GitHub app — so blocking on it would be a decision of its own. A third party now reads the sources: they are public and MIT, and neither a child's data nor a secret has ever been in this repository. The project has to exist in the organization and `SONAR_TOKEN` has to be among the repository's secrets, or the job is red. — *Rejected:* Automatic Analysis, which needs no workflow and sees no coverage; running the tests again inside the analysis job, which would double the slowest check for a number that already exists. — *Where it lives:* `.github/workflows/ci.yml`, `sonar-project.properties`, `README.md`.

**R40. Every green `main` publishes signed binaries, and nobody tags anything by hand.** `.github/workflows/release.yml` waits for the checks to pass on `main`, works out the next version — the newest tag with its patch number raised, `v0.1.0` when there are none — builds the server for `linux/amd64` and `linux/arm64` through `just release-artifacts`, writes `SHA256SUMS`, signs every file with keyless cosign, and publishes the lot as a GitHub release whose tag it creates itself. A button with a version field exists for the release that deserves a number of its own. The service itself is still delivered the way it always was: a merge to `main` builds an image and Cloud Run serves it. — *Why:* the author's decision, taken while raising the repository's OpenSSF Scorecard, and shaped by the reference service, which releases from every push to `main` and asks nobody to type a git command. The number it moves is Signed-Releases, but the thing underneath is worth having on its own: the certificate records which workflow, which repository and which commit produced a binary, so "this is the code that was running" stops being a claim and becomes something anybody can check. A side effect earns its keep too — with tags in the repository, `git describe` finally returns a version, so `/health` and the startup log say `v0.1.4` instead of a commit nobody can order. — *Consequence:* a release per merge, which is forty of them before RUN.md is finished; the version is semantic but its patch number counts merges rather than fixes. Signing happens before anything is published, because a release that appears without its signatures scores zero on a check that would otherwise not apply at all — worse than having no releases. The release runs from the commit the checks passed on, not from whatever `main` points at by then, and only when that commit is this repository's own: a pull request from a fork runs the checks here too, and the branch filter matches on the name of the branch the run came from, so a fork whose branch is called `main` would otherwise have had its code built, signed and published under our identity — the job requires the triggering run to be a push from this repository, which is what closes it. — *Rejected:* a tag pushed by hand, which is the manual step this replaces; the reference's own scheme of naming a release after the commit, which fails the questionnaire's `version_semver`; the SLSA generator, whose reusable workflow must be referenced by tag rather than by commit — it would break the rule that every action is pinned by SHA and lower Pinned-Dependencies to buy a stronger provenance format; a third-party action for creating the release, where `gh release create` with the workflow's own token adds nothing to the supply chain; signing the image that actually reaches production, which is the more useful thing and remains open — Scorecard does not look at it, and it belongs with the deployment rather than with a release. — *Where it lives:* `.github/workflows/release.yml`, `justfile`, `docs/openssf-best-practices.md`.

## Widget build

**R06. The `@modelcontextprotocol/ext-apps` package, version 2.0.0; the library is the reference, not the text of the specification.** Where the MCP Apps 2026-01-26 specification disagrees with the library — in `ui/message` and `ui/update-model-context` its `content` field is always an array of blocks, not a single object — we follow the library. — *Why:* its code is the actual runtime the hosts run; the discrepancy was found in T03 while building the widget. — *Where it lives:* T42, `web/package.json`.

**R84. The widget is built by Vite 8 into one page, with Preact and no plugin for it; TypeScript checks its types, Biome formats and lints it, and Vitest tests it in happy-dom.** `web/` is an npm project with exact versions and a lockfile, and its `.npmrc` keeps new versions exact and lets no package run an install script. `vite-plugin-singlefile` inlines the script and the styles, so the page loads nothing. JSX is compiled for Preact from the settings in `tsconfig.json`, which the type checker, the bundler and the test runner all read. TypeScript 7.0.2 compiles nothing; it only checks, in two configurations: `tsconfig.json` gives the widget the browser's globals alone, and `tsconfig.node.json` gives the scripts and the build's configurations Node's, so that code meant for the page cannot lean on something only Node has. The build's configuration is `vite.config.widget.ts`, so that the site's can stand beside it. `@modelcontextprotocol/client` and `core`, which `ext-apps` imports, are exact versions like every other package, and they move with the updates Dependabot proposes. The widget's tests talk to the library's own host, `AppBridge`, over an in-memory transport, so what the widget receives in them went through the protocol. — *Why:* the author's decisions on the bundler and the linter. Biome is one tool for formatting and lint, as `gofmt` and `golangci-lint` are on the Go side, and it works with TypeScript 7, which the spike already used; it can also forbid imports by pattern, which the site's checker needs later. Client and core are not held to the pair `ext-apps` was built against. The widget's tests run `ext-apps`'s own `App` on the installed pair, which is where an `ext-apps` that no longer fits its client would show, on the paths the widget uses; they cannot show whether a real chat host still understands the widget, since both ends of a test are made of the same packages — but no pin decides that either, because the host runs a version of its own, and a live run is what shows it. — *Consequence:* no lint rule yet catches a promise nobody waits for — Biome has one only as an experiment; the type checker and the tests are what stand there. — *Rejected:* ESLint with typescript-eslint, which supports TypeScript only up to 6.0 and needs Prettier beside it for formatting; `@preact/preset-vite`, which brings Babel for a hot reload no chat host offers; jsdom, heavier and depending on mdn-data under CC0, outside the license list; holding client and core at the pair `ext-apps` 2.0.0 was built against, where they were first pinned: a pin keeps the pair its authors tested, but it cannot tell whether a real host still understands the widget any better than the tests can, and it leaves the widget behind every fix of theirs — so the author took the pair's first update once the tests had passed on it. — *Where it lives:* `web/`, `justfile` (`web-*`, `ci-web`), `.github/dependabot.yml`, T42.

**R86. The built widget lives in a Go package beside a committed placeholder; every build that ships builds the widget first, and the checks read it back out of the image.** The web build writes `internal/widget/widget.html`, which git ignores, and `placeholder.html` beside it is committed, so the package compiles and its tests run without Node. `widget.Page()` is the built page when there is one and the placeholder otherwise. `just build`, `just run` and `just release-artifacts` build the widget first, and `web-build` refuses a page that does not name `ui/initialize`, the handshake a host starts a widget with. The image builds the widget in a Node stage of its own, pinned by tag and digest at the development image's version, and copies the page into the Go stage. `just ci-image-widget` starts the image with the development sign-in and reads the widget the way a host does, refusing the placeholder or anything that is not a widget; the image job runs it, and so does `ci-image-push`, so the image that is pushed is the image that was read. The release workflow installs Node, at the development image's version, before it builds the binaries. — *Why:* `go test` must not need Node, and a committed page that every build overwrote would leave the tree changed and `git describe` reporting a dirty version. The fallback to the placeholder is silent by design, so the checks are what keep a build that ships from carrying it — and a binary cannot be checked by its bytes, since it carries both pages. — *Rejected:* committing the built page, as the spike did — a quarter of a megabyte of generated code in every diff; a committed placeholder that the build overwrites, for the reason above; a build tag that chooses the embedded file, which makes a second build that the linter and the editor do not see. — *Where it lives:* `internal/widget/`, `web/vite.config.widget.ts`, `Dockerfile`, `justfile` (`web-build`, `build`, `run`, `release-artifacts`, `ci-image-widget`, `ci-image-push`), `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `.github/actions/node/`, T42.

**R87. The widget's resource tells a host what it needs both where it is listed and where it is read, and a tool that draws a card names the widget under both keys hosts read.** `resources/list` and `resources/read` both carry `_meta.ui`: a content security policy whose four lists are empty and sent as empty lists, and `prefersBorder: true`. A tool defined with `Spec.DrawsCard` carries `_meta.ui.resourceUri` and the flat `_meta["ui/resourceUri"]`. Resources are declared without `listChanged`, and every read of the widget is answered with a result of its own. — *Why:* the library the hosts run takes the policy that comes with the page and falls back to the listing (R06), and the Go SDK copies neither onto the other; the library's own helper for tools that draw a card writes both keys, for hosts older than the nested one. A server that keeps nothing between requests has nobody to tell that a list changed. The SDK writes into whatever result a handler returns, so a result shared between reads would be written by several at once. — *Where it lives:* `internal/transport/mcp/widget.go`, `tool.go`, `server.go`, SPEC 7.3 and 8.1, T42.

**R88. Dependabot brings the widget's protocol packages in a pull request of their own.** `@modelcontextprotocol/ext-apps`, `client` and `core` form one group in `.github/dependabot.yml`, and every update of theirs arrives in its pull request, major versions included; the group of routine bumps names them among the packages it leaves out, and every other npm package keeps to it, its major versions arriving one by one. — *Why:* the three are what the widget speaks to its host, and `ext-apps` runs on the other two, so a change to one is read with the others rather than as one line among the tools' bumps. A major version of `ext-apps` is likely to need one of its client and core, and a pull request of this group is read before it is merged whatever it moves, which is what keeping major versions apart is for elsewhere in that file. — *Consequence:* a security update is not grouped: Dependabot opens it for the package with the advisory alone. A pull request that moves `ext-apps` moves the version that R06, SPEC 8 and 03-flows name, and has to change them with it; nothing checks that, as nothing checks the wording of the repository (R22). — *Rejected:* a group for the routine versions of the three and another for their major ones, which rests on how Dependabot places an update that the patterns of two groups both match — its documentation says only that the first group matching takes it; the whole `@modelcontextprotocol` scope as the pattern, which would pull any later tool of that scope into the protocol's group. — *Where it lives:* `.github/dependabot.yml`.

## Ratings and the choice of a task

**R79. The grade sets only where a child starts, and every task stands on one ladder of grades 1–6.** A task is still a level — `1-2`, `3-4`, `5-6` — and a difficulty from 1 to 5 inside it, but the fifteen pairs stand on the one scale θ is measured on: β = the level's shift + (difficulty − 3), with `1-2` at 0, `3-4` at 2.5 and `5-6` at 5, so that the two hardest difficulties of a level overlap the two easiest of the next and no two points coincide. The grade picks the child's starting point θ₀, the shift of its level, which is written into `ratings.start` when the profile is created and never moved again; a grade changed later is a label, and neither the ratings, nor the start, nor the trial series notice it. The first five answers are a **trial series**: each on a topic the child has not met, no failure worked over again, and after every answer θ is set to the most likely level given the start and all the trial answers at once — a normal prior centred on θ₀ with a spread of one level shift, times the chance of each answer by the formula of SPEC 2.1 — while the corrections of the topics stay where they are and every counter, trap and run is written as usual. From the sixth answer on, `Update` moves θ and δ as it always did. The estimate is found by evaluating that posterior on a grid of step 0.05 over θ₀ ± n · 2.5², where the maximum has to lie — no answer pulls with a slope steeper than 1, and the prior pulls harder the further it is — and by halving the best cell on the sign of the derivative. A topic is **within reach** when its easiest point, difficulty 1 of the lowest level it is taught at, is solved with a chance of at least 0.70 at θ + δ — the corridor's own floor — and a child below every topic is given those whose easiest point is the easiest the catalog has. The corridor chooses among the points of the topic the one whose chance is nearest 0.775, by the rule and with the marker it always had, and a topic is mastered at a level: it returns to the rotation when its recommended point moves above that level, a run completed at the higher level masters it again there, and nothing moves mastery down. A run is spent once it completes, whether it earns mastery or finds the topic mastered already, so the next level takes a run of its own; without that, a topic mastered at `1-2` and carried on a long run would be mastered at `3-4` on the first task of that level it met. The readability limits follow the task's level: the sentence limit of the level as before, and Flesch–Kincaid at the youngest grade of the level plus three, 4, 6 and 8. The package still tells the model the child's grade, as their age, for the words and the plot. There is one rating scale for everybody, on which the number shown is a place on the ladder; the ranks keep their width of one corridor, 166 points, and cover the ladder in eleven steps; and during the trial series neither is shown, only how many of its five tasks are done. — *Why:* the author's decision (О-56). The grade used to decide everything — which topics exist, what a difficulty means, the readability limits and the reference tasks — and that had three consequences. A child for whom the tasks of their grade were too hard had nowhere lower to go: there were no tasks below difficulty 1 of their own level. A change of grade carried the ratings across unchanged, so θ stood too high at the next level; the child was given tasks they mostly failed, and only a run of failures could correct it, with a step already narrowed by the answers behind it. And a topic mastered at a younger level stayed mastered at an older one, where it is harder, and dropped out of the rotation without ever being met there. On one ladder a child moves down when the tasks are too hard and up when they are easy, and the trial series finds the place quickly when the grade entered misplaces them. The spread of one level shift was chosen by simulation, a child answering by the formula of SPEC 2.1. A sweep over the ratings alone, three thousand children a case and twenty answers each, weighed the spreads: at 1.25 a child whose grade was entered a level too high still failed four tasks running in 31 % of cases and a child entered a level too low was still 1.3 off after twenty answers, while at 2.5 those were 17 % and 0.7; a spread of 3.75 bought the first child little, 15 %, and cost both the second child and the correctly graded one more. The simulation kept in `internal/domain/tutor` then runs the rule, the ratings and the profile together on the real catalogs, two hundred children of grade 3 a case, twenty answers each, every child played with the series and without it from the same seed: a child placed a level too high ends the series 0.87 from where they stand against 2.19 without it, and fails four tasks running in 6 % of cases against 50 %; a child placed a level too low ends it 0.92 off against 2.37. The price is paid by the child whose grade was right: 0.84 off after the series against 0.10 without it, and a run of four failures in 6 % of cases against none, because a single slip early in the series moves the estimate a long way — which the test holds to at most 1 and 15 %. A grid rather than Newton's method from the start, because the posterior can have two peaks: five right answers at difficulty 5 of `5-6` from a start at 0 put one near 0.1 and a higher one near 7.7, and a method that climbs from the start stops at the lower. The most likely level rather than the average of the posterior is the author's wording, and the grid finds the highest peak wherever it is. The levels are defined once, in `rating`, beside the shift that places them, and the content and the rule use those: a level is now part of the arithmetic a rating runs on, and two definitions of which levels exist could drift apart. — *Consequence:* the prototype's numbers, SPEC 2.6–2.7 and `ratings.json` stand as they were, because the shift of `1-2` is zero. A child just above a start can be given a point of the level below: a child of grade 3 at θ = 2.79 gets `time.clocks` at difficulty 5 of `1-2`, at P = 0.75, rather than difficulty 2 of `3-4`, at 0.83 — both are in the corridor, the first is nearer its middle, and the grade is not asked. The corridor holds up to two points where the levels overlap. Flesch–Kincaid is stricter than it was for grades 2, 4 and 6 on the tasks of their own level. The profile gains `ratings.start`, a `grade_level` in the brief, in the current task and in every answer of the window — the trial series reads the window back — and `mastered_level` beside `mastered_since`, and θ now means a place on the ladder; none of that raises the schema version, because no file of version 1 had been written by the service when it changed: the tools that write one arrive in T43 and the storage in T50. The fixtures of `testdata/profiles` moved onto the ladder, θ of the children of grades 3–4 up by 2.5. Two of the prototype's five reference briefs no longer match, and the rule's test names them with the reason: `masha`, three answers in, is in her trial series and moves to a new topic instead of going over the one she failed; `petya` is given difficulty 5 of `1-2`, with the traps of that level's reference tasks. The catalogs speak in levels, which reverses R42's "the grade crosses that line and the level does not". — *Rejected:* carrying the rating across a change of grade unchanged, as before, for the reasons above; recomputing θ when the grade changes, which would make a label move a number only answers should move; counting the rating shown from the child's own start, which would give two children at one place on the ladder different numbers; the grade as the boundary of the topics, which is what left a struggling child nowhere to go; a start without a series of its own, which is slow — the 50 % above; Newton's method, above. — *What would change it:* the acceptance runs (T62–T64) showing the levels further apart or nearer than 2.5 — children who do well at difficulty 5 of `1-2` failing difficulty 2 of `3-4`, or finding it a warm-up — or the series moving correctly graded children too far; the shift and the spread are one constant each in `rating`, and SPEC remarks 34 and 35 hold the questions. — *Where it lives:* `internal/domain/rating` (`ladder.go`, `trial.go`, `corridor.go`, `scale.go`), `internal/domain/profile`, `internal/domain/tutor` (the simulation in `simulation_test.go`), `internal/domain/checks/readability.go`, `content`, `testdata/profiles`, SPEC 1.1, 2, 3, 4.1–4.2, 5.5, 7.2–7.3, 8.2, [04-profile](architecture/04-profile.md).

## Content for the model

**R08. Solver templates live in `content/solvers/`, one or two per topic.** A template is a short program following the solver contract, with marked slots for the numbers of the task, generalized from a solver already written for a reference task; the id of that reference task is in a comment. The package builder includes only the templates of the chosen topic and stays within the size budget, and the instructions call a template a sample one may depart from. — *Why:* the solver is the only programmatic guarantee that there is exactly one correct option (PRODUCT 4.3), and an error in it costs the child a whole attempt; a worked-through example of the typical enumeration removes the most common cause of `solver_error` for a weaker model. — *Rejected:* a mandatory skeleton, which would have made tasks bend towards whatever the template can do; and having no templates at all (О-43). The risk of sameness is countered by the rule rotating topics (T27) and by the duplicate check (T32). — *Where it lives:* T36a, T36.

**R09. Text drawing frames live in `content/drawings/`.** A frame is generic, carries no numbers from any particular task, and comes with a structural description of its objects and their relations; the model fills in the numbers and the labels. Every frame passes the format check at the default limits itself — otherwise it is not a frame. — *Why:* the drawing stops depending on what the model happens to remember about box-drawing characters, and the format check (О-11а) passes on the first attempt more often. — *Rejected:* drawing rules in the instructions with no ready-made frames (О-44); free-hand drawings remain allowed and are checked against the same limits. — *Where it lives:* T36b, T36; once the limits are calibrated, the frames are re-checked in T58.

**R16. The child's notes are data, never instructions.** `child.notes` is written by the parent and read by the chat's model, so it travels in the package inside a delimited block that the instructions introduce as information about the child, followed by the rule that nothing inside it changes what the task must be; `save_profile` strips control characters and anything that could close the block, and checks the 500-character cap after stripping. — *Why:* it is the only field in the product written by a person and read by a model, which is the shape of a prompt injection; found in the external review of 04-profile. — *What makes it survivable:* the rule never reads the notes, so a note cannot choose the topic or the difficulty, and the solver decides what is correct — the worst a note can do is steer the tone (О-31). — *Rejected:* dropping the field (it is what lets the model pitch a task at the child); trying to detect instructions in it by pattern. — *Where it lives:* SPEC 4.1.2, [04-profile](architecture/04-profile.md), T36, T43.

**R52. A reference task's solver is a file, not a field.** `content/examples/solvers/<id>.star` holds the program that proves one task's answer; the loader reads it as the task is read and fills `Example.Solver`, and the field is not part of the task's JSON at all, so a `solver` key written there is refused rather than silently ignored. A file naming no task is refused too, because nothing would ever run it — the other half of the pairing, a task with no file, is refused by the bench. — *Why:* SPEC 1.5 originally put the program in the task as a JSON string, and the first fifty showed the cost: every newline escaped, the whole program one line several hundred characters wide, no syntax highlighting, and a change to one constant rewriting the entire line in the diff. The reference solvers are the sandbox's regression suite and are meant to be read and edited for years; a form that makes a one-line change unreadable in review is the wrong form for them, and fifty tasks in is the cheapest moment to say so rather than four hundred and fifty. Naming the file after the task id is what keeps the two halves findable from either side, and it needs no index. — *Consequence:* a solver is no longer visible beside the question it answers, which is what a review needs; `just solver <id>` prints the two together. The tasks' JSON files go back to being data a person edits, with no code inside them. — *Rejected:* keeping the string and living with the diff, which is the cost above paid four hundred and fifty times; `content/solvers/`, which is already the generalised templates shown to the model (R08) and would put two different things under one name; one file per topic holding all fifty programs, which brings back the search for the right one and gives a merge conflict the whole topic to touch. — *Where it lives:* `content/example.go`, `content/examples/solvers/`, `content/solver_test.go`, `justfile`, SPEC 1.5 and 6.8.

**R37. The JSON schemas are the written contract, and Go does the checking.** `content/schemas/` holds `brief.json`, `task.json` and `self_check.json`, embedded in the binary and checked at startup for being schemas at all; what a submitted task is actually measured against is Go — a strict decode that refuses a field the format does not have, plus the explicit checks of T32 and T35. The reference tasks get no schema of their own: the `Example` type and the loader in `content/` are their format. — *Why:* a schema library would have to earn a dependency, and here it would buy the weaker half of the work. The checks that matter — five options a child can tell apart, a distractor for exactly the four wrong ones, a trap from the catalog, a level the topic is taught at — are not expressible in JSON Schema, and the refusal a model is sent has to name what to fix in words it can act on (SPEC 5.9), which a schema error is not. The schemas stay because they are the one place the three formats are written down in full, and because a later consumer — a tool description, a generated document — needs them machine-readable. — *Consequence:* the schemas and the Go types can drift, and nothing but review catches it; they sit next to each other in the same package for that reason, and a format change touches both in one commit. — *Rejected:* `santhosh-tekuri/jsonschema` or `kaptinlin/jsonschema` as the single source of truth, which leaves the catalog and option checks in Go anyway and so buys two validation paths instead of one; dropping the schemas, which SPEC 4 requires to be in the binary. — *Where it lives:* `content/schemas/`, `content/`, T23, T32, T35.

**R72. A solver template searches only what the question leaves open, and every program runs under the one step budget.** A number the question gives stands at the top of a template as a capital like any other, and one it leaves out is `None` there and is tried at every value it could take; the search then walks the unknowns alone. The template of three groups works this way for those in all three and for each pair, as the one of two groups does for the size of a group. — *Why:* tried over every overlap, three groups cost the fourth power of the smallest one: a class of sixty took 59 million steps against a budget of 25 million, and a school of a hundred asked `product` for more than the million elements it will build. A question of this kind almost always gives the pairs or those in all three, and each number given takes a loop out: with every pair given, three hundred pupils take 24 thousand steps. — *Consequence:* a question that gives none of the overlaps still searches all four, which takes a third of the budget for a class of sixty and more than twice the budget for a school of a hundred; there the model is told that the solver ran out of steps and to count the cases rather than list them. — *Rejected:* a step budget of its own for a template, which would bind nothing, because the model writes its own program from a template and the budget is what guards an instance every request shares; raising the budget for everyone. — *Where it lives:* `content/solvers/logic.sets/three-groups.star` and `two-groups.star`, `content/solver_test.go`.

## Task checks

**R10. The explanation behind a wrong option is checked deterministically, with no judgement of meaning.** Four conditions: the texts of the four distractors are pairwise distinct; a text neither equals nor is a prefix of the solution or the hint; a text is not the verbatim description of the trap from the catalog; and a text is not shorter than the minimum for its writing system (words, or characters for CJK and Thai). A rejection gets its own code and points at the explanation that needs fixing by its trap, never by its option's letter (R57). — *Why:* "a wrong answer is a diagnosis" is one of the three pillars of the product (PRODUCT 1), and in text mode the explanation is the main thing the child gets. — *Rejected:* instructions and reference tasks alone with no programmatic check; and any heuristic for "meaningfulness" — with a median generation time of 69 seconds, extra strictness costs the child another attempt (О-46). — *Where it lives:* T32a; the rejection code is defined in T12.

**R44. The solver's contract is a domain package and the interpreter is infrastructure.** `internal/domain/solver` holds the statuses, the five option texts, the shift that relabels them, the comparison a computed answer is looked up by, and the rule that turns two runs into one verdict; it declares a `Runner` interface of one method. `internal/infra/starlark` is what implements it. — *Why:* what two runs mean together is the whole point of the check, and it is arithmetic over two results — it can be written down, read and tested with no interpreter anywhere near it, which is what its properties do against two fakes of four lines each. It also keeps the dependency rule honest rather than aspirational: nothing under `internal/domain` may import `go.starlark.net`, and the linter says so. — *Rejected:* one package under `internal/solver`, as the line in RUN.md first said, which would have put a rule of pure arithmetic behind an embedded language and made every test of it a test of the sandbox as well; leaving the two runs to the pipeline of T35, which would give the bench of T29 no way to run a reference solver the way a submitted one is run. — *Where it lives:* `internal/domain/solver`, `internal/infra/starlark`, `.golangci.yml`, RUN.md T28.

**R45. Everything the sandbox predeclares caps itself at a million elements and charges the step budget for them.** *(Its price is overtaken by R125: what a built-in builds is paid a step for every sixteen bytes rather than a step for every value, so the step ceiling bounds what the built-ins of a run keep.)* The cap and the charge cover our own helpers and twelve built-ins of the language besides — `list`, `tuple`, `sorted`, `set`, `dict`, `reversed`, `zip`, `enumerate`, `min`, `max`, `any` and `all` are declared again with the cap on them — and the charge happens before the call does any work, so a call nothing could pay for is refused rather than half-built. The ceiling and the price are counted differently: the ceiling counts the elements of the list a solver ends up holding, and the price counts the values inside them, so a hundred thousand tuples of twenty costs two million steps rather than a hundred thousand. — *Why:* the interpreter counts its own instructions and looks for a cancellation only between them, so neither the step budget nor the clock can reach inside a single call. A lazy range is the way in: `range(1000000000)` costs nothing to make, `list` of it is sixteen gigabytes built where nothing is watching, and `min` of it is ten seconds of Go with both limits asleep. The length is known before the walk starts, which is what makes a refusal possible at all. — *Consequence:* the operators stay open. `[0] * 100000000` allocates through the language's own `*`, where there is no name to stand in front of, and starlark-go's own guard there stops only at 2³⁰ elements — more memory than an instance has — so a solver written that way takes the instance down rather than the request. There is no power operator in this dialect, which closes the other half of the same hole, and nothing else turns something small into something huge in one step. The budget counts elements and not digits, so `sum` and `prod` also read the run's clock as they walk (T39a.2): whole numbers grow as they are multiplied, and a product of a hundred thousand of them ran four seconds past a two-second limit inside one call, where a loop written out by hand would have been stopped between its steps. — *What would change it:* the gap ever being seen in the aggregate log; the fix is a solver in a process of its own with a memory limit on it, which is a change of shape rather than a setting. — *Rejected:* capping `range` itself, which would forbid a loop of two million iterations that the step budget pays for happily; charging a list of tuples by its length alone, which reads simpler and lets a product of nineteen pairs through — half a million tuples, ten million values and a hundred and sixty megabytes, against a ceiling that saw five hundred thousand; a memory limit in Go, which has none per goroutine — `debug.SetMemoryLimit` makes the collector work harder and refuses nothing. — *Where it lives:* `internal/infra/starlark/vocabulary.go`, SPEC 6.5 and 6.6.

**R46. A recursive solver is `error`, not `bad_source`.** The dialect keeps the recursion check on; the check belongs to the interpreter and fires when the recursive call happens, not when the file is parsed, so the status is the one for a program that failed while running. — *Why:* the alternative is to promise the parser catches something the parser does not look at. A pass over the syntax tree before the run could name the direct case, but a name in Starlark can be reassigned — the dialect allows it — so the pass would be an approximation that still does not replace the check underneath it. The model reads the same sentence either way, because every status reaches it as one refusal; the status is read by the aggregate log, and there "it failed while running" is exactly what happened. — *Rejected:* the pre-pass above; matching on the text of the library's error, which is the library's to reword. — *Where it lives:* `internal/infra/starlark/dialect.go`, SPEC 6.3 and 6.4.

**R48. A helper refuses what the solver got wrong rather than quietly mending it.** A string handed to a helper expecting a sequence is refused, and so is a date that never happened — the thirtieth of February, a thirteenth month, a year outside the four digits. Each refusal says what to write instead. — *Why:* both mendings are available and both are worse. This language does not iterate a string, so a helper that accepted one would teach a second rule that holds nowhere else in the dialect, and the model would learn the wrong one; the porting table of SPEC 6.8 carries the one line it costs instead. A month of thirteen is January of the year after, and answering about it would give a solver a confident wrong number — the one failure this whole check exists to catch. — *Rejected:* taking a string as its characters, the way Python does, for the reason above; normalising a date the way the standard library does by default, which turns a solver's bug into a plausible answer. — *Where it lives:* `internal/infra/starlark/calendar.go`, `internal/infra/starlark/vocabulary.go`, SPEC 6.5 and 6.8.

**R53. The step ceiling is 25,000,000, and the memory it lets through is the price.** *(Its measure of what the helpers let one run hold is overtaken by the load of T52a.3, R124: products of pairs hold 824 MiB at this ceiling, more than twice the 381 of the two products of nineteen measured here; SPEC remark 63. Settled by R125: the helpers pay for bytes, so at this ceiling what they keep is at most 381 MiB whatever they build, and the costliest reference solver is 2,413,617 steps under that price.)* `MATHTRAIL_SOLVER_STEPS` defaults to twenty-five million, up from ten; the time limit stays at two seconds. — *Why:* SPEC 6.6 asks for a ceiling an order of magnitude above the costliest reference solver, and the bench over all 450 measured that one at 2,081,362 steps — ten million was under five times it. Three of the prototype's checks, transcribed as they stood, did not fit ten million at all, and a model's first draft looks more like a transcription than like the rewrites SPEC 6.8 describes. Time is not what limits it: at the measured rate twenty-five million steps are some four hundred milliseconds, against two seconds a run. — *Consequence:* the step budget is also the only thing that bounds memory (R45), so the bound moves with it. Measured on one run: what the helpers build rises from 190 MiB to 381 MiB — the product of nineteen pairs that R45 was written to refuse now passes, twice — and a loop of appends from 129 MiB to 326 MiB, on an instance of 512 MiB that runs up to four solvers at once. The same measurements found that the operator gap R45 accepts is wider than it says: `xs = xs + xs` in a loop reaches 480 MiB in under three hundred steps, at any ceiling. Nothing runs a submitted solver yet, so neither is reachable today. The review of T39a.2 found it wider again: the methods of the values themselves take a lazy range of any length in one step — `x.extend(range(3000000))` is nineteen steps, `x += range(3000000)` eighteen and `set().union(range(3000000))` twenty at the default budget, three times the million the helpers refuse, and a billion is as cheap to ask for — so no cap on the helpers can close the gap, and only a limit on the memory of the process can. Time has the same gap inside a single call: the clock is seen only between instructions, the step budget counts elements rather than their digits, and a list of a million copies of one number with a hundred thousand digits, which appending pays for honestly, keeps `sorted` or `set` busy for minutes; a process of its own would bound its time as well as its memory. — *What would change it:* the tools that first run a submitted solver (T41–T45) are where memory has to be settled, because that is when the gap becomes reachable from outside. Two shapes are on the table: a separate allowance for what the helpers build, kept at ten million values while the steps stay at twenty-five, which restores R45's bound for the helpers and nothing else; or the process of its own with a memory limit that R45 names, which closes the operators too. — *Rejected:* keeping ten million and relaxing the rule of SPEC 6.6, which would leave a model's ordinary first draft refused for being ordinary; making the two costliest reference solvers cheaper, which would hide the distribution the ceiling is calibrated on. — *Where it lives:* `internal/config/config.go`, `internal/telemetry/solver.go` (the buckets reach the new ceiling), SPEC 6.5, 6.6 and remark 15.

**R54. The near-duplicate check is pg_trgm reproduced, and the fingerprint is fixed for good.** `internal/domain/checks` cuts a question the way Postgres's `pg_trgm` does — lowercased, split on anything that is neither a letter, a digit nor a mark, each word padded with two spaces in front and one behind, the set of its trigrams — and compares two sets by their Jaccard index. A question whose task is in a language written without spaces — or, with no language, one most of whose letters are in the scripts written so — is cut into padded character bigrams instead, and what it is compared with is cut the same way. The reference tasks are compared by their texts; the child's past tasks by a MinHash sketch of the same set: FNV-1a of each shingle, xor-ed with a hundred and ninety-two seeds that step by the golden ratio, spread by the SplitMix64 finaliser, the smallest kept per seed and its lowest four bits stored, two to a byte — 96 bytes in standard base64 — and the share of agreeing positions taken back by the one in sixteen that agree by chance. A sketch that does not decode to 96 bytes is skipped, and each of the two sources is reported once however many of its entries a question resembles. — *Why:* the threshold was chosen with Postgres's numbers, so the measure has to give those numbers, and it does: the fifteen exported pairs, the fifty most alike reference pairs and all sixteen buckets of the nearest-neighbour distribution match `trgm_similarity.json`. The last took one detail that is not about the measure — the export read single-precision values as their shortest decimals, and a similarity of exactly 0.65 or 0.70 falls into one bucket or the next depending on it. The sketch is fixed because the profile keeps it: two hundred of them per child, compared against for as long as the file lives, and a sketch made any other way agrees with them nowhere — the service would stop noticing a repeat of anything given before the change and say nothing. A test pins two sketches as literals for that reason, and it is not to be regenerated. The sketch was replaced once, before any profile kept one: it began as sixty-four one-byte positions, whose error of about 0.06 let the same task given new numbers in Russian — 0.74 alike against 0.7 — slip under the threshold about one time in five; a hundred and ninety-two four-bit positions err by about 0.03 in 128 characters of base64, which two hundred of them can take and leave the profile inside its 64 KB target (T39a). — *Consequence:* a change of how sketches are made needs a way to carry the old ones; a changed threshold needs nothing, because a sketch is compared, not judged. **R71. A run that stops at a `%` format Starlark cannot fill is told so.** When a run fails, the sandbox takes the position the interpreter stopped at from the top of its call stack and looks at the source there. If that is a `%` whose left side is a string written out, or a name the program binds once, at its top level, to a string written out, and Starlark cannot fill that string — a stray `%`, a width or a precision, a number of values it does not ask for, a key with no dictionary to find it in — the run is `bad_format`, and the model is told, in a sentence of the service's own, how `%` is written in this dialect. Any other failure stays `error`. The guide lists `%` among the differences from Python that bite. — *Why:* models write Python, whose `%` has widths and precisions, and a task about percentages puts a `%` into every message. The interpreter's own sentence, "unknown conversion", never reaches the model (R62), so such a run was told only that the solver failed while it ran, which sent the model looking through its logic for a mistake in a string. A position is exact where the library's sentence is not: it is the operator the run could not carry out, and reading it ties the verdict to the source rather than to wording the library may change, just as the limits are read from the budgets. — *Consequence:* a stray `%` that a run never reaches — in a `fail()` for a case that does not happen — costs nothing, and the program still proves its answer. A string put together while the program runs is not read, and a run that stops at one is `error`. The programs the content ships are held to the same check throughout, reached or not, because models copy them; their names are bound the way a run binds them, so a local that shadows such a name, or a function of the program's own named after a built-in, is not taken for it. — *Rejected:* escaping `%` in the model's program, which cannot tell a percent sign from a conversion and would change a program the model wrote; checking before the run, which would refuse a program that proves its answer over a string it never reaches, at the cost of an attempt of the child's (R59); reading the interpreter's message. — *Where it lives:* `internal/infra/starlark/format.go` and `classify.go`, `internal/domain/solver/solver.go`, `internal/domain/checks/answer.go`, `content/instructions/task_writing.md`, `content/format_test.go`, SPEC 6.3, 6.4 and 6.7.

**R78. "Another task" before an answer is how a child walks past a task they do not like, and punishing that would punish a stray tap; but leafing through hard tasks until an easy one comes shows only in what the parent can see, and a skip that left no trace would hide it. — *Rejected:* counting a skip as a wrong answer, as "I don't know" is (R93); leaving it free and unseen, as before. — *Where it lives:* SPEC 2.2, 3.2, 7.3 and 8.2, `docs/architecture/03-flows.md` and `04-profile.md`, RUN.md (T44, T57).

**R99. The tools of the profile: what they say, and when they write.** `get_profile` and `save_profile` answer with the child's details — the parent's notes among them — how far the trial series has got, and a short recommendation, `{topic, grade_level, difficulty, goal}`, taken from the rule's brief; the plot, the traps and the rule's reasoning reach the model with `next_task` alone. `get_progress` and `read_progress` answer the same progress (R97), with the details the progress screen shows and without the notes; the domain package `progress` works it out from the profile and the catalog each time, and "mastered" there is the rule's own `tutor.Mastered`, held at the level the topic's tasks now come from. `save_profile` makes an edit: a field left out stays, a list given replaces the one kept, an empty `notes` or `ui_language` clears it; text is cleaned — control characters dropped, and those that show nothing or reorder the text; any space read as a plain one — before its cap is counted (R16), and in the words the model reads whatever the parent wrote — the pseudonym, the interests, the notes — stands in quotes, a string of JSON apart from every sentence of the service's; the language is kept as a canonical BCP 47 tag of at most 35 characters that names its language outright; skills are ids of the catalog, and a profile may leave out all 25 of them; lists are written as `[]`, never null. Details that break a rule are refused as an answer, `status: rejected` with `code: invalid_profile`, one problem per field naming the rule and never the value — a count of how far off it is, and the place of a skill the catalog does not have in the list as it was sent; an edit that asks for what is already there writes nothing, and a call that names no field is answered with the profile as it is. A save that lost to a write made in between is a failure with a sentence of its own, and is not retried here. The store's other refusals — a damaged file, one from a newer build, access taken back — are told in the general sentence until T51 gives each its own, and the progress carries no misconception map until T57a builds it. Until profiles live in the parent's Drive (T50), the container keeps them in the memory of the process. — *Why:* the author's decisions on the notes — the model reads them back to the parent who wrote them, and no screen the child sees draws them — and on the cap, which was the size of the catalog when the catalog had fifteen skills; the rest keeps the tools cheap and honest: a write only when something changed, a refusal the model can act on field by field, and no word of a parent's text in anything that goes further than the answer. — *Rejected:* the whole brief as the recommendation, which a card has no use for; a refusal of a call that names no field, which costs the model an error to fix for nothing; the limits in the input schema, whose library quotes the value that broke them; a retry of a lost save here, which belongs to the store that loses it (T51). — *Where it lives:* SPEC 4.1, 5.9, 7.2, 7.3 and remarks 5, 28, 30, 36 and 42, `docs/architecture/04-profile.md`, RUN.md (T43).

**R100. The tools of a task: what they take, what they say, and when a request is over.** `next_task` takes the language of the chat, which is required: a call without it is refused by the protocol library, and one whose language is empty or names none by the tool — there is no fallback to a host's locale or to the cards' `ui_language`. The language is read as `ui_language` is, a canonical BCP 47 tag that names its language. The model may set a topic, a level or a difficulty of its own with a reason of at most 300 characters; everything it passes is checked by the rule, and what breaks a rule is refused as an answer, `status: rejected` with `code: invalid_arguments`, one problem per argument naming the rule and never the value — a level named alone is held to the rule's topic, which the refusal names — and a reason with no choice chooses nothing and is not kept. The request opened is kept in the profile with a new id, and the package goes to the model in the words of the result alone, never in the payload a card is drawn from. While a request is younger than the window, `MATHTRAIL_REQUEST_WINDOW`, fifteen minutes by default and never under one, `next_task` hands it back as it was, with the package again, `already_open` and its age, applies none of its arguments and writes nothing; past the window the request is abandoned: the next `next_task` replaces it and a task handed in for it is stale. A task left on the card without an answer is recorded as skipped when the next one is asked for (R98). `submit_task` takes no language of its own — the task is written in the request's, and the checks read it from there — and takes the brief, the task and the self-check as whatever JSON arrives, read by the structure check in its own words. Its solver runs before the profile is read (R61); a task for no request that is open spends nothing and writes nothing, and its card shows the task the child already has when there is one, so that a task handed in twice cannot turn the card the child is working on into a wait. An accepted task is the one the request asked for — its topic, level, difficulty and language are the request's, not the model's to say again — and its answer, its traps and their explanations, its solution and its program are sealed together; the card is handed only what a child may see. `task_submitted` is written for every task that was judged; a stale one leaves none, only its `tool_call` and the `solver_run` lines of the runs it cost. The review is two spans under the call, `examine_task` with the solver's runs under it and `judge_task`, opened by the transport, so that the checks stay free of anything that watches them. — *Why:* the author's decision on the language: a task in a language guessed is a generation wasted, and a guess that is sometimes right hides the model that never passes it. The rest keeps one source for each fact — the request for where a task stands and what language it is in — and makes every "only once" of 03-flows a field of the profile rather than a hope about the model. — *Rejected:* the fallback of SPEC 7.5 as it stood; a `language` argument of `submit_task` beside the request's, which would leave the question of which is right; the limits of `next_task` in its input schema, and the parts of a task typed there, whose library would quote back what broke them (remark 36); the package in the payload, which a card is drawn from; a stale task shown as a wait over a task the child is still solving. — *Where it lives:* SPEC 3.4, 4.1, 5.9, 7.2, 7.3, 7.5, 11.2, 12.2, 12.5 and remarks 29 and 36; `docs/architecture/03-flows.md`, `docs/architecture/04-profile.md`; RUN.md (T44).

**R101. The tool of the answer: what it takes, what it says, and when it writes.** *(Only an answer recorded here is told again: R126 seals the task anew with the letter it was given.)* `submit_answer` takes the task's id, the answer and `hint_used`, which is false when left out. The answer is read as a child or a model types it — a letter in either case, with the spaces around it dropped, or `?` for "I don't know" — and anything else is refused by the tool, `status: rejected` with `code: invalid_arguments`, naming the rule and never the value. The profile judges the answer, not the tool: the sealed part of the task says whether a letter is right and which trap stands behind a wrong one, and `?` is a wrong answer that chose no option and took no trap (R93), so its entry in the window is `confused`, never right, with no `chosen` and no `trap` — and the profile and its schema refuse one that says otherwise. The answer is recorded once. The task stays on the card with the answer it was given — the choice, the hint, the level in the topic before and after, and which answer of the trial series it was, as `current_task.answered` — until the next task is asked for; the same task answered again, from a second tab, after a reply lost on its way, or by the model after the card, opens the seal again and is told the same result word for word with `already_answered`, and nothing is written and no line is left. `next_task` takes an answered task off the card with nothing recorded — it is no skip — and a task handed out over one replaces it the same way. An answer to a task that is not on the card is `status: stale`, `code: stale_task`, on the `task` screen: the card that sent it stays on its task, and the words say what is on the card now without repeating an id the profile does not know — and, for a task whose answer the window keeps, that the answer is recorded, lest the model tell the child it was lost. A task whose seal can no longer be opened is taken off the card, the profile written, and the model told in a failure of ours with a sentence of its own, error `sealed`: no answer is recorded, and no skip, since the child did not leaf past it; a task that had its answer before the seal was lost is told in a second sentence that the answer counts and only telling it again is gone. The result is the same in both modes — `screen: result`, and `result` with the choice, whether it was right, the right option, the trap as `{id, text}`, the solution, the hint and the rating in the topic before and after, or how far the trial series has got — and the words tell the model how to explain it, around the task's own texts, quoted. `answer_recorded` is written once the file holds the answer and carries the version of the instructions the task was written to; the topic, the trap and that version come from a file a person can edit, so the line holds the first two to the catalog and the version to the shape of the service's own, `other` otherwise; the span `record_answer`, under the call, says whether the answer was right and names the trap by its catalog id, and nothing else — no letter, no pace, no rating. A write that lost to another is the failure of R99 and is not retried here: the same call made again finds the answer recorded, or records it. — *Why:* 03-flows asks for exactly this — the first call records, any later one returns the same recorded result and writes nothing — and the right option, the trap and the solution live only in the seal, which used to leave the file with the task, so nothing could tell the result again; a card whose reply was lost, or a second tab, has to be able to draw its result. The author chose the kept answer over a shorter telling. The answered task leaves at the next ask rather than at the next hand-out, so that a lesson never holds an answered task beside an open request. Judging in the profile makes an entry that is both "I don't know" and right impossible to build rather than merely refused. — *Rejected:* telling a repeated answer from the window — right or wrong and the letter, with no right option and no solution — which leaves a card that lost its reply with no result to draw; refusing it as the prototype did, which breaks 03-flows and the tool's idempotence; keeping the answered task until the next one is handed out; the answer held to a list in the input schema, whose library quotes back what broke it; a measurement of answers, which the line already counts; recording a task whose seal is lost as skipped. — *Consequence:* the answered task keeps its open part and its seal in the file until the next ask, no larger than while it was being worked on. `current_task.answered` is optional and did not raise the version: until T50 no file is shared between builds, and T50 decides whether what an older build would make of it — an answered task recorded as skipped as well — is a version and a migration or a window written down (SPEC remark 44). The instructions tell the model to record "I don't know" as `?` and that recording twice returns what was recorded. — *Where it lives:* `internal/domain/profile/answer.go`, `task.go`, `request.go`, `validate.go` and `profile.schema.json`; `internal/transport/mcp/submitanswer.go`, `submittask.go`, `events.go` and `failure.go`; `content/instructions/mcp_instructions.md`; SPEC 5.9, 7.2, 7.3, 7.4, 12.2, 12.5 and remarks 36, 43 and 44; `docs/architecture/02-auth.md`, `03-flows.md` and `04-profile.md`; RUN.md (T45).

**R102. `next_task` answers in words alone.** Its result has no payload, and the tool declares no output schema: a short paragraph for the model — which request is open, in which language, that the task is the model's to write and is handed in with its id, and the last recorded answer — and then the package. A request already open comes back the same way, saying since when; its words ask for the task if the model has written it, and only then offer the package to a model that has not — a turn cut short, say. They no longer say the task is being written: to a model that has not written one, that reads as the service at work. Two chats writing for one request at once remain possible, and share its three attempts until one task is accepted; after that the other is stale and spends nothing. A refusal is the one exception: it keeps its small payload, `screen`, `last_answer`, `status`, `code` and `problems`, because its status is what marks it a refusal, for the model and in the log. — *Why:* the local run in Claude Code 2.1.280 found that a host may show the model a result's payload in place of its words. The model received `{"request_id": …, "screen": "waiting"}` and never the package, took the task for something the service was preparing, and asked for it fifteen times in thirty seconds without writing one. The words were the only place the package travelled (R100), and the payload of `next_task` has no reader but the model, since no card is drawn from it. The author chose words alone over the package in the payload. — *Rejected:* the package in the payload, with the words the same JSON — safe, since `next_task` draws no card, but it undoes the rule that no payload ever holds the package, which is the simplest way to be sure no card ever shows one; the words of every tool carried in its payload as well — the sturdiest against such hosts and the largest change, left until T63 shows whether ChatGPT needs it (SPEC remark 45). — *Consequence:* `next_task` is the one tool without an output schema (SPEC 7.1); `request_id`, `already_open` and `age_seconds` leave the payload, and the words say them, the last answer among them. The frame still reads a refusal's status from its payload. The other tools' guidance words do not reach a model in such a host: it acts on the payload, the server's instructions and the tools' descriptions — as much of each as the host keeps (R103). — *Where it lives:* `internal/transport/mcp/nexttask.go`; SPEC 7.1, 7.3 and remarks 16 and 45; `docs/architecture/03-flows.md`; `docs/live/04-local-run.md`; RUN.md (T46).

**R103. The rules of a lesson come first in the instructions, within 2,048 characters.** The server's instructions open with a section of their own, "Always", that says what must hold in a lesson whatever the host: a pseudonym only, and never in a task; the language of the chat, and wording that does not show whether the child is a boy or a girl; the answer, the solution and the explanations kept until the child has answered, and the hint given only when asked; the answer recorded before anything is explained, "I don't know" as `?`; a wrong answer explained from its trap's text, with the right option at the end of the solution; the next task asked for only when the child wants it; and `last_answer` read before the current task is spoken of. The instructions up to the end of that section are at most 2,048 characters long, and the sections after it say how. Every tool's description is at most 2,048 characters as well, so `next_task` lists the topics by id with the levels each is taught at, as SPEC 7.2 has it, and no longer with what each topic is. — *Why:* the local run in Claude Code 2.1.280 found that a host may cut them: it keeps the first 2,048 characters of a server's instructions and of each tool's description, and marks the cut "… [truncated]" (SPEC remark 46). The instructions were 5,298 characters long, and the model was given the child, the profile and the start of how a task is asked for, and nothing about the answer or the next task: it asked for the next task after every answer on its own, and explained a wrong answer from the right option as often as from its trap. The words of `submit_answer`, which say the same, do not reach a model in that host either (R102). The description of `next_task` was 2,780 characters long and lost the topics at the end of its list. With the rules first, the model stopped after every explanation and waited to be asked, and began the one wrong answer of the run from its trap. — *Rejected:* raising the limit for the local runs, which tests a host nobody has; the whole instructions cut down to 2,048 characters, which takes from the hosts that read them whole what only a host that cuts would lose; the rules carried in the payload of every result, the larger change R102 left until T63 shows whether it is needed. — *Consequence:* each rule is said once, in "Always", and the sections below say how a lesson goes; a model chooses a topic of its own by the id alone, and the package describes the topic it writes on. A test of the content holds "Always" to be the first section and to end within the length, and the test of the tool listing holds every description to it. — *Where it lives:* `content/instructions/mcp_instructions.md` and `content/content_test.go`; `internal/transport/mcp/nexttask.go`, `profile_test.go` and `task_test.go`; SPEC 7.1 and remarks 28, 45 and 46; `docs/live/04-local-run.md`; RUN.md (T46).


## Configuration

**R18. Viper reads the configuration, and nothing but the environment feeds it.** `internal/config` declares every variable once — name, default and type — and unmarshals it into `Config`; `Validate()` then refuses with a message that names the variable. No file, no remote source and no flag is registered. — *Why:* the author's decision, reversing the earlier "no Viper" note in CLAUDE.md. The table of SPEC 11 grows to around twenty variables as the sign-in, the limits and the solver arrive, and hand-rolled parsing grows a branch per type as it goes; Viper keeps that in one declaration and matches how the platform's other services read their configuration, so a person moving between them reads the same code. — *Rejected:* `os.Getenv` with hand-written parsing, which is what this replaced; registering a config file "for later", which would quietly break the rule that a deployment is configured by its environment alone (PRODUCT 6). — *Consequence:* an empty variable reads as unset, because Viper's `AllowEmptyEnv` stays off — the one behaviour worth knowing when a deployment sets a variable to the empty string and expects it to override a default. — *Where it lives:* `internal/config`, SPEC 11, CLAUDE.md ("Config").

**R19. gin serves the HTTP surface, and it stays in `internal/transport/http`.** The router, the handlers and the middleware follow the shape of the platform's other services: a handler is a struct with its dependencies and a constructor, a route is one line in `NewRouter`, an error answer is `apierror.Response` wherever no protocol prescribes a shape of its own (OAuth answers with `error` and `error_description`, JSON-RPC with its error object), and every request passes a request id, a panic recovery and a request log. — *Why:* the author's decision. The surface grows to the MCP endpoint, five OAuth endpoints and three metadata documents, each with its own middleware needs; routing groups, parameter binding and one recovery path are worth more than the standard multiplexer once that is true, and a person moving between this service and the others reads the same code. — *Consequence:* the domain packages must stay free of it — the linter denies `gin` and `net/http` inside `internal/domain`, which is the one place this service deliberately differs from the reference. An `http.Handler` from the MCP SDK mounts with `gin.WrapH`. — *Rejected:* `net/http`'s multiplexer, which is what this replaced; handlers inside domain packages, as the reference does it. — *Where it lives:* `internal/transport/http`, `.golangci.yml`.

## Limits and storage

**R15. A ceiling on failed generations, separate from the daily limit.** *(Set in T52: `MATHTRAIL_DAILY_FAILED`, five by default, checked in `next_task` beside the tasks of the day — R121.)* `daily.failed` in the profile counts requests that ended in `attempts_exhausted`, and `next_task` refuses with `limit_reached` once it reaches its ceiling — five a day by default, the number set in T52. — *Why:* О-35 deliberately makes a refusal cost nothing, which alone leaves a model that keeps failing the checks free to loop — three refusals, a new request, three more — with only a per-instance rate limit in the way (О-24). Each round costs the family a turn of a free-tier chat limit and six Drive calls; it costs us no tokens at all, since the service makes no LLM calls (PRODUCT 4.3). Found in the external review of 03-flows. — *Rejected:* charging the daily limit for refusals, which would redefine О-35 and make a bad model cost the child their lesson; leaving the loop to the rate limit alone. — *Where it lives:* SPEC 5.10, [03-flows](architecture/03-flows.md), [04-profile](architecture/04-profile.md), T43, T52.

**R17. The profile is recovered through pinned revisions, and pinning has two triggers.** *(Amended by R119: Drive lets go of a revision kept forever only by deleting it, so the first write of a day alone is kept, the earliest past a hundred are deleted, and a recovery keeps each revision it reads.)* A damaged file is recovered from at most five revision bodies: the four newest **plus the newest pinned one**. Pinning fires on every fiftieth write by our own `revision` counter **or** on the first write of a new day, seen from the `updated_at` already in the file. — *Why:* Drive purges unpinned revisions at a hundred, which is about a day and a half of use, so the pinned snapshot is the one guaranteed to exist — and a recovery that only looked at the last five would step straight past it after six broken writes in a row. The calendar trigger exists because a write lost in the write race takes its revision number with it, and a trigger that fires only on an exact multiple can miss. Found in the external review of 05-storage. — *Rejected:* pinning every write (200-pin ceiling, and the parent's storage quota); a deeper recovery window (more bodies fetched on a path that is already rare). — *Where it lives:* [05-storage](architecture/05-storage.md), T51.

**R80. The store is one contract: an explicit account, a revision only the store reads, and an export that is a place.** *(T51 kept `Load` as it is: a damaged file put back is told as `ErrRestored`, and two files by the export. The fifth operation is `StartOver`, and restoring from the bin stays the parent's, in Drive — R118 to R120.)* `internal/store` declares `Storage` with four operations; a fifth is agreed for T51, below. `Load` answers the profile and the revision it was read at. `Create` keeps the first profile of an account, and refuses an account that has one, readable or not. `Save` writes only over the revision it was computed from, and never creates. It also takes only a profile whose own `revision` is one past the stored one, which is the touch every write carries: 05-storage pins the history by that number and notices an early read by it, and the store is the one place every write passes through. A store checks this without reading the file again, since the revision it handed out can carry the number. `Export` answers a `Location`: the folder, the file and a link. There are four refusals: `ErrNotFound`, `ErrConflict`, `ErrCorrupted` and `ErrAccessRevoked`. Every call names its `Account`, made by `NewAccount` from the identifier the sign-in derived and the Google access token that opens the parent's Drive. The token sits behind a pointer that nothing outside the package can name, so no printing at any depth and no JSON reaches it, and an account prints as its identifier in whatever verb it is asked for. Accounts cannot be compared: two made alike hold different pointers, so the compiler refuses `==` rather than let it answer false. Two refusals come before anything is looked at. An account that names no one is refused by every operation, whatever its token would open, so that a call which lost its identity on the way in cannot reach anybody's profile. A profile that breaks its own rules is refused wherever it was aimed. A `Revision` is a string that only the store that issued it compares. Damage is decided once, in `store.Parse`, for every store. A file that is not JSON, is not a profile, or has an older shape this build has no way up from is `ErrCorrupted`, with its cause beside it. A file from a newer build is not damage and keeps `profile.ErrNewer`. The store in memory keeps the bytes `profile.Marshal` writes and reads them back through `store.Parse`, so it validates, copies and classifies exactly as the store in Drive will; checking a revision and writing are one step under its lock. `internal/store/storetest` holds every store to the same cases. The contract lets two racing saves both land, because a store that can compare revisions only before it writes cannot promise more ([05-storage](architecture/05-storage.md), "Two tabs"). — *Why:* the tools arrive before the store in Drive, so the operations they are written against have to hold once Drive is behind them. Starting over in place of a file nothing can read becomes a fifth operation, as agreed with the author after T40. It arrives with the store in Drive in T51: the damaged file is set aside and never deleted, and it is marked as set aside instead of as the profile. A new profile takes its place, both stores implement the operation, and `storetest` holds them to it. Whether restoring a file from the bin at the parent's request is also an operation of the store is left for T51 to decide. Until then `Create` refuses to replace any file at all. The credential travels in the signature and not in the context, because the context would hide what a call cannot work without. The export is the file itself, as 05-storage has it, and a store with nothing to open answers the zero location. Keeping bytes rather than a pointer makes the store in memory faithful at no cost, and a single shared contract is what makes the two stores interchangeable rather than merely similar. — *Rejected:* a user identifier alone, with the token read from the context. An export that hands over the file's contents, which would be the second copy 05-storage rules out. A result struct in place of the three results of `Load`: the notices T51 needs ("two files were found", "restored from the revision of that date") may extend `Load` then, and a mechanical change at every call is cheaper than a struct that nothing fills yet. Running the suite a second time so that its own lines count as covered: the lines that report a failure never run in a passing test. `storetest` is test code in a package of its own: `codecov.yml` leaves it out of the coverage, and `sonar-project.properties` counts it among the tests, as it does a `_test.go` file. The total that `just ci-test` prints still counts it, because Go reports a package without tests of its own as uncovered. — *Where it lives:* `internal/store`, `internal/store/memory`, `internal/store/storetest`. T43–T45 use it. T50–T51 implement it for Drive, add the fifth operation with its case, and add revoked access to the suite.

**R115. Drive is reached through a thin client of the service's own, and the store of profiles in Drive stands on it.** `internal/infra/drive` makes the five calls the store needs — a search by one of the service's own properties, the name of a file, what a file holds, a new file or folder, and new content for a file — each as one request to Drive's HTTP API v3, with the parent's token, asking for the fields the caller reads and no others, within `MATHTRAIL_DRIVE_TIMEOUT` (10 s by default, SPEC 9.2), following no redirect and reading at most 1 MB of an answer. Drive's refusals become six sentinels: no such file (404), the token not taken (401), a pause asked for (429, or 403 with `userRateLimitExceeded`, `rateLimitExceeded` or `dailyLimitExceeded`), a full Drive (403 with `storageQuotaExceeded`), Drive not answering (a 5xx, no answer, or an answer that breaks off or does not read as Drive's), and a file larger than the caller would read. A call its caller gave up on stays the caller's own and is none of them. A call about a file names one, or it is not sent — as it stands it would reach the address of the search — and an answer about a file says which file it is, or it is Drive not answering. Every answer is read to its end, so that its connection carries the next call. Any other refusal is told by its status and Drive's reason, a word of Drive's list. No error carries the address of a request, Drive's own sentence or the token: the address and the sentence name the file (SPEC 12.3). `internal/infra/drive/drivetest` stands in for Drive over `httptest`, as `googletest` does for the sign-in: a Drive for every token; the parent's own files never shown, which is the `drive.file` scope; the part of the search language the service uses, and a 400 that fails the test for anything else; exactly the fields asked for; uploads held to Drive's multipart form; the calls counted by kind, and the next call of a kind refused or left unanswered when a test asks. The store is `internal/store/drive`, package `drivestore`, as `internal/transport/mcp` is `mcpserver`, so that it does not share the client's name. — *Why:* five calls do not need Google's client library. `google.golang.org/api/drive/v3` brings the whole of it and its transports, the reason R107 turned down `idtoken`; its own instrumentation writes the address of every request into a span, and that address holds the file's ID; and a stand-in has to speak HTTP either way. Two packages, because CLAUDE.md's layout and R104 put Drive's API among the infrastructure, and RUN.md puts the store under `internal/store` (the author's decision, which settles note 1 of 01-context). The client changes when Drive's API does, and the store when what a profile needs of Drive does; T51 adds to both — revisions to the one, the recovery, the bin and a file set aside to the other. The client knows neither whose Drive it reaches nor the service's logs, like `cimd` and `googleauth`. What watches the calls is the store's, which knows the account. — *Rejected:* Google's client library, above; one package with the client unexported inside it, as RUN.md's wording had it, which would put Drive's request shapes and the profile's rules in one package that T51 then doubles; a mock of the client in place of the stand-in, which proves nothing about what the contract suite holds the two stores to (R43). — *Consequence:* no new dependency. The client's five methods are an interface's ceiling (CLAUDE.md), so the revisions T51 needs come as an interface of their own. **R116. **R125. What the sandbox's built-ins build is paid for by its bytes, an instance runs one solver for each vCPU, and it has 1 GiB, nine tenths of it told to the runtime.** Everything predeclared pays the step budget before it works: a step for every element it walks, as before, and for what it builds and hands back a step for every sixteen bytes, estimated from the sizes it was handed, with a quarter on top for the allocator's rounding. The estimates are:
- a list, 32 bytes and 16 for each value;
- a list of tuples, 32, and for each tuple 40 plus 16 for each value;
- a set or a dictionary, 512, and 256 for each entry;
- a whole number made past 32 bits as a range or a numbering is walked, 48;
- each sequence `product` and `zip` begin to walk, 64.

`internal/infra/starlark/price.go` holds them (SPEC 6.5). The cap of a million elements, and of a tuple of a million values, is unchanged, and `product` now reads its pools where they are instead of copying them out once for every repeat.

`MATHTRAIL_SOLVER_CONCURRENCY` defaults to 1, and a deployment sets it from its `cpu`, a whole number of vCPUs. The instance's `memory` is `1Gi`, with at least 1 GiB for every vCPU at the default step ceiling and more in proportion to a higher one, and a deployment sets `GOMEMLIMIT` to nine tenths of it. `settings` may set neither. The steps stay at twenty-five million, the clock at two seconds, the wait at three, and the requests of an instance at eighty. The line that says the sandbox is built now also says what the runtime got: its processors and its soft limit.

The load of T52a runs every Monday against the image of what is on `main`, by hand, and on a pull request that changes it (`.github/workflows/load.yml`, `just ci-load`). Each run is held to the memory measured for it, with room to spare, and the reports are the run's summary.

— *Why:* the author's decisions, taken while planning T52b on what T52a measured.
- **The budget of steps limited processor time, not memory.** A value cost one step whatever it took, so pairs held 824 MiB in one run, and a single call could build some 400 MB before anything looked. Priced by bytes, the steps bound what the built-ins of a run keep: 381 MiB at the ceiling. The four numbers of an instance can then be set against each other: one run's worth, the collector's as much again, and the service beside them come to a GiB for each solver running at once.
- **One slot for each vCPU, because the clock is wall time.** Runs sharing a processor each spend it on the others' work, and the verdict of a task — accepted, or rejected as too slow at the cost of an attempt — would turn on what happened to run beside it.
- **Memory costs nothing inside the free tier up to 2 GiB for each vCPU,** since vCPU-seconds run out first.
- **`GOMEMLIMIT` keeps garbage within the instance.** `product` keeps little and lets go of a great deal: four of it at once on an instance of 512 MiB peak at 469 MiB with the soft limit, and end the instance with `GOMEMLIMIT=off`.

Measured on the development machine in a container of one vCPU and 1 GiB (`docs/load.md`):
- every scenario is clean: `tuples` peaks at up to 782 MiB, `pairs` at up to 705, and `sets` between 411 and 580 as the collector chose;
- with eighty hand-ins in flight past the instance's pace, every call was answered within 6.2 seconds, 85 % of them as busy;
- at 512 MiB every scenario survives too, but at its soft limit, 50 MiB short of the kill, with the heaviest runs a fifth to a third slower;
- with four slots at 1 GiB, `tuples` and `pairs` end the instance, and a solver that needs 0.62 seconds alone is stopped by the clock in 38 runs of 44.

— *Consequence:*
- A set costs some twenty steps an element, and a run may hold one of a million. The costliest reference solver rises from 2,081,362 steps to 2,413,617, still under a tenth of the ceiling.
- A hand-in that finds the one slot taken for its wait is told the sandbox is busy. It spends no attempt, where four slots would have blamed its solver.
- One account handing in solvers that spend their whole clock, for requests nobody opened, keeps an instance's single slot busy; a freed slot goes to whoever waited longest. Such a hand-in spends no attempt, so the account pays nothing for it. That stays open (`docs/load.md`).
- What the language builds by itself stays unpriced: literals, operators, the methods of values. `[{} for i in range(n)]` keeps 512 bytes for every nine steps and ended the instance of 1 GiB in the load. `[0] * n` and `xs = xs + xs` are as R45 and R53 say.
- Merging this changes the deployed service: a revision of 1 GiB, with the two variables.

— *What would change it:* that gap seen in the aggregate log. The fix is a solver in a process of its own with a memory limit on it, as R45 names.

— *Rejected:*
- **Four slots with the clock as insurance.** Verdicts depend on the load, 4 × 381 MiB needs 2 GiB, and a clock long enough to be insurance for four breaks the minute of R122.
- **The old price with 2 GiB.** Pairs still hold 824 MiB a run, and sets and empty tables stay unpriced.
- **A watch on the heap in the process that cancels a run past a line.** It cannot stop an operator inside one instruction, and cannot tell whose run grew.
- **The process of its own now.** A change of shape, and the author's decision.
- **Pricing what a call lets go of as well.** It would charge every small `max` for its iterator.
- **A second allowance in bytes beside the steps, R53's option.** It is a second number to calibrate where one price bounds both.
- **Slots from `GOMAXPROCS`.** The runtime never sets it below two on a machine of two processors or more.
- **Reading `memory.max` inside the service.** A deployment's environment already says it.

— *Where it lives:* `internal/infra/starlark/price.go`, `vocabulary.go`, `combinatorics.go`, `starlark.go` and their tests; `internal/config/config.go`; `internal/app/container.go`; `infra/terraform/variables.tf`, `service.tf`; `tools/load/`; `justfile` (`ci-load`); `.github/workflows/load.yml`; SPEC 6.5, 6.6, 10.5, 11.1, 11.2 and remarks 15 and 63; `docs/load.md`; `docs/self-hosting.md`.

## The cloud

**R26. Terraform owns every cloud resource, and the three things it must not hold stay out of it.** `infra/terraform/` describes the enabled APIs, the image repository with its cleanup policies, the two secrets, the runtime identity, the Cloud Run service, its public invoker binding, the domain mapping, the spend alert and the federated identity a deployment arrives as. What it does not describe: the **values** of the secrets, which are added with `gcloud` by hand; the **project, its billing and the Google OAuth client**, which exist before the first apply; and **domain ownership and DNS**, which live with the registrar. Because a revision cannot start before its secrets hold something, the first apply is two passes — the secrets, then everything else — and that order is the self-hosting page's spine. — *Why:* a state file holding the sealing key is a copy of the key in a bucket that anyone with state access can read, and the key is the one secret whose loss forges every token; a project or an OAuth client recreated by a tool takes the parents' `drive.file` grants with it, and those cannot be recovered. — *Rejected:* `google_secret_manager_secret_version` resources with the values in variables, which puts both secrets in the state; a bootstrap module creating the project and the billing link, which makes a `destroy` capable of deleting the one thing that must never be recreated. — *Where it lives:* `infra/terraform/`, [self-hosting](self-hosting.md), T20.

**R27. The custom domain is a Cloud Run domain mapping in `us-central1`, and the platform's own address is withdrawn.** The region is chosen by two constraints at once: only a handful of regions offer domain mappings at all, and the free allowance is a discount at first-tier prices. The mapping is in Terraform, and `default_uri_disabled` is a variable that is turned on as a step of its own once the domain answers — Cloud Run asks for a domain to be mapped before its own address is withdrawn, and until the certificate is issued that address is the only way to reach anything. — *Why:* PRODUCT 7 asks for our own domain and PRODUCT 6 for $0, and a domain mapping is the only thing that satisfies both — a global external Application Load Balancer bills a forwarding rule by the hour whether or not anybody visits. One entrance also means one issuer, which is what the sign-in metadata depends on. — *Consequence:* Google labels domain mappings a preview feature and says they are not production-ready, citing latency; that is accepted for v1 and recorded as О-52, to be judged on the numbers from the live runs rather than on the label. If the latency turns out to be real, the escape hatch is a load balancer and a monthly bill. — *Rejected:* a load balancer from the start, which breaks the cost requirement before a single child has used the service; serving on the `run.app` address, which PRODUCT 7 rules out. — *Where it lives:* `infra/terraform/service.tf`, [self-hosting](self-hosting.md), PRODUCT 12.2 (О-52).

**R28. gcloud is installed for x86_64 only.** Its x86_64 archive carries a Python interpreter of its own and runs straight out of the tarball; the arm archive expects to find a system Python, and this image has none. On arm the same commands are run from Google's own `google-cloud-cli` image. Terraform, being one static binary, is installed on both. — *Why:* the alternative is a distro Python from `apt`, which would be the only unpinned thing in an image where everything else is an exact version, and an exact `apt` pin breaks on the day Ubuntu supersedes the package. Running a tool from a pinned container image is what this repository already does for everything that is not Go. — *Where it lives:* `.devcontainer/Dockerfile`, [self-hosting](self-hosting.md).

**R29. The deployment owns which image is served; the configuration owns everything around it.** `google_cloud_run_v2_service` ignores changes to `template[0].containers[0].image`, so the `image` variable is only what a newly created service starts with — the placeholder that lets a fresh project apply cleanly — and after that a deployment rolls revisions with `gcloud run services update --image <digest>`. — *Why:* two owners and no rule between them is drift by construction: a deployment publishes a digest and the next `terraform apply` puts the placeholder back. Of the two ways to settle it, this one keeps the deployment identity as narrow as T20 made it; the other — a pipeline running `terraform apply -var image=…` — would hand a workflow the state bucket and the right to change every resource in the project in order to move one string. — *Consequence:* the digest that is live is not recorded in the state, so "what is deployed" is a question for Cloud Run (`gcloud run services describe`), and a rollback is a revision — `gcloud run services update-traffic --to-revisions=…`, or the deployment run again at an older commit — never a `terraform apply`. — *Rejected:* Terraform applying from a workflow; leaving the field unignored and hoping the two owners agree. — *Where it lives:* `infra/terraform/service.tf`, `.github/workflows/deploy.yml`, T21.

**R30. A deployment is configured by repository variables, one per Terraform output, and holds no secret at all.** *(The variables half is superseded by R33: the configuration moved into the repository, and the only repository setting left is one secret. What stands is the rest — the triggers, and the federated token as the only credential.)* Six variables carry the target — the identity provider, the deployment identity, the image repository, the service, its region and the public address — and each is a copy of one output of the configuration that created it. The only credential is the federated token the workflow mints for itself; there is no service account key anywhere, and nothing in the repository or in its settings is secret. A deployment starts on a push to `main`, which is what a merged pull request produces, or by hand, and then it deploys whatever branch it was started from. — *Why:* variables rather than secrets, because none of these values is one and pretending otherwise makes them harder to read when a deployment misbehaves; one variable per output, because then the question "where did this value come from" has one answer. Pushes to `main` are the trigger because the checks gate the pull request that produced them, and running the same checks again in the deployment would double every merge for a verdict already given. — *Consequence:* a commit pushed straight to `main`, past a pull request, is deployed without the checks having finished — so the branch is protected, and the previous revision is one command away. — *Where it lives:* `.github/workflows/deploy.yml`, [self-hosting](self-hosting.md), T21.

**R32. The cloud is delivered by the pipeline, and what the pipeline signs in through is not the pipeline's to create.** `terraform apply` runs on every push to `main` and on a manual run from any branch; a pull request that touches `infra/` gets a `plan` in its summary. What stays outside is `infra/bootstrap.sh`, run once by a person: the project and its billing, the bucket the state lives in, the federated pool with its GitHub provider, and the identity Terraform is applied as. The two secret values are seeded by the apply itself and only when they are empty — the sealing key is 32 bytes generated in the job, the Google client secret comes from the one repository secret. — *Why:* the author's decision: deployments are not done by hand. Everything Google exposes through an API therefore belongs to the pipeline, and what is left by hand is left for a reason that can be named — no API exists (the consent screen and the OAuth client), the record lives at a registrar (DNS), or it is the door the pipeline walks in by. A sealing key generated inside the job is also simply better than one pasted through a form: nobody has to be trusted with a value nobody ever sees. — *Consequence:* an apply on every merge means a change made by hand in the console is undone, silently, by the next merge; that is the intent, and it is worth knowing before somebody edits a service in the console. The identity that applies the configuration is broad within its one project — an enumerated set of roles, not Owner — and holds no key at all: only a federated token from this repository, under a condition naming the owner's numeric id. It is deliberately not the identity that rolls out images; the narrow one from R29 stays as it was. — *Rejected:* a service account key in a repository secret, which would let a workflow bootstrap itself at the price of the one thing this design does not have; Cloud DNS, so that the records could be Terraform's too, because a managed zone is billed monthly and $0 is a requirement; `terraform apply` from a laptop, which is what this replaced and which survives as the documented path for when the pipeline is unavailable. — *Where it lives:* `infra/bootstrap.sh`, `.github/workflows/deploy.yml`, `justfile`, [self-hosting](self-hosting.md), T22.

**R33. The deployment's configuration lives in the repository.** `infra/terraform/prod.auto.tfvars` (project, region, host, client id, repository and owner id, pool id), `infra/terraform/backend.hcl` (the state bucket) and `infra/ci.env` (the provider and the identity a workflow needs before it can sign in) are committed. There are no repository variables, and there are two repository secrets: the OAuth client's secret and the id of the billing account. The billing account is the one deployment fact deliberately kept out of the files — it is not a credential, and no API accepts it without IAM, but it names the account that pays and this repository is public, so it arrives from the environment as `TF_VAR_billing_account`, which Terraform reads by itself. — *Why:* changing where this service deploys is then a pull request with a diff and a reviewer, rather than a field in a settings page whose history nobody can read. None of the values is a secret — a client id travels in every authorization request, and the pool is guarded by its condition rather than by the obscurity of its name — and the REST API that would have written repository variables needs a personal access token with `repo` scope, a credential worth more than the values it would set. — *Consequence:* a public repository states which project, project number and host this deploys to; that is accepted. A fork edits three files and runs the bootstrap, and needs nothing else. — *Where it lives:* `infra/terraform/prod.auto.tfvars`, `infra/terraform/backend.hcl`, `infra/ci.env`, `.gitignore`, T22.

**R34. The liveness probe answers on `/health`, and never on `/healthz`.** The frontend that sits in front of a Cloud Run service answers the literal path `/healthz` itself, with its own HTML page, and the request never reaches the container. Measured on the first delivery, against a service that was in fact healthy: `/healthz` was intercepted on both the platform's own address and the mapped domain, while `/health`, `/healthzz`, `/healthz/`, `/livez` and `/readyz` all arrived and were answered by our router. The deployment check asks for `/health`. — *Why:* the failure it caused is the expensive kind — a green service, a red delivery, and a probe that cannot be reached from anywhere outside. It cost an afternoon to find because everything else was working, and the difference between the two paths is one letter. — *Consequence:* the path appears in the endpoint tables, in the deployment check and in the container's own comment, which says why it is not the conventional name; a copy of this service running anywhere else is unaffected, because `/health` is reserved nowhere. — *Rejected:* `/livez` or `/readyz`, which arrive today but belong to the same family of names the platform helps itself to; `/healthz/` with its trailing slash, which our router redirects and which therefore works by accident rather than by design. — *Where it lives:* `internal/transport/http/router.go`, `justfile`, SPEC 9.1, T22.

**R35. A finding from the static analysis is answered by changing the code; accepting one is the last resort and carries a written reason.** The first full sweep of the 27 findings on the new code is what set the rule, and what it changed is worth listing, because most of it was not a considered position but a line nobody had reread: every download now refuses a protocol downgrade, on itself and on redirects; the development image is installed from a registry at an exact version rather than by running an installer script off the network, and no longer defaults to root; the deployment identity holds a role of five permissions instead of a ready-made one of sixty, which had included deleting the service and opening a root shell inside a running container; the site's footer navigation is named for a screen reader; and two shell scripts name their parameters. One finding stayed and is marked in place: the `"http://"` in the site check is the string that check searches for, and removing it removes the check. A second pass merged the two remaining adjacent `RUN` instructions and stopped there, because both other findings turned out to cost more than they were worth, and the cost was measured rather than assumed. Installing the editor's Go tools the way the rule wants means a second Go module in the repository with a `go.sum` of its own to keep current, for versions that are already exact and already verified against the Go checksum database; it was written, read, and taken back out. Forbidding every npm install step means the Claude Code CLI loses the native binary that step puts in place and starts through a Node wrapper instead, every time it runs. Both are marked, and those are the reasons. — *Why:* a mark makes the number go down and leaves the reason where it was, and this sweep found that the reasons were mostly real. The one exception is what a mark is for: an analyser that cannot tell a protocol from a search term. — *Consequence:* the identity that applies the configuration gained the right to write roles, because the configuration now defines one; a deployment that never had to delete a service can no longer do so, and if some later step turns out to need a permission the five do not cover, it fails in the delivery and the list grows by one. — *Where it lives:* `.devcontainer/Dockerfile`, `infra/terraform/deploy.tf`, `infra/bootstrap.sh`, `site/templates/page.html`, `internal/site/check/check.go`.

**R36. The environment asks nothing of the host beyond Docker itself, and that is a rule, not a convenience.** Whoever opens this repository installs Docker and VS Code and reopens in the container; no builder plugin, no daemon configuration, nothing edited as root. Two things follow. The image is written for any builder — no `RUN --mount`, no heredocs — so build caches are what the builder happens to offer rather than something the file depends on. And the network the container runs on is created before it starts, by `.devcontainer/host-network.sh` through `initializeCommand`, carrying the MTU of the host's own default route; `post-start` mirrors that value onto the docker running inside the container, which would otherwise hand its own networks 1500 again. — *Why:* a tunnel on the host — a VPN, in practice — makes the real limit smaller than the 1500 Docker assumes, and then a container's large downloads stop after a few kilobytes while small requests answer normally; nothing in the error names the network, and the hours go into the Dockerfile instead. The first fix written for it was a daemon setting applied by hand on one machine, which is exactly the kind of instruction this project does not get to give. Detecting the host's MTU and building the container's network with it costs twenty lines and holds for anyone, not just the machine it was debugged on. — *Consequence:* the container runs on a named network rather than the default bridge, and that network is created on every start — a host without `bash`, such as Windows outside WSL, cannot run the script and needs the network made by hand. A host whose tunnel appears or disappears keeps the MTU the network was built with: the script says so and names the one command that clears it, because a network in use cannot be changed from under a running container. Downloads inside the image go through one helper with `--retry-all-errors`, because the failure this was all written for — a transfer that dies partway — is not one a plain `--retry` repeats. — *Rejected:* cache mounts and the BuildKit-only syntax they need, which bought faster rebuilds at the price of a plugin the host had to have; telling each person to set `default-network-opts` in their daemon, which is the same fix written as a chore. — *Where it lives:* `.devcontainer/host-network.sh`, `.devcontainer/devcontainer.json`, `.devcontainer/post-start.sh`, `.devcontainer/Dockerfile`.

**R49. Traces and metrics go straight to the platform's standard endpoint, and a request pays for its own delivery.** `internal/telemetry` builds a tracer provider and a meter provider on every start, and attaches OTLP-over-HTTP exporters to them only where there is somewhere to send: `https://telemetry.googleapis.com`, signed with the credentials the platform issues, naming the project in a `gcp.project_id` resource attribute and in the `X-Goog-User-Project` header. The sampler keeps a tenth of the traces whatever a request arrives saying: a remote parent, marked kept or not, goes through `TraceIDRatioBased(0.1)`, and our own spans follow their parent — the frontend's decision travels in a header a client can set too, and a client asking for every trace would be choosing what the service spends. A request whose trace is kept delivers its spans before it finishes, with a deadline of 200 ms, and measurements leave at most once a minute, as deltas, with whichever request finds them due, kept trace or not, beside the spans rather than after them so that each has the whole deadline. Off a deployment the switch is off and the providers drop everything, so no credential is needed to run the tests or the server. — *Why:* four numbers decide the shape. Google's own Go exporters (`exporter/trace` v1.38.0, `exporter/metric` v0.62.0) are deprecated and will be archived after 1 January 2027, and they post to this same endpoint, so taking them buys nothing and costs a migration. A sidecar collector wants 0.25–0.5 vCPU and 256–512 MB on every instance against 180 000 vCPU-seconds of free allowance, which is the whole budget spent on carrying telemetry rather than on answering children. `cpu_idle = true` means the processor is taken away once a response has been returned, so a batch left in memory after that is a batch that may never leave — hence a delivery inside the request. And the free allowances are what the labels are for: the platform's own system metrics and automatic traces are not billed at all, Logging gives 50 GiB a month, Trace 2.5 million spans, and custom metrics 150 MiB — a label carrying a user or a task identifier passes that last one in a week, so every label is a closed dictionary and every histogram's buckets are written out. — *Consequence:* the resource is built with `contrib/detectors/gcp`, which adds two Apache-2.0 modules and one call to the platform's metadata service at startup, and is what makes the instance identifier in a span the same one the console shows. HTTP rather than gRPC as the transport, because the credentials then attach as an ordinary `http.Client` and the collector a test posts to is an ordinary `httptest` server; it saves nothing in the binary, because the exporter's own configuration package imports gRPC whichever transport is chosen. Exporting at all costs this build 186 packages and 19 MB — 24.8 MB to 43.5 MB, measured — and that is the price of OTLP in Go rather than of anything decided here. It is also a standing maintenance cost: the image scan reads the modules linked into the binary rather than the code that runs, so a gRPC advisory now fails the build of a service that serves no gRPC, and the answer each time is to raise the version. The delivery carries its own 200 ms rather than trusting whoever asked for it to remember one, so a caller that brought no deadline still gets its goroutine back, and it is detached from the request, because a caller who hung up would otherwise take the spans with them. A delivery in the background is bounded by the processor that makes it, five seconds with every retry inside them: the exporters' own timeout applies only to a client they build for themselves, and they are handed the signed one. The collector's root is held to one rule, `collector.Root` in a package of its own that imports no exporter, so the configuration checks it with the same rule without carrying the SDK — http or https, a host and at most a path, with no user, query or fragment, and a refusal that never repeats what a secret could hide in — and the configuration adds only that it be https off this machine. The caller of a sampled request waits for the delivery too: a small answer leaves the process only when the handlers return, and the delivery is the last of them. That deadline costs what it saves: a delivery that misses it loses its batch, since the SDK discards a batch that failed to send rather than holding it for the next attempt, and the first delivery from a new instance — the one paying for the connection — is the likeliest to miss. Accepted, because the alternative is a child waiting on a collector; the number is revisited against the latencies of T64 rather than against a guess. and the one setting that belongs to the whole binary — the handler that reports a failed delivery — is installed at the composition root beside the web framework's mode, never by the constructor, because a constructor that reaches for a global changes what every other part of the same process reports. Neither a missing project nor missing credentials stops the service: both are reported once and leave export switched off, because an image can be rolled before the configuration that names the project reaches it, and a service that refused to start over telemetry would be an outage caused by observability. Enabling the telemetry endpoint is not enough on its own, which the first live run is what found: it accepts the data and decides nothing about keeping it, so a project without Cloud Trace has no bucket for a span to land in and one without Cloud Monitoring answers every measurement with a 403. The service reports either once and keeps serving, so nothing about it is loud — `apis.tf` enables all three. Enabling them is all it takes, and the first live run is also what showed how that looks while it is happening: the storage behind each is provisioned after the first data arrives rather than before, so for some twenty minutes a trace read answers `_Trace bucket not found` and no metric exists anywhere, while the service reports nothing because nothing of its own failed. Documented behaviour for Cloud Run — whose spans, unlike other senders', are not supposed to provision that storage at all — made this look like a missing manual step, and it is not one; `docs/self-hosting.md` says to wait rather than to click. Granting the runtime identity `roles/telemetry.writer` and `roles/serviceusage.serviceUsageConsumer` is the first binding this configuration makes on the project itself, so the identity Terraform is applied as gained `roles/resourcemanager.projectIamAdmin` in `infra/bootstrap.sh` — an existing project needs that grant re-run once before the first apply that carries this. — *Still open:* from 1 September 2026 Cloud Monitoring charges $0.35 a month for every metric named in an alerting policy. The spend alert of T20 is a Billing budget and is free of this; whether any of our own metrics is worth alerting on is a decision for T64. — *Rejected:* Google's own exporters, above; a sidecar collector, above; the Google Cloud Trace agent's `X-Cloud-Trace-Context` alone, which would tie the service to one platform's header instead of the standard one; relying on the periodic reader by itself, which under `cpu_idle` fires only when a request happens to wake the instance. — *Where it lives:* `internal/telemetry`, `internal/config`, `internal/app/container.go`, `infra/terraform/apis.tf`, `infra/terraform/service.tf`, `infra/bootstrap.sh`, SPEC 11.2 and 12.5.

**R50. A request cannot forge a log line, and the encoder is what stops it — not a sanitiser.** *(Superseded by R76 for the path and the verb, which no longer reach a log line: the alerts this entry answers went with them, and nothing here is a reason to dismiss a new one. What still stands is the encoder and its test, as the guard for whatever else a field carries.)* The code scan reports every place a request's own path, method or query reaches a log call (CWE-117, four alerts across `middleware/logger.go` and `middleware/recovery.go`). They are kept and answered rather than removed: a deployment writes JSON, a JSON encoder escapes newlines, quotes and control bytes, and `internal/logger` carries the test that holds it to that — a path of `/x\n{"severity":"ERROR",…}` comes back as one object whose `path` is that whole string and whose `severity` is still the one this service gave it. — *Why:* the attack the rule describes is a caller ending the line they are in and starting one of their own, and the encoder makes it impossible; the test says so in a way that a comment could not, because it goes red the day somebody swaps the encoder. The console format does not escape, and that is what it is for: it is read by a person at a terminal and never by a collector. A deployment refuses it, so that "never" is enforced rather than hoped for. — *Rejected:* stripping control characters out of the path before logging it, which would silence the alert and cost the one thing the line is read for — what was actually asked — while defending against nothing the encoder does not already; marking the alerts dismissed with no test behind the reason, which is the same claim without the evidence. — *Consequence:* the alerts stay open on the dashboard unless somebody dismisses them by hand, and the reason to give is this entry. — *Where it lives:* `internal/logger/logger_test.go`, `internal/transport/http/middleware/logger.go`, `internal/transport/http/middleware/recovery.go`.

**R73. A request's log line carries only the parameters defined to hold no data, and a panic is one field of it.** The request log writes the query parameters on a short list the sign-in and its protocols define — `code_challenge_method`, `error`, `grant_type`, `prompt`, `response_mode`, `response_type` and `scope` as the words their protocols define, with anything else in them written as `other` once, and `client_id`, `redirect_uri` and `resource` as a scheme and a host, which say which client or resource it is — and only counts the others, names included. A panic is caught by the recovery next to the handlers, below tracing, counting and the request log, so that a panicked request is answered 500, logged in its own request line, counted and delivered like any other; the line says what the request panicked with in the runtime's own words for a fault of the runtime, found inside whatever wrapped it, and by the value's type alone for anything else, beside the stack. Above everything stands a last resort for a panic of the middleware itself, which writes the one line the request log could not. A handler that panics with `http.ErrAbortHandler`, however wrapped, is passed on to the server as the abort it is: it is neither a panic nor an answer. The delivery of a sampled request's spans runs on the way out of an abort too, so it catches a panic of its own and writes it as a line of its own: a panic there would replace the abort with a 500. The errors a request collected are written by the same rule as a panic — a fault of the system in the system's own words, anything else by its type — because the text of a failed write names both ends of the connection; and for the same reason a span reaches the exporter without the text of its status, which the instrumentation fills with those errors. A connection that died under the service's own call is a fault like any other, since the framework reports a client that hung up as an error of the request rather than a panic. — *Why:* no personal data of a child, no task and no answer may reach a log, and a list of what to hide keeps out only what somebody thought of: a provider's `login_hint` carries a parent's email address and its `hd` the domain of a school, a name a caller chose can carry anything a value can, an address can hide an email address or a name in its path, its query or its user, and a panic value is whatever the code that panicked had in hand. A runtime fault is described by the runtime in types and numbers, the one kind of panic text that cannot carry data — and only a fault the runtime made, since any type can call itself a runtime error. One fault is one line, which is also what keeps a panic from being counted twice by whoever alerts on errors. — *Consequence:* a parameter this service starts to rely on is only counted until it is added to the list, and a panic of our own is found by its stack rather than its message. A value is chosen as freely as a name, so a listed parameter is held to its protocol's words — OAuth 2.0 with PKCE, resource indicators and registration, OpenID Connect, and the scopes this service and Google's sign-in speak, `mcp`, `openid` and `drive.file` among them — and an error of `alice@school.example` or a scope of a child's name is written as `other`. A scope the service starts to use is `other` in the log until it is added to the words. The recovery is this service's own rather than the framework's, because the framework's swallows an abort and lets the request be logged and counted as a 200. — *Rejected:* the list of secrets to mask, which is what this replaced; logging the panic's message after scrubbing it, which cleans a string rather than never writing it; a second line for the panic beside the request's. — *Where it lives:* `internal/transport/http/middleware/logger.go`, `query.go`, `recovery.go`, `tracing.go`, `internal/logger/panic.go` (where the rule for a panic moved in T41, so that the MCP endpoint writes a panic by it too), `internal/telemetry/redact.go`, `internal/transport/http/router.go` (T39a.3).

**R76. A request is named in a log line by the route it matched, never by the path it asked for.** The request's own line and the last resort's write `route` — the pattern the router declared, or `other` when nothing matched — and the method from the same closed list the metrics use, with `other` for a verb nobody defined. A probe is told by its route too, so the path a caller wrote is not read at all, and the traces blank the path and the verb the instrumentation records for itself. — *Why:* R73's own reason reaches the path: a name a caller chose can carry anything, and a path nothing matched is text a caller wrote, as free as the value of a query, which R73 already keeps out; a matched path carries identifiers the day a route has a parameter. The metrics and the traces already name a request this way (R49), so one request now reads the same in all three. It also removes what the code scan reports under CWE-117 rather than answering it: a fifth alert, raised when the path moved into `LastResort`, blocked the merge of the pull request that moved it. — *Consequence:* our log no longer says which path a 404 asked for. The platform's own request log still carries the whole address of every request, and that is where a path a host probed for — the sign-in's metadata documents, say — is found. A 405 is written as `other` too, since the framework matches no route for it. For the same reason a request for `/health` with a method nobody declared is no probe any more: it is logged, counted and traced like any other request that failed. — *Rejected:* keeping the path and dismissing each alert as R50 did, which answers the forged line and not the caller's text; stripping control characters out of the path, which R50 already rejected; holding the path's segments to a list of protocol words the way the query is held, which would keep the well-known paths readable at the cost of a second list to maintain, for what the platform's log already has. — *Where it lives:* `internal/transport/http/middleware/route.go`, `logger.go`, `recovery.go`, `probe.go`, `tracing.go`, `middleware_test.go`, `observability_test.go`, `internal/telemetry/redact.go`, SPEC 12.2.

**R74. The way out is one budget, in fixed shares.** `MATHTRAIL_SHUTDOWN_TIMEOUT`, nine seconds by default, is the whole time from a stop being asked for to the process ending: the server drains the requests in flight for three quarters of it, and the container is closed in the quarter left — a start that fails halfway is closed in the same quarter. — *Why:* the platform stops the process ten seconds after asking it to. Before this the drain and the close took the whole budget each, twenty seconds between them, and the part cut off was the telemetry's last delivery. Fixed shares keep each clock where it is used: the server measures its drain from the moment it sees the stop, the close is measured from the moment the server has returned, and the two add up to the budget with nothing to keep in step. The default stops a second short of the platform's ten, for the moment the signal takes to arrive and the lines written after the close. — *Consequence:* a close that needed more than its quarter does not get the time a quick drain left unused. The close is mostly the telemetry's final delivery, which takes well under a second against a collector that answers. A way out shorter than a second is refused at start, since a quarter of it would be no time to deliver anything in. A drain cut short by a request still running is a warning, not a failure: the stop was asked for and happened, and the process ends as it would have — an exit code of failure would dress every scale-down with a slow request up as a crash. — *Rejected:* one deadline taken when the stop arrives and shared by both, the drain taking up to its share and the close whatever is left. The process has to learn the moment of the stop outside the server, which costs either a wait on the group's context ahead of the group itself — a hang the day a member returns without that context ending — or a second clock kept in step with the server's; and it pulls the close out of a deferred call, where a panic or an early return would skip it. — *Where it lives:* `internal/config/config.go` (`DrainTimeout`, `CloseTimeout`), `internal/app/server.go`, `internal/app/container.go`, `cmd/server/main.go`, SPEC section 11 (T39a.6).

**R77. A stop that arrives while the service is starting is a stop, not a failed start.** When building the container fails because the process was told to stop — its context has ended, and the error is that ending passed back — `run` writes `shutdown` with `started: false` as information and the process exits with 0. Any other failure of the build is still a failed start, written once as an error, even when a stop arrived beside it. — *Why:* the platform sends its stop to an instance that is still starting when it replaces a revision or scales down, and with export switched on the trace exporter refuses to start on an ended context. That was an error line and an exit code of 1 for a stop that had been asked for, which anyone alerting on errors would read as a crash. Without export the same stop already ended cleanly, at the listener. — *Rejected:* treating every cancellation as a stop, which would also hide a context this process was never asked to end. — *Where it lives:* `cmd/server/main.go`, `cmd/server/main_test.go`, SPEC 12.2.

**R75. How a text reads on a card lives with the solver's options.** `solver.Key` and `solver.Blank`, with the folding behind them, decide when two texts are one answer and when a text shows nothing. They sit in `internal/domain/solver` beside the options' labels, although `checks`, `profile` and `content` also ask `Blank` about texts that are not options — a constraint, an explanation, the options of a stored task. — *Why:* it is one rule. The solver's `match` and the structure check have to agree on which options are one, a stored task has to be judged blank by the measure that let it in, and a reference task has to load by the measure a submitted one is held to. Whatever package held the rule, all four would import it: a package of its own would move the import rather than remove it, and would put the options' labels and the comparison of their texts in two places that only ever change together. — *Consequence:* a change to how a card reads changes which stored profiles validate and which reference tasks load. That is intended: they are the same texts. — *Rejected:* a small package for the text of a card, which is the same coupling under another name (T39a). — *Where it lives:* `internal/domain/solver/options.go`, SPEC 5.2.

**R51. Eight Scorecard findings stay open, and none of them is a thing to fix.** They arrive as code-scanning alerts beside CodeQL's and are answered here once rather than re-argued at every scan. **Two are false for this configuration.** `Dangerous-Workflow` (critical) reports the release workflow checking out `workflow_run.head_sha`; Scorecard does not read the `if:` that guards the only job in that file, which requires the triggering run to be a push whose head repository is this one, so a fork's pull request can never reach it — the same reasoning R40 records. `Vulnerabilities` reports GO-2026-5932, the advisory that `golang.org/x/crypto/openpgp` is unmaintained and unsafe by design; the module is required for `chacha20poly1305` in `seal` and that one package is imported nowhere, which `govulncheck` — which follows reachability rather than a dependency list — confirms by finding nothing. The advisory has no fixed version, so no upgrade clears it. **Three need a second person.** `Code-Review` counts approved changesets and finds none, `Branch-Protection` wants required approvers, codeowners review, stale-review dismissal and last-push approval, and every one of those asks somebody other than the author to approve. A solo project cannot satisfy them, and inventing a second account to do so would be worse than the score. **Two heal by themselves.** `Maintained` warns that the repository is younger than ninety days, and `SAST` counts thirteen of twenty-six commits scanned because the CodeQL workflow was added halfway through the history; both improve with nothing but time, as does `CI-Tests` at twenty-five of twenty-six. **One is already decided.** `Pinned-Dependencies` wants the npm install pinned by hash; R35 explains why that install step exists at all, and npm verifies the tarball against the registry's own integrity hash, which is the verification available to a global install. — *Why:* a check that will be red for the life of a one-person project is not a defect, and treating it as one costs either a fabricated reviewer or an afternoon per scan. Naming them once means the next reader can tell the eight that are answered from the one that would be new. — *Consequence:* the Scorecard score stays where it is, deliberately; a finding that is not on this list is worth reading. — *Where it lives:* `.github/workflows/release.yml`, `.github/workflows/codeql.yml`, `.devcontainer/Dockerfile`, R35, R40.

## The public site

**R23. The site is built by a small Go program, and all of it is temporary.** `cmd/sitegen` builds `site/` into `site/dist/` with `html/template` and goldmark; `cmd/sitecheck` then judges the finished directory. Both are replaced by the widget's own Preact and Vite toolchain once that exists — the renderer first, the checker one task later, for the reason in R25. — *Why:* the privacy policy has to be live before the first deployment, because Google will not release the consent screen without it, and `web/` does not exist yet at that point. Reaching for npm here would either block the policy behind the widget build or introduce a second, throwaway JavaScript toolchain. Go is already pinned, already in the image, and already the language the tests are written in. — *Rejected:* hand-written HTML per page and per locale, which duplicates the masthead, the footer and the language switcher into every file and drifts by the third locale; a static site generator, which is a new toolchain and a new license to track for six pages. — *Consequence:* goldmark and a direct `golang.org/x/net` sit in `go.mod` for programs the service does not ship, and both leave with the programs that needed them. — *Where it lives:* `internal/site/`, `cmd/sitegen`, `cmd/sitecheck`, T19, T66, T66c.

**R24. The address scheme is decided once and never moved.** Every page lives at `/<locale>/` or `/<locale>/<page>/`; the apex is a page in its own right — the product's name, its one line and the languages it exists in — rather than a redirect. hreflang x-default points at the apex for a front page and at the reference locale for anything else. — *Why:* the addresses of the privacy policy and the terms are handed to Google for the consent screen and to the directories for the listing, and neither forgives a link that moved. The apex is what a product is listed under, and a redirect is a poor thing to list; Google also expects the policy to sit on the domain that hosts the home page, which the scheme satisfies by construction. — *Consequence:* T66 may replace the renderer but not the addresses, and `sitecheck` fails the build if a page that was published disappears. The authorized domain registered in T22 is the top private domain, which covers both the site on the apex and the service on its subdomain. — *Where it lives:* `internal/site/render`, `internal/site/check`, T19, T22, T66.

**R25. The checker outlives the renderer by exactly one task, and then the site owns no Go at all.** T66 replaces the renderer and keeps `cmd/sitecheck` untouched; T66c ports the five rules to TypeScript under `web/tools/sitecheck/` and deletes `internal/site/` and `cmd/sitecheck`. The ported checker takes a directory and nothing else, and a lint rule forbids it to import from `web/src/**`. — *Why:* the author's decision that no Go about the site survives the project. Doing it in two steps is not caution: while the renderer moves, the old checker is the only judge that has no stake in the new builder, so "the Vite output still passes the unchanged checker" is real evidence rather than a build agreeing with itself. The same reasoning is what the lint rule protects afterwards — a checker that imports the builder's `hreflang` tests that a function equals itself, and in one language that import is one keystroke away. — *Rejected:* keeping the Go checker for good, which leaves a second toolchain in the repository for one program; off-the-shelf npm checkers, which cover dead links and markup validity but not the three rules that matter most to a site in twenty-two languages — no third-party loads, a complete hreflang matrix, and no locale quietly missing a page; moving both at once, which would leave a disagreement with no arbiter. — *Consequence:* after T66 the site is no longer covered by `just ci-test`, and `just ci-site` — already on every pull request — becomes its only gate. The design tokens stay a plain CSS file rather than a bundle artefact, because the consent screen and the sign-in error pages are rendered by the service itself and read the same file (SPEC 8.9). — *Where it lives:* `web/tools/sitecheck/`, T48, T66, T66c.

## The boundaries of v1

**R14. There are no printable task sheets in v1.** There will be no tool that hands the adult 3–5 checked tasks as a single text. — *Why:* the profile stores fingerprints of past tasks, not their texts (О-40), so a sheet could only be assembled from tasks generated on the spot: 3–5 generations in a row, which is the message limit of a free tier, a daily-limit calculation of its own, and in effect a return to the cancelled task buffer (О-6). — *Where it lives:* PRODUCT 2 ("not included"); no separate task is added in phase 7 (О-47).
